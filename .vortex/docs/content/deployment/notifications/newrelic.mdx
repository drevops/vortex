# New Relic

The New Relic channel records each deployment as a [deployment
marker](https://docs.newrelic.com/docs/apm/apm-ui-pages/events/record-deployments/)
in New Relic APM, so you can line up a code change with the performance
data around it.

## Setup

1. [Create a New Relic User API
   Key](https://docs.newrelic.com/docs/apis/intro-apis/new-relic-api-keys/#user-key)
   (format: `NRAK-XXXXXXXXXXXXXXXXXXXXXX`).
2. Set `NEWRELIC_ENABLED` (or `VORTEX_NOTIFY_NEWRELIC_ENABLED`) in the
   hosting environment variables of the environments where New Relic is
   configured. Any non-empty value turns the channel on.
3. Add `VORTEX_NOTIFY_NEWRELIC_USER_KEY` to your hosting provider's
   environment variables. Without it, the channel falls back to
   `NEWRELIC_USER_KEY`.

:::tip Enable only where needed

Set `NEWRELIC_ENABLED=true` only in environments where New Relic APM is
configured (typically production and staging), and leave it unset
everywhere else. The channel checks only that the value isn't empty, so
`false` and `0` switch it on too. Keeping it off elsewhere avoids API calls
and potential errors in development or feature branch environments.

:::

## Environment variables

| Variable | Required | Default | Location | Description |
|----------|----------|---------|----------|-------------|
| `VORTEX_NOTIFY_NEWRELIC_ENABLED` | **Yes** | `NEWRELIC_ENABLED` | Hosting | Turns the channel on; any non-empty value counts |
| `VORTEX_NOTIFY_NEWRELIC_USER_KEY` | **Yes** | `NEWRELIC_USER_KEY` | Hosting | New Relic User API Key |
| `VORTEX_NOTIFY_NEWRELIC_PROJECT` | No | `VORTEX_NOTIFY_PROJECT` | `.env` | Project name |
| `VORTEX_NOTIFY_NEWRELIC_APP_NAME` | No | `<project>-<label>` | `.env` | Application name as it appears in New Relic |
| `VORTEX_NOTIFY_NEWRELIC_APPID` | No | Looked up by application name | `.env` | Application ID |
| `VORTEX_NOTIFY_NEWRELIC_DESCRIPTION` | No | Default template | `.env` | Deployment description |
| `VORTEX_NOTIFY_NEWRELIC_CHANGELOG` | No | Description | `.env` | Deployment changelog |
| `VORTEX_NOTIFY_NEWRELIC_USER` | No | `Deployment robot` | `.env` | User performing deployment |
| `VORTEX_NOTIFY_NEWRELIC_REVISION` | No | `VORTEX_NOTIFY_NEWRELIC_SHA`, or `<label>-<date>-<time>` without one | Hosting | Deployment revision |
| `VORTEX_NOTIFY_NEWRELIC_ENDPOINT` | No | `https://api.newrelic.com/v2` | `.env` | API endpoint |
| `VORTEX_NOTIFY_NEWRELIC_BRANCHES` | No | `main,master,develop` | `.env` | Restrict to specific branches (comma-separated) |
| `VORTEX_NOTIFY_NEWRELIC_LABEL` | No | `VORTEX_NOTIFY_LABEL` | Hosting | Deployment label |
| `VORTEX_NOTIFY_NEWRELIC_SHA` | No | `VORTEX_NOTIFY_SHA` | Hosting | Commit SHA used as the revision |
| `VORTEX_NOTIFY_NEWRELIC_ENVIRONMENT_URL` | No | `VORTEX_NOTIFY_ENVIRONMENT_URL` | Hosting | Environment URL |
| `VORTEX_NOTIFY_NEWRELIC_LOGIN_URL` | No | `VORTEX_NOTIFY_LOGIN_URL` | Hosting | Login URL |
| `VORTEX_NOTIFY_NEWRELIC_EVENT` | No | `VORTEX_NOTIFY_EVENT`, then `post_deployment` | Hosting | Deployment event; `pre_deployment` records nothing |

When `VORTEX_NOTIFY_NEWRELIC_APPID` is empty, the channel looks the
application up by name. If no application matches, it skips the
notification and passes, which is what you want in environments New Relic
doesn't monitor. Like most channels, it skips `pre_deployment`.

An empty `VORTEX_NOTIFY_NEWRELIC_BRANCHES` falls back to the default list,
so list every branch you want New Relic to hear about.
