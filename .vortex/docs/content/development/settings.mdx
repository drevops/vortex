# Settings

Drupal reads its site configuration from `settings.php` and `services.yml`:
database connections, file paths, and everything that should behave
differently from one environment to the next. **Vortex** ships its own
versions of
[`settings.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/settings.php)
and
[`services.yml`](https://github.com/drevops/vortex/blob/main/web/sites/default/services.yml),
built so the same files work in every environment.

The shipped `settings.php` works out where the site is running (locally, in
CI, or in a hosting environment) and applies settings to match. Each
module's overrides live in a small file of their own, so you can see at a
glance what a module does differently in each environment.

Drupal Scaffold's own
[`default.settings.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/default.settings.php)
and
[`default.services.yml`](https://github.com/drevops/vortex/blob/main/web/sites/default/default.services.yml)
are there too, if you'd rather start from those.

This page is for developers who need a setting to differ between
environments, and for the lead or DevOps engineer bringing a project onto a
hosting platform. It explains how `settings.php` detects the environment and
which variables it reads. It also shows how to add your own per-module
overrides and test them. For the full list of variables, see
[Variables](variables.mdx).

## Approach

A site rarely runs the same way everywhere. Local, CI, development, staging,
and production environments each need their own adjustments: a module on
here and off there, different performance settings, different APIs, or
different services to talk to.

Drupal has no standard way to manage these differences. Its configuration
system isn't built for conditional logic, such as applying different
settings per runtime environment or reading values from environment
variables.

Modules like `config_split` let you maintain separate configuration sets per
environment, but they're limited. They don't support environment-based
conditions inside the configuration YAML files, and they can't read
environment variables directly. They also don't help when you need dynamic
logic (for example, setting values based on external service URLs).

**Vortex** still ships `config_split`, and it's the right tool when
declarative configuration is enough, such as enabling a module in staging
but not in production. It falls short when settings need conditional logic
or values from the environment. It also gives you no way to test
automatically which settings apply in a given environment.

So **Vortex** splits the job in 2:

- The _environment type_ is [detected](#environment-type-detection) from the
  environment the site runs in. This step applies the hosting platform's own
  settings, but no module configuration.
- Configuration overrides live in [per-module override
  files](#per-module-overrides), with conditions based on the detected
  _environment type_.

The split pays off in 4 ways:

- It keeps environment detection separate from configuration logic.
- It shows in 1 place how a module behaves in a specific environment.
- It lets you delete a module's override file without touching
  `settings.php` when the module is no longer needed.
- It stops environment-specific settings from leaking into unrelated parts
  of the configuration.

### In practice

Say the business asks to let an external stakeholder review the `stage`
environment, which [Shield](modules/contributed-modules.mdx#shield) protects
with HTTP authentication. The shipped `settings.shield.php` override already
reads the `DRUPAL_SHIELD_DISABLED` variable, so you can make the change
without editing code:

1. In your hosting provider's environment variables, set
   `DRUPAL_SHIELD_DISABLED=1` on the `stage` environment.
2. Apply the variable: Acquia applies it on its own, and Lagoon needs a
   deployment. The `stage` site then opens without the HTTP authentication
   prompt.

When the review is over, remove the variable and apply the change the same
way. Confirm that the `stage` site asks for the Shield credentials again.

You don't commit anything, and no other environment changes, because the
override file defines the behavior once and each environment opts in through
its own variables.

## Settings file structure

The
[`settings.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/settings.php)
file is organized into the following sections:

- [Database](#database)
- [General](#general)
- [Environment type detection](#environment-type-detection)
- [Per-module overrides](#per-module-overrides)
- [Local overrides](#local-overrides)

The sections run in a fixed order and load more files along the way:

```text
🚀 Drupal bootstrap
   │
   ▼
📄 web/sites/default/settings.php
   │
① 🛢️ Database
   │  Connection credentials from environment variables.
   ▼
② ⚙️ General
   │  File paths, hash salt, timezone, maintenance theme.
   ▼
③ 🔍 Environment type detection
   │  Requires environment.drupal.php from the drevops/environment-detector
   │  package. The detector applies the active platform's settings and
   │  stores the detected type in $settings['environment']. No module
   │  overrides are applied here.
   ▼
④ 🧩 Per-module overrides
   │  Loads every web/sites/default/includes/modules/settings.<module>.php,
   │  each applying its overrides based on the detected environment type.
   ▼
⑤ 🏠 Local overrides
   │  Loads web/sites/default/settings.local.php and services.local.yml
   │  when present (local development only).
   ▼
🏁 Fully configured site
```

Projects with the migration feature load 1 more file between the per-module
overrides and the local overrides: `settings.migration.php`, which defines
the [migration database connection](migrations.mdx#drupal-settings).

### Database

The database connection comes from environment variables, with a default
for each value.

Hosting providers and container images name these variables differently, so
each setting accepts several names and uses the first one that's set:

| Variable             | Alternative variables                   | Default              | Purpose           |
|----------------------|-----------------------------------------|----------------------|-------------------|
| `DATABASE_NAME`      | `DATABASE_DATABASE`, `MARIADB_DATABASE` | `drupal`             | Database name     |
| `DATABASE_USERNAME`  | `MARIADB_USERNAME`                      | `drupal`             | Database username |
| `DATABASE_PASSWORD`  | `MARIADB_PASSWORD`                      | `drupal`             | Database password |
| `DATABASE_HOST`      | `MARIADB_HOST`                          | `localhost`          | Database host     |
| `DATABASE_PORT`      | `MARIADB_PORT`                          | `3306`               | Database port     |
| `DATABASE_CHARSET`   | `MARIADB_CHARSET`, `MYSQL_CHARSET`      | `utf8mb4`            | Character set     |
| `DATABASE_COLLATION` | `MARIADB_COLLATION`, `MYSQL_COLLATION`  | `utf8mb4_general_ci` | Collation         |

The table prefix is always empty, and the driver is always `mysql`.

You rarely need to set these yourself: the local stack sets them in
`docker-compose.yml`, and the alternative names cover providers and images
that use their own. For a custom database setup, or a hosting provider that
needs specific values, set them in that environment.

### General

This section sets the values every environment needs, and it doesn't look
at the environment type. The environment detector in the
[next section](#environment-type-detection) can adjust a few of these
values for its platform, such as the temporary directory on Acquia.

The following environment variables customize it:

| Variable                    | Alternative variables | Default                           | Purpose                                  |
|-----------------------------|-----------------------|-----------------------------------|------------------------------------------|
| `DRUPAL_CONFIG_PATH`        | None                  | `../config/default`               | Location of configuration sync directory |
| `DRUPAL_PUBLIC_FILES`       | None                  | `sites/default/files`             | Public files directory path              |
| `DRUPAL_PRIVATE_FILES`      | None                  | `sites/default/files/private`     | Private files directory path             |
| `DRUPAL_TEMPORARY_FILES`    | `TMP`                 | `/tmp`                            | Temporary files directory path           |
| `DRUPAL_HASH_SALT`          | None                  | SHA-256 hash of the database host | Cryptographic salt for security          |
| `DRUPAL_TIMEZONE`           | `TZ`                  | `UTC`                             | Runtime timezone                         |
| `DRUPAL_MAINTENANCE_THEME`  | `DRUPAL_THEME`        | `claro`                           | Theme used during maintenance mode       |

It also does the following, and no variable changes it:

- Loads `services.yml` as a service container definition
- Skips the `node_modules` and `bower_components` directories in file
  scans
- Sets `auto_create_htaccess` to `FALSE`, so Drupal creates no `.htaccess`
  files in writable directories
- Updates entities in batches of 50
- Starts an empty `config_exclude_modules` list for the per-module files to
  fill

The page cache lifetime (`DRUPAL_CACHE_PAGE_MAX_AGE`, default `900` seconds)
is set in the `settings.system.php`
[per-module override](#per-module-overrides), not in this section. The full
generated list of `DRUPAL_*` variables is in the
[Variables reference](variables.mdx).

#### Hash salt

The `DRUPAL_HASH_SALT` variable sets Drupal's `hash_salt`, which secures
one-time login links, password-reset URLs, and CSRF/form tokens.

When `DRUPAL_HASH_SALT` isn't set, **Vortex** derives a fallback salt by
hashing the database host name. That gets a new project running without any
setup, and it's fine for local and CI use, but nowhere else:

- A database host isn't a secret. It appears in logs, backups, `.env` files,
  and `drush status` output, so the derived value only resists blind
  guessing.
- The derived value changes if the database host ever changes (for example,
  failover or migration), silently invalidating outstanding one-time login
  and password-reset links.

:::warning

Set a unique, long, random `DRUPAL_HASH_SALT` for every hosted environment,
meaning dev, stage, and production, as a platform variable or secret. See
the [Acquia](/docs/hosting/acquia) and [Lagoon](/docs/hosting/lagoon)
hosting pages for each platform's steps.

:::

### Environment type detection

The _environment type_ names the context the Drupal site runs in. Settings
and deploy steps check it to decide how to behave in each environment.

The
[`drevops/environment-detector`](https://github.com/drevops/environment-detector)
package does the detection. It identifies the active _hosting platform_
(such as Acquia or Lagoon) or _CI service_ and resolves the environment
type from it. It then applies that platform's environment-specific Drupal
settings.

The detector recognizes 6 environment types:

| Type | Description | Lifespan |
|------|------------|----------|
| `local` | Your own machine or a local container stack; no hosting platform is active. | Persistent |
| `ci` | An automated CI runner (GitHub Actions, CircleCI). | Ephemeral, per job |
| `development` | A shared, long-lived hosting environment for ongoing integration work. Also the safe fallback. | Persistent |
| `preview` | A short-lived, throwaway per-branch or per-PR environment with its own URL. | Ephemeral |
| `stage` | A persistent pre-production environment that mirrors production; used for UAT and release sign-off. | Persistent |
| `production` | The live environment serving real users. | Persistent |

The detected type lands in `$settings['environment']`, where modules and
settings overrides read it to drive environment-specific behavior. The
detector also sets the `ENVIRONMENT_TYPE` environment variable to the same
value.

Most shipped module settings treat `preview` the same as `development`.
`settings.storybook.php` is the exception: it opens the Storybook render
route in `local`, `ci`, and `development` only.

#### Environment type constants

The detector exposes the supported environment types as constants on the
`DrevOps\EnvironmentDetector\Environment` class:

- `Environment::LOCAL` (`local`)
- `Environment::CI` (`ci`)
- `Environment::DEVELOPMENT` (`development`)
- `Environment::PREVIEW` (`preview`)
- `Environment::STAGE` (`stage`)
- `Environment::PRODUCTION` (`production`)

Use these constants in module settings files instead of hardcoding the
string values.

#### Detection mechanism

The detector resolves the environment type from the active platform. It
also applies that platform's Drupal settings, such as the reverse proxy,
trusted hosts, and file paths:

- When a hosting platform or CI service is detected, that platform sets
  the environment type.
- When the active platform can't name a specific type, the type falls back
  to `Environment::DEVELOPMENT`. That's the safest default: a misconfigured
  environment never gets local settings in production, or production
  settings locally.
- When no platform is detected, the type is `Environment::CI` if a generic
  CI signal is present, and `Environment::LOCAL` otherwise.

The detector owns every platform-specific setting. **Vortex** only sets 2
of the variables it reads: `.env` sets `ENVIRONMENT_PRODUCTION_BRANCH` to
`main` for Lagoon, and `docker-compose.yml` sets `LOCALDEV_URL` for the
local stack.

#### Overriding environment type

To force a specific environment type, set the `ENVIRONMENT_TYPE`
environment variable. When it's set before detection runs, the detector
uses its value as is.

Overriding the type helps in the following cases:

- Testing environment-specific behavior locally
- Working around gaps in the detection logic
- Forcing a known environment type for debugging

For example, to simulate the CI environment locally, add
`ENVIRONMENT_TYPE=ci` to your `.env.local` file and run `ahoy up`.

### Per-module overrides

This section loads every `settings.[module].php` file from the
`includes/modules` directory, in alphabetical order. Each file holds the
configuration overrides for 1 Drupal module, or for 1 concern such as
trusted hosts.

**Vortex** ships an override file for each contributed module it
configures, so you can maintain or remove each one independently. It also
ships 3 files that don't belong to a contributed module:

- `settings.automated_cron.php` sets the Automated Cron interval to `0` in
  the `local` and `ci` environments, so cron doesn't run on page requests
  there.
- `settings.system.php` sets the page cache lifetime and turns on CSS and
  JavaScript aggregation in `production`. In `local` and `ci`, it shows all
  errors and skips file permissions hardening. In `ci`, it stores outgoing
  email in the state system instead of sending it.
- `settings.trusted_hosts.php` adds each domain in the comma-separated
  `DRUPAL_TRUSTED_HOSTS` variable to the trusted host patterns.

➡️ See [Contributed modules](modules/contributed-modules.mdx) for what each
shipped override configures, module by module.

#### Creating custom module settings

To add settings for a new module, create a file following the naming
pattern:

```shell
web/sites/default/includes/modules/settings.[module_name].php
```

Each settings file follows these rules:

- Use the detector's constants (such as `Environment::LOCAL` and
  `Environment::PRODUCTION`) for conditional logic
- Use environment variables for configuration values
- Provide default values for when environment variables aren't set
- Be self-contained and removable without affecting other modules

The following override file for the Environment Indicator module follows
these rules:

import EnvironmentIndicatorModuleSettingsExample from
  '!!raw-loader!@site/../../web/sites/default/includes/modules/settings.environment_indicator.php';

#### Shield

[Shield](https://www.drupal.org/project/shield) restricts access to your
site with HTTP authentication. **Vortex** enforces Shield in non-production
hosted environments, and keeps local development and CI open without
authentication. Production is left alone, so Shield stays under UI control
there.

The following table shows where Shield is enabled:

| Environment | Shield enabled | Reason                                                            |
|-------------|----------------|-------------------------------------------------------------------|
| Local       | No             | No need for HTTP auth during local development                    |
| CI          | No             | Automated tests must access the site freely                       |
| Development | **Yes**        | Protects development environments from crawlers                   |
| Preview     | **Yes**        | Protects ephemeral preview environments                           |
| Stage       | **Yes**        | Protects staging environments from public access                  |
| Production  | Not enforced   | Left to the site configuration - enable or disable through the UI |

The following environment variables configure Shield:

| Variable                             | Default | Purpose                                             |
|--------------------------------------|---------|-----------------------------------------------------|
| `DRUPAL_SHIELD_USER`                 | None    | HTTP authentication username                        |
| `DRUPAL_SHIELD_PASS`                 | None    | HTTP authentication password                        |
| `DRUPAL_SHIELD_PRINT`                | None    | Message shown in the authentication popup (module default when unset) |
| `DRUPAL_SHIELD_ALLOW_ACME_CHALLENGE` | None    | Set to `1` to keep the `/.well-known/acme-challenge/*` path open for Let's Encrypt certificate generation |

To turn Shield off in an environment where it would otherwise be on, set
`DRUPAL_SHIELD_DISABLED` to `1`. That helps for temporary access during
debugging, or in an environment that needs no protection.

#### Reroute Email

[Reroute Email](https://www.drupal.org/project/reroute_email) intercepts
outgoing email and sends it to a configurable address instead of the
intended recipients. Real users don't get email from non-production
environments, and you can still test email features there.

The following table shows where rerouting is on:

| Environment | Rerouting enabled | Reason                                                        |
|-------------|-------------------|---------------------------------------------------------------|
| Local       | No                | Emails are typically not sent in local development            |
| CI          | No                | Automated tests don't send real emails                        |
| Development | **Yes**           | Prevents accidental delivery to real users                    |
| Preview     | **Yes**           | Prevents accidental delivery to real users                    |
| Stage       | **Yes**           | Stage runs a copy of production content, so any address that survives database sanitization is real |
| Production  | No                | Production emails must reach actual recipients                |

Rerouting is the default, so it's also on in any custom environment type
outside the 6 standard ones.

The settings file excludes the module from the exported configuration, so
the [development modules](provision.mdx#development-modules) deploy step is
the only place that installs it.

The following environment variables configure the rerouting:

| Variable                       | Default                              | Purpose                                              |
|--------------------------------|--------------------------------------|------------------------------------------------------|
| `DRUPAL_REROUTE_EMAIL_ADDRESS` | `webmaster@your-site-domain.example` | Address to receive all rerouted emails               |
| `DRUPAL_REROUTE_EMAIL_ALLOWED` | `*@your-site-domain.example`         | Pattern for addresses allowed to bypass rerouting    |

To turn rerouting off in an environment where it would otherwise be on, set
`DRUPAL_REROUTE_EMAIL_DISABLED` to `1`. To send real mail from `stage`
during UAT, set this variable there.

import RerouteEmailModuleSettingsExample from

### Local overrides

`settings.php` ends by loading `settings.local.php` when it exists, so you
can override settings on your machine without touching the shared
configuration. To turn the local overrides on, follow these steps in
`web/sites/default`:

1. Copy `example.settings.local.php` to `settings.local.php`.
2. Copy `example.services.local.yml` to `services.local.yml`.

Git ignores both copies, and `settings.local.php` is the file that loads
`services.local.yml`. Drupal builds a new service container when that list
of service files changes, so no cache rebuild is needed. Confirm that the
HTML source of the next page you load carries Twig debug comments, such as
`<!-- THEME DEBUG -->`.

The example files change the following settings:

- Every error message shows, with backtrace information.
- CSS and JavaScript aggregation is off.
- The render, page, and dynamic page caches are bypassed.
- Twig debugging is on.
- Responses carry cacheability debug headers.
- `rebuild.php` is accessible.
- File permissions hardening is skipped.

To check how the site behaves without the local overrides, set the
`DRUPAL_SETTINGS_LOCAL_SKIP` environment variable to `1`. The site then
skips `settings.local.php` even when it exists.

## Guidelines

Follow these guidelines when working with settings:

- **Don't modify `settings.php` directly.<br/>** Use environment variables
  for [general](#general) settings or
  [per-module override files](#per-module-overrides) for any custom or
  environment-aware configuration.

- **Keep all overrides isolated by module.**<br/>
  Each file holds the logic for a single module only. When the module goes,
  its override file goes with it, and no unrelated setting changes.

- **Use environment variables for configuration that changes by
  environment.**<br/>
  Prefix all such variables with `DRUPAL_` (for example,
  `DRUPAL_MY_SETTING`) to distinguish them from other environment
  variables.<br/>
  Always define a default hardcoded value for each environment variable.

- **Guard a variable by what it holds.**<br/>
  A _boolean flag_ (a variable whose only job is to switch behavior on) is
  read with `getenv('DRUPAL_MY_FLAG') === '1'`. Every other value, including
  an unset variable, an empty string, `0`, `true`, and `yes`, leaves the
  behavior off.<br/>
  A _value carrier_ (a variable whose value is used) is read with
  `!empty(getenv('DRUPAL_MY_VALUE'))`. Assign it to a variable first when
  the value is needed after the guard.<br/>
  Compare with `===` and `!==`, never with `==`.

:::warning Flags accept only `1`

Each of the following flags acts only when it's exactly `1`. Any other
value, such as `true`, `yes`, or `on`, counts as unset, so the flag has no
effect. Set each one to exactly `1`, wherever you set it:

- `DRUPAL_CLAMAV_ENABLED`
- `DRUPAL_REDIS_ENABLED`
- `DRUPAL_REROUTE_EMAIL_DISABLED`
- `DRUPAL_SHIELD_DISABLED`
- `DRUPAL_SHIELD_ALLOW_ACME_CHALLENGE`
- `DRUPAL_SETTINGS_LOCAL_SKIP`
- `VORTEX_REDIS_EXTENSION_LOADED`

:::

- **Gate on the presence of a contributed module only when the file needs
  it.**<br/>
  `file_exists($contrib_path . '/my_module')` belongs in an override file
  that loads a file from the module directory or registers its paths. An
  override file that only writes `$config` or `$settings` needs no such
  guard, because Drupal ignores overrides for a module that isn't installed.

- **Use conditions based on _environment type_ within per-module override
  files.**<br/>
  This keeps environment-specific configuration out of the main
  `settings.php` file.<br/>
  Use the `$settings['environment']` variable to check the current
  _environment type_.

## Testing settings with unit tests

**Vortex** includes a [set of unit
tests](https://github.com/drevops/vortex/blob/main/tests/phpunit/Drupal) to
verify that settings are applied correctly for each detected environment
type.

They're meant to be maintained in your project, alongside your settings.
They check that environment-driven configuration behaves as expected, for
each environment type and for the environment variables that switch
behavior on or off. The 3 test classes cover the following:

- `DatabaseSettingsTest`: the database connection settings
- `EnvironmentSettingsTest`: the settings in every environment type
- `SwitchableSettingsTest`: the settings that environment variables switch
  on or off

To run only the settings tests, run the following command inside the CLI
container (open a shell there with `ahoy cli`):

```shell
vendor/bin/phpunit --group=drupal_settings
```

Confirm that PHPUnit reports `OK` at the end of the run.

They're part of the `unit` test suite, so `ahoy test-unit` runs them too.
Remove these tests if you don't want to maintain them.
