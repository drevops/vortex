# Settings

Drupal reads its site configuration from `settings.php` and `services.yml`:
database connections, file paths, and everything that should behave
differently from one environment to the next. **Vortex** ships its own
versions of
[`settings.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/settings.php)
and
[`services.yml`](https://github.com/drevops/vortex/blob/main/web/sites/default/services.yml),
built so the same files work in every environment.

The shipped `settings.php` works out where the site is running (locally, in
CI, or in a hosting environment) and applies settings to match. Each
module's overrides live in a small file of their own, so you can see at a
glance what a module does differently in each environment.

Drupal Scaffold's own
[`default.settings.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/default.settings.php)
and
[`default.services.yml`](https://github.com/drevops/vortex/blob/main/web/sites/default/default.services.yml)
are there too, if you'd rather start from those.

## Approach

A site rarely runs the same way everywhere. Local, CI, development, staging,
and production environments each need their own adjustments: a module on
here and off there, different performance settings, different APIs, or
different services to talk to.

Drupal has no standard way to manage these differences. Its configuration
system isn't built for conditional logic, such as applying different
settings per runtime environment or reading values from environment
variables.

Modules like `config_split` let you maintain separate configuration sets per
environment, but they're limited. They don't support environment-based
conditions inside the configuration YAML files, and they can't read
environment variables directly. They also don't help when you need dynamic
logic (for example, setting values based on external service URLs).

**Vortex** still ships `config_split`, and it's the right tool when
declarative configuration is enough, such as enabling a module in staging
but not in production. It falls short when settings need conditional logic
or values from the environment. It also gives you no way to test
automatically which settings apply in a given environment.

So **Vortex** splits the job in 2:

- The _environment type_ is [detected](#environment-type-detection) from the
  environment the site runs in. This step applies the hosting platform's own
  settings, but no module configuration.
- Configuration overrides live in [per-module override
  files](#per-module-overrides), with conditions based on the detected
  _environment type_.

The split pays off in 4 ways:

- It keeps environment detection separate from configuration logic.
- It shows in one place how a module behaves in a specific environment.
- When a module is no longer needed, you can delete its override file
  without touching `settings.php`.
- It stops environment-specific settings from leaking into unrelated parts
  of the configuration.

### In practice

Say the business asks to let an external stakeholder review the `stage`
environment, which [Shield](modules/contributed-modules.mdx#shield) protects
with HTTP authentication. The shipped `settings.shield.php` override already
reads the `DRUPAL_SHIELD_DISABLED` variable, so you can make the change
without editing code:

1. Set `DRUPAL_SHIELD_DISABLED=1` on the `stage` environment in your hosting
   provider's environment variables and apply it (Acquia applies it
   automatically; Lagoon requires a deployment).
2. When the review is over, remove the variable to restore the default
   behavior.

You don't commit anything, and no other environment changes, because the
override file defines the behavior once and each environment opts in through
its own variables.

## Settings file structure

The
[`settings.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/settings.php)
file is organized into the following sections:

- [Database](#database)
- [General](#general)
- [Environment type detection](#environment-type-detection)
- [Per-module overrides](#per-module-overrides)
- [Local overrides](#local-overrides)

The sections run in a fixed order, loading additional files from the
`includes/` directories along the way:

```text
🚀 Drupal bootstrap
   │
   ▼
📄 web/sites/default/settings.php
   │
① 🛢️ Database
   │  Connection credentials from environment variables.
   ▼
② ⚙️ General
   │  File paths, hash salt, timezone, maintenance theme.
   ▼
③ 🔍 Environment type detection
   │  Loads web/sites/default/includes/providers/settings.<provider>.php
   │  (acquia, lagoon, circleci, gha, container) and stores the detected
   │  type in $settings['environment']. Provider files also apply their
   │  platform settings; no module overrides are applied here.
   ▼
④ 🧩 Per-module overrides
   │  Loads every web/sites/default/includes/modules/settings.<module>.php,
   │  each applying its overrides based on the detected environment type.
   ▼
⑤ 🏠 Local overrides
   │  Loads web/sites/default/settings.local.php and services.local.yml
   │  when present (local development only).
   ▼
🏁 Fully configured site
```

Projects with the migration feature load 1 more file between the per-module
overrides and the local overrides: `settings.migration.php`, which defines
the [migration database connection](migrations.mdx#drupal-settings).

### Database

The database connection comes from environment variables, with a default
for each value.

Hosting providers and container images name these variables differently, so
each setting accepts several names and uses the first one that's set:

| Variable             | Alternative Variables                   | Default              | Purpose           |
|----------------------|-----------------------------------------|----------------------|-------------------|
| `DATABASE_NAME`      | `DATABASE_DATABASE`, `MARIADB_DATABASE` | `drupal`             | Database name     |
| `DATABASE_USERNAME`  | `MARIADB_USERNAME`                      | `drupal`             | Database username |
| `DATABASE_PASSWORD`  | `MARIADB_PASSWORD`                      | `drupal`             | Database password |
| `DATABASE_HOST`      | `MARIADB_HOST`                          | `localhost`          | Database host     |
| `DATABASE_PORT`      | `MARIADB_PORT`                          | `3306`               | Database port     |
| `DATABASE_CHARSET`   | `MARIADB_CHARSET`, `MYSQL_CHARSET`      | `utf8mb4`            | Character set     |
| `DATABASE_COLLATION` | `MARIADB_COLLATION`, `MYSQL_COLLATION`  | `utf8mb4_general_ci` | Collation         |

The table prefix is always empty, and the driver is always `mysql`.

You rarely need to set these yourself: the local stack sets them in
`docker-compose.yml`, and the alternative names cover providers and images
that use their own. Set them only for a custom database setup, or for a
hosting provider that needs specific values.

### General

This section sets what every environment needs: file paths, the
configuration sync directory, the hash salt, the timezone, and the
maintenance theme. It doesn't look at the environment type. The provider
files in the [next section](#environment-type-detection) adjust a few of
these values for their platform, such as the temporary directory on Acquia.

It also sets a few values that no variable controls. It loads `services.yml`
and trusts the `^localhost$` host pattern. It skips the `node_modules` and
`bower_components` directories in file scans and creates no `.htaccess`
files in writable directories. It updates entities in batches of 50, and
starts an empty `config_exclude_modules` list for the per-module files to
fill.

These environment variables customize it:

| Variable                    | Alternative Variables | Default                        | Purpose                                  |
|-----------------------------|-----------------------|--------------------------------|------------------------------------------|
| `DRUPAL_CONFIG_PATH`        |                       | `../config/default`            | Location of configuration sync directory |
| `DRUPAL_PUBLIC_FILES`       |                       | `sites/default/files`          | Public files directory path              |
| `DRUPAL_PRIVATE_FILES`      |                       | `sites/default/files/private`  | Private files directory path             |
| `DRUPAL_TEMPORARY_FILES`    | `TMP`                 | `/tmp`                         | Temporary files directory path           |
| `DRUPAL_HASH_SALT`          |                       | _Generated from database host_ | Cryptographic salt for security          |
| `DRUPAL_TIMEZONE`           | `TZ`                  | `UTC`                          | Runtime timezone                         |
| `DRUPAL_MAINTENANCE_THEME`  | `DRUPAL_THEME`        | `claro`                        | Theme used during maintenance mode       |

The page cache lifetime (`DRUPAL_CACHE_PAGE_MAX_AGE`, default `900` seconds)
is set in the `settings.system.php`
[per-module override](#per-module-overrides), not in this section. The full
generated list of `DRUPAL_*` variables is in the
[Variables reference](variables.mdx).

#### Hash salt

The `DRUPAL_HASH_SALT` variable sets Drupal's `hash_salt`, which secures
one-time login links, password-reset URLs, and CSRF/form tokens.

When `DRUPAL_HASH_SALT` isn't set, **Vortex** derives a fallback salt by
hashing the database host name. That gets a new project running without any
setup, and it's fine for local and CI use, but nowhere else:

- A database host isn't a secret. It appears in logs, backups, `.env` files,
  and `drush status` output, so the derived value only resists blind
  guessing.
- The derived value changes if the database host ever changes (for example,
  failover or migration), silently invalidating outstanding one-time login
  and password-reset links.

:::warning

Set a unique, long, random `DRUPAL_HASH_SALT` for every hosted environment
(dev, stage, and production) as a platform variable or secret. See the
[Acquia](/docs/hosting/acquia) and [Lagoon](/docs/hosting/lagoon) hosting
pages for platform-specific guidance.

:::

### Environment type detection

The _environment type_ names the context the Drupal site runs in, such as
local, CI, development, staging, or production. Settings and scripts check
it to decide how to behave in each one.

**Vortex** detects the type automatically from variables that known _hosting
provider_ and CI platforms set. The provider files that do the detecting
also apply their platform's own settings, but they leave module
configuration to the per-module override files.

The detected type lands in `$settings['environment']`, where modules,
settings overrides, and shell scripts read it to drive environment-specific
behavior.

#### Environment type constants

**Vortex** defines a constant for each supported environment type, with the
string value it stands for:

- `ENVIRONMENT_LOCAL` (`local`)
- `ENVIRONMENT_CI` (`ci`)
- `ENVIRONMENT_DEV` (`dev`)
- `ENVIRONMENT_STAGE` (`stage`)
- `ENVIRONMENT_PROD` (`prod`)

Settings files compare `$settings['environment']` against these constants,
and shell scripts compare it against the string values.

#### Detection mechanism

Detection relies on variables that hosting and CI platforms set. The logic
lives in the `includes/providers` directory, 1 file per provider:
`settings.acquia.php`, `settings.lagoon.php`, `settings.circleci.php`,
`settings.gha.php`, and `settings.container.php`. `settings.php` loads every
file in that directory, and each file acts only when it recognizes its
platform.

To add support for a custom platform, create a `settings.[provider].php`
file in that directory with the relevant detection logic.

The type starts as `ENVIRONMENT_LOCAL`, and the provider files change it:

- A hosting provider sets `ENVIRONMENT_DEV`, and its own conditions raise
  that to `ENVIRONMENT_STAGE` or `ENVIRONMENT_PROD`. On Acquia, the `prod`
  environment becomes `ENVIRONMENT_PROD`, and `stage` or `test` becomes
  `ENVIRONMENT_STAGE`. On Lagoon, the `production` environment type or the
  branch in `VORTEX_LAGOON_PRODUCTION_BRANCH` becomes `ENVIRONMENT_PROD`.
  Otherwise, the `main`, `master`, `release/*`, and `hotfix/*` branches
  become `ENVIRONMENT_STAGE`.
- A CI provider (CircleCI or GitHub Actions) sets `ENVIRONMENT_CI` when the
  `CI` variable is set.
- `settings.container.php` sets no type. It adds the local container URLs
  from `LOCALDEV_URL` to the trusted host patterns.
- With no provider detected, the type stays `ENVIRONMENT_LOCAL`.

Besides the type, the provider files apply only their platform's own
settings. Examples are Acquia's settings include and temporary directory,
the reverse proxy and cache prefix on Lagoon, and trusted host patterns.
They don't change module configuration. Per-module override files in
`includes/modules` handle that separately, so the setup stays modular and
independent of the hosting platforms.

#### Overriding environment type

You can override the detected environment type by setting the
`ENVIRONMENT_TYPE` environment variable. Any non-empty value replaces the
detected type, including names outside the 5 constants.

This is useful when:

- Testing environment-specific behavior locally.
- Working around gaps in the detection logic.
- Forcing a known environment type for debugging.

For example, add `ENVIRONMENT_TYPE=ci` to your `.env.local` file and run
`ahoy up` to simulate the CI environment locally.

### Per-module overrides

This section loads every `settings.[module].php` file from the
`includes/modules` directory, in alphabetical order. Each file holds the
configuration overrides for 1 Drupal module.

**Vortex** ships pre-configured settings for several core and contributed
modules, each in its own file, so you can maintain or remove each one
independently.

➡️ See [Contributed modules](modules/contributed-modules.mdx) for what each
shipped override configures, module by module.

#### Creating custom module settings

To add settings for a new module, create a file following the naming
pattern:

```shell
web/sites/default/includes/modules/settings.[module_name].php
```

Each settings file should:

- Use environment type constants (such as `ENVIRONMENT_LOCAL` and
  `ENVIRONMENT_PROD`) for conditional logic
- Use environment variables for configuration values
- Provide default values for when environment variables aren't set
- Be self-contained and removable without affecting other modules

### Local overrides

`settings.php` ends by loading `settings.local.php` when it exists, so you
can override settings on your machine without touching the shared
configuration. To use it, copy `example.settings.local.php` and
`example.services.local.yml` to `settings.local.php` and
`services.local.yml`. Git ignores both copies, and `settings.local.php` is
the file that loads `services.local.yml`.

The examples show every error message, turn off CSS and JavaScript
aggregation, bypass the render, page, and dynamic page caches, and switch on
Twig debugging.

Set the `DRUPAL_SETTINGS_LOCAL_SKIP` environment variable to `1` to skip the
local overrides even when `settings.local.php` exists, for example to check
how the site behaves without them.

## Guidelines

Follow these guidelines when working with settings:

- **Don't modify `settings.php` directly.<br/>** Use environment variables
  for [general](#general) settings or
  [per-module override files](#per-module-overrides) for any custom or
  environment-aware configuration.

- **Keep all overrides isolated by module.**<br/>
  Each file holds the logic for a single module only. When the module goes,
  its override file goes with it, and no unrelated setting changes.

- **Use environment variables for configuration that changes by
  environment.**<br/>
  Prefix all such variables with `DRUPAL_` (for example,
  `DRUPAL_MY_SETTING`) to distinguish them from other environment
  variables.<br/>
  Always define a default hardcoded value for each environment variable.

- **Guard a variable by what it holds.**<br/>
  A _boolean flag_ (a variable whose only job is to switch behavior on) is
  read with `getenv('DRUPAL_MY_FLAG') === '1'`. Every other value, including
  an unset variable, an empty string, `0`, `true`, and `yes`, leaves the
  behavior off.<br/>
  A _value carrier_ (a variable whose value is used) is read with
  `!empty(getenv('DRUPAL_MY_VALUE'))`. Assign it to a variable first when
  the value is needed after the guard.<br/>
  Compare with `===` and `!==`, never with `==`.

:::warning Flags accept only `1`

An environment that sets a shipped flag to `true`, `yes`, `on`, or any other
non-empty value gets the behavior turned off. Set every flag below to
exactly `1`, wherever you set it: `DRUPAL_CLAMAV_ENABLED`,
`DRUPAL_REDIS_ENABLED`, `DRUPAL_REROUTE_EMAIL_DISABLED`,
`DRUPAL_SHIELD_DISABLED`, `DRUPAL_SHIELD_ALLOW_ACME_CHALLENGE`,
`DRUPAL_TMP_PATH_IS_SHARED`, `DRUPAL_SETTINGS_LOCAL_SKIP`, and
`VORTEX_REDIS_EXTENSION_LOADED`.

:::

- **Gate on the presence of a contributed module only when the file needs
  it.**<br/>
  `file_exists($contrib_path . '/my_module')` belongs in an override file
  that loads a file from the module directory or registers its paths. An
  override file that only writes `$config` or `$settings` needs no such
  guard, because Drupal ignores overrides for a module that isn't installed.

- **Use conditions based on _environment type_ within per-module override
  files.**<br/>
  This keeps environment-specific configuration out of the main
  `settings.php` file.<br/>
  Use the `$settings['environment']` variable to check the current
  _environment type_.

## Testing settings with unit tests

**Vortex** includes a [set of unit
tests](https://github.com/drevops/vortex/blob/main/tests/phpunit/Drupal) to
verify that settings are applied correctly for each detected environment
type.

They're meant to be maintained in your project, alongside your settings.
They check that environment-driven configuration behaves as expected, for
each environment type and for the environment variables that switch
behavior on or off. The 3 test classes cover the database settings, the
settings in every environment type, and the switchable settings.

To run unit tests for settings:

```shell
vendor/bin/phpunit --group=drupal_settings
```

They're part of the `unit` test suite, so `ahoy test-unit` runs them too.
Remove these tests if you don't want to maintain them.
