# Settings

Drupal reads its site configuration from `settings.php` and `services.yml`:
database connections, file paths and every setting that differs between
environments. **Vortex** ships its own
versions of
[`settings.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/settings.php)
and
[`services.yml`](https://github.com/drevops/vortex/blob/main/web/sites/default/services.yml),
and the same files work in every environment.

The shipped `settings.php` detects where the site runs, such as locally, in
CI or on a hosting platform, and applies settings to match. Each module's
overrides live in a small file of their own, so 1 file shows what a module
does differently in each environment.

Drupal Scaffold's own
[`default.settings.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/default.settings.php)
and
[`default.services.yml`](https://github.com/drevops/vortex/blob/main/web/sites/default/default.services.yml)
are there too, if you'd rather start from those.

This page is for developers who need a setting to differ between
environments, and for the lead or DevOps engineer who brings a project onto
a hosting platform. It explains how `settings.php` detects the environment
and which variables it reads. It also shows how to add your own per-module
overrides and test them. For the full list of variables, see
[Variables](variables.mdx).

## Approach

A site rarely runs the same way everywhere. Local, CI, development, staging
and production environments each need their own adjustments: a module on
in 1 environment and off in another, or different performance settings,
APIs and connected services.

Drupal has no standard way to manage these differences. Its configuration
system has no conditional logic, so it can't apply settings per runtime
environment or read values from environment variables.

Modules such as `config_split` keep a separate configuration set per
environment, but they have the following limits:

- Their configuration YAML files can't hold conditions based on the
  environment.
- They can't read environment variables directly.
- They can't apply dynamic logic, such as setting values based on external
  service URLs.

**Vortex** still ships `config_split`, and it's the right tool when
declarative configuration is enough, such as enabling a module in staging
but not in production. It falls short when settings need conditional logic
or values from the environment. It also can't test automatically which
settings apply in a given environment.

So **Vortex** splits the job in 2:

- `settings.php` [detects](#environment-type-detection) the
  _environment type_ from the environment the site runs in. This step
  applies only the hosting platform's own settings.
- [Per-module override files](#per-module-overrides) hold the configuration
  overrides, with conditions based on the detected _environment type_.

The split pays off in 4 ways:

- Environment detection stays separate from configuration logic.
- 1 file shows how a module behaves in each environment.
- When a module goes, you delete its override file and leave `settings.php`
  alone.
- Environment-specific settings stay out of unrelated parts of the
  configuration.

### In practice

Say the business asks you to let an external stakeholder review the `stage`
environment, which [Shield](modules/contributed-modules.mdx#shield) protects
with HTTP authentication. The shipped `settings.shield.php`
override reads the `DRUPAL_SHIELD_DISABLED` variable, so you make the change
in your hosting provider's settings:

1. In your hosting provider's environment variables, set
   `DRUPAL_SHIELD_DISABLED=1` on the `stage` environment.
2. Apply the variable. Acquia restarts the environment on its own, and
   Lagoon needs a redeployment. The `stage` site then opens without the
   HTTP authentication prompt.

When the review is over, remove the variable and apply the change the same
way. Confirm that the `stage` site asks for the Shield credentials again.

You commit nothing, and no other environment changes, because the override
file defines the behavior once and each environment opts in through its own
variables.

## Settings file structure

The
[`settings.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/settings.php)
file has the following sections:

- [Database](#database)
- [General](#general)
- [Environment type detection](#environment-type-detection)
- [Per-module overrides](#per-module-overrides)
- [Local overrides](#local-overrides)

The sections run in a fixed order and load more files from the `includes/`
directories along the way:

```text
🚀 Drupal bootstrap
   │
   ▼
📄 web/sites/default/settings.php
   │
① 🛢️ Database
   │  Connection credentials from environment variables.
   ▼
② ⚙️ General
   │  File paths, hash salt, timezone, maintenance theme.
   ▼
③ 🔍 Environment type detection
   │  Loads web/sites/default/includes/providers/settings.<provider>.php
   │  (acquia, lagoon, circleci, gha, container) and stores the detected
   │  type in $settings['environment']. Provider files also apply their
   │  platform settings; no module overrides are applied here.
   ▼
④ 🧩 Per-module overrides
   │  Loads every web/sites/default/includes/modules/settings.<module>.php,
   │  each applying its overrides based on the detected environment type.
   ▼
⑤ 🏠 Local overrides
   │  Loads web/sites/default/settings.local.php and services.local.yml
   │  when present (local development only).
   ▼
🏁 Fully configured site
```

Projects with the migration feature load 1 more file between the per-module
overrides and the local overrides: `settings.migration.php`, which defines
the [migration database connection](migrations.mdx#drupal-settings).

### Database

The database connection comes from environment variables, with a default
for each value. Hosting providers and container images name these variables
differently, so each setting accepts several names and uses the first one
that's set:

| Variable             | Alternative variables                   | Default              | Purpose           |
|----------------------|-----------------------------------------|----------------------|-------------------|
| `DATABASE_NAME`      | `DATABASE_DATABASE`, `MARIADB_DATABASE` | `drupal`             | Database name     |
| `DATABASE_USERNAME`  | `MARIADB_USERNAME`                      | `drupal`             | Database username |
| `DATABASE_PASSWORD`  | `MARIADB_PASSWORD`                      | `drupal`             | Database password |
| `DATABASE_HOST`      | `MARIADB_HOST`                          | `localhost`          | Database host     |
| `DATABASE_PORT`      | `MARIADB_PORT`                          | `3306`               | Database port     |
| `DATABASE_CHARSET`   | `MARIADB_CHARSET`, `MYSQL_CHARSET`      | `utf8mb4`            | Character set     |
| `DATABASE_COLLATION` | `MARIADB_COLLATION`, `MYSQL_COLLATION`  | `utf8mb4_general_ci` | Collation         |

The table prefix is always empty, and the driver is always `mysql`.

The local stack sets these variables in `docker-compose.yml`. The
alternative names cover providers and images that use names of their own.
For a custom database setup, or a hosting provider that needs specific
values, set the variables in that environment.

### General

This section sets the values every environment needs, and it doesn't depend
on the environment type. The provider files in the
[next section](#environment-type-detection) adjust a few of these values
for their platform, such as the temporary directory on Acquia.

The following environment variables customize this section:

| Variable                    | Alternative variables | Default                           | Purpose                                  |
|-----------------------------|-----------------------|-----------------------------------|------------------------------------------|
| `DRUPAL_CONFIG_PATH`        | None                  | `../config/default`               | Location of configuration sync directory |
| `DRUPAL_PUBLIC_FILES`       | None                  | `sites/default/files`             | Public files directory path              |
| `DRUPAL_PRIVATE_FILES`      | None                  | `sites/default/files/private`     | Private files directory path             |
| `DRUPAL_TEMPORARY_FILES`    | `TMP`                 | `/tmp`                            | Temporary files directory path           |
| `DRUPAL_HASH_SALT`          | None                  | SHA-256 hash of the database host | Cryptographic salt for security          |
| `DRUPAL_TIMEZONE`           | `TZ`                  | `UTC`                             | Runtime timezone                         |
| `DRUPAL_MAINTENANCE_THEME`  | `DRUPAL_THEME`        | `claro`                           | Theme used during maintenance mode       |

This section also does the following, and no variable changes it:

- Loads `services.yml` as a service container definition
- Trusts the `^localhost$` host pattern
- Skips the `node_modules` and `bower_components` directories in file
  scans
- Sets `auto_create_htaccess` to `FALSE`, so Drupal creates no `.htaccess`
  files in writable directories. `settings.acquia.php` turns it back on for
  Acquia.
- Updates entities in batches of 50
- Starts an empty `config_exclude_modules` list for the per-module files to
  fill

The `settings.system.php` [per-module override](#per-module-overrides) sets
the page cache lifetime through its `DRUPAL_CACHE_PAGE_MAX_AGE` variable,
which defaults to `900` seconds. The [Variables reference](variables.mdx)
lists every `DRUPAL_*` variable.

#### Hash salt

The `DRUPAL_HASH_SALT` variable sets Drupal's `hash_salt`, which secures
one-time login links, password-reset URLs and CSRF and form tokens.

When `DRUPAL_HASH_SALT` isn't set, **Vortex** derives a fallback salt by
hashing the database host name. A new project then runs without any setup.
The fallback suits local and CI use only, for 2 reasons:

- A database host isn't a secret. It appears in logs, backups, `.env` files
  and `drush status` output, so the derived value only resists blind
  guessing.
- The derived value changes when the database host changes, for example
  after a failover or a migration, silently invalidating outstanding
  one-time login and password-reset links.

:::warning

Set a unique, long, random `DRUPAL_HASH_SALT` for every hosted environment
(dev, stage and production) as a platform variable or secret.
`settings.lagoon.php` sets no salt of its own. On Acquia,
`settings.acquia.php` loads the platform's settings file after this
section, so a salt set in that file takes precedence. See
[Set up hosting](../installation.mdx#6-set-up-hosting) for each platform's
steps.

:::

### Environment type detection

The _environment type_ names the context the Drupal site runs in: local,
CI, development, staging or production. Settings and scripts check it to
decide how to behave.

**Vortex** detects the type from variables that known _hosting provider_
and CI platforms set. The provider files that detect the type also apply
their platform's own settings, but they leave module configuration to the
per-module override files.

The detected type goes into `$settings['environment']`, where modules,
settings overrides and shell scripts read it to drive environment-specific
behavior.

#### Environment type constants

**Vortex** defines a constant for each supported environment type, listed
here with its string value:

- `ENVIRONMENT_LOCAL` (`local`)
- `ENVIRONMENT_CI` (`ci`)
- `ENVIRONMENT_DEV` (`dev`)
- `ENVIRONMENT_STAGE` (`stage`)
- `ENVIRONMENT_PROD` (`prod`)

Settings files compare `$settings['environment']` against these constants.
Shell scripts compare it against the string values.

#### Detection mechanism

The detection logic lives in the `includes/providers` directory, 1 file per
provider. Each file acts only when its platform's variable is present:

- `settings.acquia.php`: `AH_SITE_ENVIRONMENT`
- `settings.circleci.php` and `settings.gha.php`: `CI`
- `settings.container.php`: `LOCALDEV_URL`
- `settings.lagoon.php`: `LAGOON_KUBERNETES`

`settings.php` loads every `settings.*.php` file in that directory, in
alphabetical order. To support a custom platform, create a
`settings.[provider].php` file in that directory with its detection logic.

The type starts as `ENVIRONMENT_LOCAL`, and the provider files change it:

- A hosting provider sets `ENVIRONMENT_DEV`, and its own conditions raise
  the type to `ENVIRONMENT_STAGE` or `ENVIRONMENT_PROD`:
  - On Acquia, an `AH_SITE_ENVIRONMENT` of `prod` becomes
    `ENVIRONMENT_PROD`. A value of `stage` or `test` becomes
    `ENVIRONMENT_STAGE`.
  - On Lagoon, a `LAGOON_ENVIRONMENT_TYPE` of `production` becomes
    `ENVIRONMENT_PROD`. So does a `LAGOON_GIT_BRANCH` that exactly matches
    `VORTEX_LAGOON_PRODUCTION_BRANCH`, which `.env` sets to `main`. When
    that variable is empty, the script skips this match. Any other `main`,
    `master`, `release/*` or `hotfix/*` branch becomes `ENVIRONMENT_STAGE`.
- `settings.circleci.php` and `settings.gha.php` both check the generic `CI`
  variable, so a provider-specific variable such as `CIRCLECI` has no
  effect. Any non-empty value other than `0` sets `ENVIRONMENT_CI`.
  `docker-compose.yml` passes `CI` from the runner into the containers.
- `settings.container.php` sets no type. It adds the local container URLs
  from `LOCALDEV_URL` to the trusted host patterns.
- With no provider detected, the type stays `ENVIRONMENT_LOCAL`.

Besides the type, the provider files apply only their platform's own
settings, such as the following:

- Acquia's settings include and temporary directory
- The reverse proxy and cache prefix on Lagoon
- Trusted host patterns

The per-module override files in `includes/modules` handle module
configuration, so the setup stays modular and independent of the hosting
platforms.

#### Override the environment type

To force a specific environment type, set the `ENVIRONMENT_TYPE`
environment variable. Any value other than an empty string or `0`
replaces the detected type, including names outside the 5 constants.

Overriding the type helps in the following cases:

- Testing environment-specific behavior locally
- Working around gaps in the detection logic
- Forcing a known environment type for debugging

For example, to simulate the CI environment locally, add
`ENVIRONMENT_TYPE=ci` to your `.env.local` file and run `ahoy up`.

### Per-module overrides

This section loads every `settings.[module].php` file from the
`includes/modules` directory, in alphabetical order. Each file holds the
configuration overrides for 1 Drupal module, or for 1 concern such as
trusted hosts.

**Vortex** ships an override file for each contributed module it
configures, so you can maintain or remove each file on its own. It also
ships 3 files that belong to no contributed module:

- `settings.automated_cron.php` sets the Automated Cron interval to `0` in
  the `local` and `ci` environments, so cron doesn't run on page requests
  there.
- `settings.system.php` sets the page cache lifetime and turns on CSS and
  JavaScript aggregation in `prod`. In `local` and `ci`, it shows all
  errors and skips file permissions hardening. In `ci`, it stores outgoing
  email in the state system instead of sending it.
- `settings.trusted_hosts.php` adds each domain in the comma-separated
  `DRUPAL_TRUSTED_HOSTS` variable to the trusted host patterns.

➡️ See [Contributed modules](modules/contributed-modules.mdx) for what each
shipped override configures, module by module.

#### Create custom module settings

To add settings for a new module, create a file that follows this naming
pattern:

```shell
web/sites/default/includes/modules/settings.[module_name].php
```

Each settings file follows these rules:

- Use environment type constants, such as `ENVIRONMENT_LOCAL` and
  `ENVIRONMENT_PROD`, for conditional logic.
- Use environment variables for configuration values.
- Provide a default value for each environment variable that isn't set.
- Keep the file self-contained, so you can remove it without affecting
  other modules.

The following override file for the Environment Indicator module follows
these rules:

import EnvironmentIndicatorModuleSettingsExample from
  '!!raw-loader!@site/../../web/sites/default/includes/modules/settings.environment_indicator.php';

### Local overrides

`settings.php` ends by loading `settings.local.php` when it exists, so you
can override settings on your machine and leave the shared configuration
alone. To turn the local overrides on, follow these steps in
`web/sites/default`:

1. Copy `example.settings.local.php` to `settings.local.php`.
2. Copy `example.services.local.yml` to `services.local.yml`.

Git ignores both copies. `settings.local.php` loads `services.local.yml`.
Drupal builds a new service container when its list of service files
changes, so no cache rebuild is needed. Confirm that the HTML source of the
next page you load carries Twig debug comments, such as
`<!-- THEME DEBUG -->`.

The example files change the following settings:

- Every error message shows, with backtrace information.
- CSS and JavaScript aggregation is off.
- The render, page and dynamic page caches are bypassed.
- Twig debugging is on.
- Responses carry cacheability debug headers.
- `rebuild.php` is accessible.
- File permissions hardening is skipped.

To check how the site behaves without the local overrides, set the
`DRUPAL_SETTINGS_LOCAL_SKIP` environment variable to `1`. The site then
skips `settings.local.php` even when it exists.

import LocalSettingsExample from
  '!!raw-loader!@site/../../web/sites/default/example.settings.local.php';

## Guidelines

Follow these guidelines when you work with settings:

- **Don't modify `settings.php` directly.<br/>** Use environment variables
  for [general](#general) settings or
  [per-module override files](#per-module-overrides) for any custom or
  environment-aware configuration.

- **Keep all overrides isolated by module.**<br/>
  Each file holds the logic for 1 module only. When the module goes, you
  delete its override file, and no unrelated setting changes.

- **Use environment variables for configuration that changes by
  environment.**<br/>
  Prefix each such variable with `DRUPAL_`, for example
  `DRUPAL_MY_SETTING`, to tell it apart from other environment
  variables.<br/>
  Define a hardcoded default value for each environment variable.

- **Guard a variable by what it holds.**<br/>
  Read a _boolean flag_, a variable that only switches behavior on, with
  `getenv('DRUPAL_MY_FLAG') === '1'`. Every other value leaves the behavior
  off: an unset variable, an empty string, `0`, `true` and `yes`.<br/>
  Read a _value carrier_, a variable whose value is used, with
  `!empty(getenv('DRUPAL_MY_VALUE'))`. Assign it to a variable first when
  the value is needed after the guard.<br/>
  Compare with `===` and `!==`, never with `==`.

:::caution Flags accept only `1`

Each of the following flags acts only when it's exactly `1`. Any other
value, such as `true`, `yes` or `on`, counts as unset, so the flag has no
effect. Set each flag to exactly `1`, wherever you set it:

- `DRUPAL_CLAMAV_ENABLED`
- `DRUPAL_REDIS_ENABLED`
- `DRUPAL_REROUTE_EMAIL_DISABLED`
- `DRUPAL_SHIELD_DISABLED`
- `DRUPAL_SHIELD_ALLOW_ACME_CHALLENGE`
- `DRUPAL_TMP_PATH_IS_SHARED`
- `DRUPAL_SETTINGS_LOCAL_SKIP`
- `VORTEX_REDIS_EXTENSION_LOADED`

:::

- **Gate on the presence of a contributed module only when the file needs
  it.**<br/>
  `file_exists($contrib_path . '/my_module')` belongs in an override file
  that loads a file from the module directory or registers its paths. An
  override file that only writes `$config` or `$settings` skips the guard,
  because Drupal ignores overrides for a module that isn't installed.

- **Use conditions based on _environment type_ within per-module override
  files.**<br/>
  The conditions keep environment-specific configuration out of the main
  `settings.php` file.<br/>
  Check the current _environment type_ in `$settings['environment']`.

## Test settings with unit tests

**Vortex** includes a [set of unit
tests](https://github.com/drevops/vortex/blob/main/tests/phpunit/Drupal)
that verify the settings for each detected environment type. Maintain them
in your project, alongside your settings.

The tests check each environment type and each environment variable that
switches behavior on or off. They live in 3 test classes:

- `DatabaseSettingsTest`: the database connection settings
- `EnvironmentSettingsTest`: the settings in every environment type
- `SwitchableSettingsTest`: the settings that environment variables switch
  on or off

To run only the settings tests, open a shell in the CLI container with
`ahoy cli` and run the following command:

```shell
vendor/bin/phpunit --group=drupal_settings
```

Confirm that PHPUnit reports `OK` at the end of the run.

The tests are part of the `unit` test suite, so `ahoy test-unit` runs them
too. If you don't want to maintain them, remove them.
