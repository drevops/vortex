# Variables

<!-- markdownlint-disable -->

**Vortex** scripts read their settings from environment variables, so you
change how a script behaves by setting a variable instead of editing the
script.

This page is for developers and DevOps engineers who configure a project's
scripts locally, in CI, or on the hosting platform. It explains where a
value can come from and which one wins, then documents the project's
variables in the [variables list](#variables-list).

Variables come in 2 main types:

**Project configuration variables** are set once during project setup and
stay the same for the life of the project. You usually set them in the
`.env` file, or in the environment settings of your CI or hosting provider.

**Runtime variables** change during the project's life to alter how a
script behaves. For example, they change how a deployment runs, or skip
deploying a particular branch in CI.

## `.env` and `.env.local` files

`.env` holds the project's shared values and is committed with the code. It
lists only the variables a project usually sets. Every other optional
variable takes its default from the script that reads it. Add a variable to
`.env` when you need a value other than the default.

`.env.local` holds your local overrides and secrets, such as passwords and
API keys. Create it by copying `.env.local.example`. Git ignores it, so it
stays out of the repository. To apply a change to either file, see
[Environment > Environment
variables](environment/README.mdx#environment-variables).

## Override order (bottom values win)

Each source in the following list overrides the ones before it:

1. The default value in the script that reads the variable
2. The default value in the container, taken from the image
3. The default value in `docker-compose.yml`
4. The value in `.env`, where the last assignment in the file wins
5. The value in `.env.local`, where the last assignment in the file wins
6. The value from the environment

Each script loads `.env` and then `.env.local` itself, and skips every
variable that's already set in its environment. A value set in your shell,
in CI, or on the hosting platform wins over both files.

### Naming conventions

Variables that **Vortex** scripts own start with the `VORTEX_` prefix, which
keeps them apart from everything else in the environment. A few go without
it, such as `WEBROOT` and `PACKAGE_TOKEN`.

Drupal-specific variables start with the `DRUPAL_` prefix.

The environment detector reads shared, platform-neutral names that carry
neither prefix, such as `ENVIRONMENT_TYPE`, `ENVIRONMENT_PRODUCTION_BRANCH`,
and `LOCALDEV_URL`. `LOCALDEV_URL`, the local development URL, also shares
its value with the unprefixed hosting route, `LAGOON_ROUTE`.

Variables of third-party services, such as `NEWRELIC_ENABLED` or
`RENOVATE_TOKEN`, keep the names those services use.

### Default values

Every _required_ variable that a **Vortex** script uses is checked before the
script proceeds. An empty or unset one stops the script with an error that
names it, such as `Missing required value for VORTEX_DEPLOY_WEBHOOK_URL`.

Every _optional_ variable has a default value set in the script itself, so
the scripts run without extensive configuration. For example, a variable can
have a default value in the script and be overridden in the `.env` file. The
CI or hosting provider can override it again for all environments, and then
for a specific environment.

A variable with neither a provided value nor a script default is a defect in
the template, so report it. Without a default, a condition can take the
wrong branch, and the override chain has no base value to fall back to.

An empty value can't override a default. The scripts treat an empty value as
unset, so the script default applies instead. The exception is
`VORTEX_EXPORT_DB_FILE_STRUCTURE_TABLES`, where an empty value replaces the
`cache*` default.

### Boolean variables

Boolean variables use `1` for true and `0` for false, so a flag means the
same thing in every environment. We don't use `true`/`false`, `yes`/`no`, or
other variations, because some systems interpret `true` and `false`
differently.

Most scripts compare a flag against `1`, so `VORTEX_PROVISION_SKIP=true`
doesn't skip anything. 2 flags, `VORTEX_NOTIFY_SKIP` and
`VORTEX_NOTIFY_NEWRELIC_ENABLED`, switch on for any value other than an
empty one or `0`. `VORTEX_NOTIFY_NEWRELIC_ENABLED` takes `true`, because it
falls back to Lagoon's `NEWRELIC_ENABLED`. Third-party variables keep their
own values, such as `RENOVATE_DRY_RUN=true`.

### Columns of the variables list

The [variables list](#variables-list) collects the variables that `.env`,
`.env.local.example`, `docker-compose.yml`, the `scripts/` directory, CI,
and the hosting platforms define or use. A variable that only a **Vortex**
script reads isn't in the list. The script declares it, with a comment and
its default, at the top of its file in `vendor/drevops/vortex-tooling/src/`.

The list has 4 columns:

- **Name**: the variable's name.
- **Description**: what the variable does, taken from the comment before its
  definition.
- **Default value**: the value the variable gets when you don't set it.
  `UNDEFINED` means it has no default.
- **Defined or used in**: the files that define or read the variable.

Besides file paths, the **Defined or used in** column uses these labels:

- `ENVIRONMENT`: the variable comes from the environment that runs the
  scripts, such as your shell or the hosting platform.
- `CI config`: the variable comes from the CI configuration or from your CI
  provider's settings.
- `LAGOON ENVIRONMENT`: the variable is set in Lagoon environments.
- `ACQUIA ENVIRONMENT`: the variable is set in Acquia environments.
