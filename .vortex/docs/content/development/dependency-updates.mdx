# Dependency updates

**Vortex** provides [Renovate](https://renovatebot.com) configuration for your project's automated dependency updates.

## How updates are organized

All Renovate PRs use the branch prefix `deps/` and are labeled `Dependencies`.
Assignees can be configured in the `assignees` field.

### Update rules

| Group | Packages | Update types | Schedule | Minimum release age |
|---|---|---|---|---|
| **Drupal core** | `drupal/core-recommended`, `drupal/core-composer-scaffold` and other `drupal/core-*` packages | Minor, patch | Daily before 2 AM UTC | None |
| **Drupal contrib and PHP packages (non-core)** | All Drupal contrib modules and non-Drupal Packagist packages | Minor, patch | Weekly, Sunday before 2 AM UTC | 14 days for Packagist packages |
| **JS packages** | All npm packages (root `package.json` only) | Minor, patch | Weekly, Sunday before 2 AM UTC | 14 days |
| **Container images** | All images in `.docker/` and `docker-compose.yml` | Major, minor, patch | Daily before 3 AM UTC | 14 days for Docker Hub images |
| **CI tools** | npm packages that CI runs at a pinned version through `npx` | Major, minor, patch | Daily before 3 AM UTC | 14 days |
| **GitHub Actions** | All actions (pinned to digests) | Major, minor, patch | Daily before 3 AM UTC | 14 days |

### Auto-merge

Every group auto-merges by default. GitHub merges the PR as soon as it meets
the base branch's protection rules, such as passing required status checks.
Each group in `renovate.json` lists an explicit `automerge` flag. To merge a
group's PRs yourself, set its flag to `false`:

```json
{
    "groupName": "PHP - Drupal core - Minor and patch",
    "groupSlug": "php-drupal-core-minor-patch",
    ...
    "automerge": false
}
```

The CLI asks which groups to auto-merge. It sets the flag to `true` for the
groups you select and to `false` for the rest. When you update **Vortex**, the
CLI preselects the groups whose flag is already `true`.

Auto-merge requires 2 repository settings:

1. **"Allow auto-merge"** enabled under *Settings > General > Pull Requests*.
2. **"Require status checks to pass before merging"** configured in the base
   branch's branch protection rules, with at least 1 required status check
   selected. Otherwise, GitHub might merge even if CI is red.

Every required status check must also report on `deps/*` branches. A check
that never reports keeps the PR blocked indefinitely, such as a CircleCI job
that a branch filter excludes from `deps/*` branches. A GitHub Actions job
skipped by its `if` condition reports as skipped, which satisfies the
requirement.

### Minimum release age

Renovate holds back a new release until it's 14 days old, in every group except
Drupal core. A registry often detects and pulls a compromised release within
days. Nobody reviews an auto-merged update, so the delay keeps such a release
out of your project.
[Renovate recommends 14 days](https://docs.renovatebot.com/upgrade-best-practices/#wait-two-weeks-before-automerging-third-party-dependencies)
when you auto-merge third-party dependencies.

Each delayed group sets `minimumReleaseAge` next to its `automerge` flag:

```json
{
    "groupName": "JavaScript - All packages - Minor and patch",
    "groupSlug": "js-all-minor-patch",
    ...
    "minimumReleaseAge": "14 days",
    "automerge": true
}
```

Renovate creates the branch and the PR only after a release reaches that age.
The top-level `"internalChecksFilter": "strict"` setting enforces this, so
GitHub's auto-merge can't merge a release early. When the newest release is
too young, Renovate proposes the newest release that's old enough. A grouped
PR leaves out the packages that have no release old enough yet.

The delay adds to each group's schedule. A weekly group proposes a release 14
to 21 days after it's published, and a daily group 14 to 15 days after.

#### Drupal core

Drupal core has no delay, so Renovate proposes a core security release on the
next daily run. The core rule in `renovate.json` carries a `description` that
says so.

#### Registries without release dates

Renovate can hold back a release only when its registry records the
publication date. Of the registries **Vortex** uses, 2 record no dates:
Drupal.org (Drupal contrib modules) and GitHub Container Registry (the
Gitleaks image). Their updates arrive without the delay. The top-level
`"minimumReleaseAgeBehaviour": "timestamp-optional"` setting lets these updates
through; without it, Renovate holds them back indefinitely. The
`logLevelRemap` entry stops Renovate from reporting them as a repository
problem on the Dependency Dashboard.

Renovate ages a GitHub Action by the date of the commit its tag points to. The
action's publisher controls that date, so the delay is a weaker safeguard for
actions than for registry packages.

#### Security fixes

When Renovate can read your repository's Dependabot alerts, it raises a fix for
a published advisory straight away, skipping the delay and the schedule.
Otherwise, a security fix arrives as a routine update and waits like any other.
To apply a fix sooner, update the dependency yourself or request the pending
update from the Dependency Dashboard.

#### Changing the delay

To change a group's delay, edit its `minimumReleaseAge`. To remove the delay,
delete the key. A group with auto-merge turned off keeps its delay, so delete
the key too if you want those PRs as soon as a release is published.

The Dependency Dashboard lists updates waiting for the minimum age under
**Pending Status Checks**, where you can also request 1 early. The self-hosted
service turns the dashboard off by default: set `RENOVATE_DEPENDENCY_DASHBOARD`
to `true` to see them.

## Configuration

The configuration is stored in [`renovate.json`](https://github.com/drevops/vortex/blob/main/renovate.json). It is
based on [Renovate configuration for automated Drupal dependency updates](https://github.com/drevops/renovate-drupal)
project.

### PR throughput and presentation

- **Concurrent PR limit:** `prConcurrentLimit: 10` - at most 10 open PRs
  across all groups at any time.
- **Hourly PR limit:** `prHourlyLimit: 0` - no hourly cap; the per-group
  schedules above provide throttling.
- **Commit body table:** `commitBodyTable: true` - grouped update commits
  include a version-comparison table in the commit message body.
- **Dashboard labels:** the Renovate dependency dashboard issue is labeled
  `Dependencies` (`dependencyDashboardLabels`).

### Disabled updates

These are intentionally skipped by Renovate - update them manually:

| Group | What is skipped | Why |
|---|---|---|
| Drupal core major | `drupal/core-recommended`, `drupal/core-composer-scaffold` and other `drupal/core-*` packages | Major version upgrades may introduce breaking changes |
| PHP and Drupal contrib major | All Drupal contrib modules and non-Drupal Packagist packages | Major version upgrades may introduce breaking changes |
| JS major | All npm packages | Major version upgrades may introduce breaking changes |
| PHP language version | `php` constraint in `composer.json` | Major version upgrades may introduce breaking changes |
| JS language versions | `node`, `npm` in `package.json` | Major version upgrades may introduce breaking changes |
| JS non-root packages | Any `package.json` not at the root | Theme dependencies are managed separately |

## Continuous integration

Renovate can run as a hosted GitHub app or as a standalone self-hosted service
in CircleCI or GitHub Actions. A self-hosted service suits projects that
restrict third-party access to their repositories.

:::note

If the job is configured but a required variable is not provided, the job
still runs and the Renovate update steps are skipped gracefully without
failing the build. On GitHub Actions the required variables are
`RENOVATE_TOKEN` and `RENOVATE_GIT_AUTHOR`; CircleCI additionally requires
`RENOVATE_REPOSITORIES`, since it has no repository to default to.

:::

### Dependency dashboard

The Renovate Dependency Dashboard is a GitHub issue that provides visibility into:

- Available dependency updates that are scheduled for later execution
- Updates waiting for their release to reach the
  [minimum release age](#minimum-release-age)
- Updates that have been filtered out due to configuration rules
- Failed update attempts and their reasons

The dashboard is created with the title "RenovateBot Dependency Dashboard (self-hosted)"
when running in self-hosted mode. This dashboard is particularly useful for understanding
why certain updates might not be applied immediately due to scheduling constraints or
configuration rules.
