# PHPUnit

import Tabs from '@theme/Tabs';
import TabItem from '@theme/TabItem';

[PHPUnit](https://phpunit.de/) tests your custom PHP code. **Vortex** sets
it up with 4 test suites that follow Drupal's test types. Unit tests check a
class in isolation, kernel and functional tests check it against a
bootstrapped Drupal, and functional JavaScript tests drive a real browser.

**Vortex** includes a PHPUnit configuration in
[`phpunit.xml`](https://github.com/drevops/vortex/blob/main/phpunit.xml),
based on Drupal core's `core/phpunit.xml.dist`, so you can customize the
test suites per project.

## Usage

## Writing tests

### Skipping tests

`phpunit.xml` excludes the `skipped` group by default, so a
`#[Group('skipped')]` attribute (imported from
`PHPUnit\Framework\Attributes\Group`) on a test class or method takes it out
of the test run:

```php
#[Group('skipped')]
public function testSomethingToSkip(): void {
  // This test will be skipped
}
```

Calling `markTestSkipped()` instead fails the run, because `phpunit.xml`
sets `failOnSkipped`. Use the attribute rather than the older
`@group skipped` docblock annotation, too: PHPUnit 11 reports a deprecation
for annotations, and `failOnPhpunitDeprecation` turns that into a failure.

### Boilerplate

**Vortex** ships unit, kernel, functional, and functional JavaScript
boilerplate tests for a custom
[module](https://github.com/drevops/vortex/blob/main/web/modules/custom/ys_base/tests/src)
and the custom
[theme](https://github.com/drevops/vortex/blob/main/web/themes/custom/your_site_theme/tests/src),
plus project-level tests for the [Drupal settings and the CI
configuration](https://github.com/drevops/vortex/blob/main/tests/phpunit).

These boilerplate tests run in the continuous integration pipeline from the
moment you install **Vortex**, and they make a good starting point for your
own.

#### Drupal settings tests

The [Drupal settings
tests](https://github.com/drevops/vortex/blob/main/tests/phpunit/Drupal)
check that the site gets the right settings for the environment type it
runs in. Every module's settings multiply against 5 environment types
(`local`, `ci`, `dev`, `stage`, and `prod`), so a missed override is a
common mistake. It shows up only after you deploy to the environment that
lacks it.

`EnvironmentSettingsTest` covers environment detection and the settings
each environment type gets. `SwitchableSettingsTest` covers the settings
that modules and services switch on and off, and `DatabaseSettingsTest`
covers the database connection. The tests belong to your site: keep them in
step with every change you make to `settings.php` and the files it
includes.

#### Continuous integration pipeline configuration tests

The [CircleCI configuration
tests](https://github.com/drevops/vortex/blob/main/tests/phpunit/CircleCiConfigTest.php)
check the CircleCI configuration that's hardest to eyeball: the regular
expressions that filter the branches and tags before they're deployed to
the hosting environment. They match each filter against sample branch and
tag names, and check that no filter pattern exceeds the 128 characters the
CircleCI compiler accepts.

The installer keeps this test only when you choose CircleCI as the CI
provider. It looks the deployment jobs up by their position in the `commit`
workflow, so if you move a job in that list, update the test too. Keep the
test in step with your continuous integration configuration.

### Project conventions

For project-specific test writing conventions (test class structure, base
classes, data providers, test data conventions), see your project's
`docs/testing.md` file.

The installer scaffolds `docs/testing.md` when you install **Vortex**, and
your project team maintains it to record the testing practices you agree
on.

## Configuration

See the PHPUnit [configuration
reference](https://docs.phpunit.de/en/11.5/configuration.html).

All global configuration takes place in the
[`phpunit.xml`](https://github.com/drevops/vortex/blob/main/phpunit.xml)
file in the project root. It configures:

- Test suite directories and naming patterns
- Bootstrap file for Drupal integration
- Environment variables for test execution
- Code coverage settings
- The JUnit report
- The excluded `skipped` group
- The HTML output logger for browser tests

The configuration is strict. A warning, a skipped test, or a PHPUnit
deprecation fails the run, and the run stops at the first error, failure,
warning, or risky test.

By default, PHPUnit runs the tests of your custom modules and themes, plus
the project-level tests in `tests/phpunit`: the Drupal settings tests and,
on CircleCI projects, the CircleCI configuration test.

### Test suites

PHPUnit tests are organized into test suites defined in `phpunit.xml`:

- **unit** - fast tests of isolated PHP classes without a Drupal bootstrap
- **kernel** - tests with a partial Drupal bootstrap (database and core
  services)
- **functional** - tests with a full Drupal bootstrap and browser simulation
- **functional-javascript** - tests with a full Drupal bootstrap and a real
  browser (Chrome via Selenium) for JavaScript interactions

Each suite collects the matching `tests/src/` directory (`Unit`, `Kernel`,
`Functional`, or `FunctionalJavascript`) of every custom module and theme.
The `unit` suite also collects `tests/phpunit`.

To add test targets, add a directory to a test suite:

```xml
<testsuite name="unit">
  <directory>my/custom/dir/*/tests</directory>
</testsuite>
```

### Chrome session flags

Functional JavaScript tests use a Chrome browser running in the
[`selenium/standalone-chromium`](https://hub.docker.com/r/selenium/standalone-chromium)
container. `phpunit.xml` passes the following flags to it in
`MINK_DRIVER_ARGS_WEBDRIVER`, so the tests run the same way every time:

| Flag                             | Purpose                                                          |
|----------------------------------|------------------------------------------------------------------|
| `--disable-extensions`           | Prevents interference from browser extensions                    |
| `--disable-popup-blocking`       | Allows tests to open popups without being blocked                |
| `--disable-translate`            | Prevents the translation bar from appearing on non-English pages |
| `--force-prefers-reduced-motion` | Disables CSS animations and transitions for test stability       |
| `--test-type`                    | Suppresses error dialogs and crash recovery prompts              |
| `--window-size=1920,1080`        | Sets a deterministic viewport size for consistent screenshots    |

The `w3c: true` option is required for compatibility with Selenium 4.

### Bootstrap

The custom
[`tests/phpunit/bootstrap.php`](https://github.com/drevops/vortex/blob/main/tests/phpunit/bootstrap.php)
file runs before tests to:

1. Set `BROWSERTEST_OUTPUT_BASE_URL` from the `LOCALDEV_URL` environment
   variable so that HTML output links are accessible from the host machine.
2. Create the `web/sites/simpletest/browser_output` directory required by
   the `HtmlOutputLogger` extension before it initializes (see [Drupal core
   issue #2992069](https://www.drupal.org/project/drupal/issues/2992069)).
3. Load Drupal core's own `web/core/tests/bootstrap.php`.

## Reports

PHPUnit writes a JUnit XML report to
`.logs/test_results/phpunit/phpunit.xml`.

### Coverage

PHPUnit writes 3 coverage reports to `.logs/coverage/phpunit/`:
[Cobertura XML](https://cobertura.github.io/cobertura/) in `cobertura.xml`
for automated coverage checks, a text summary in `coverage.txt`, and an HTML
report in `.coverage-html` for browsing while you write tests. CI reads the
coverage rate from `cobertura.xml` and builds the PR comment from
`coverage.txt`.

Coverage measures the code in your custom modules and themes,
`web/sites/default/includes`, and `settings.php`. It leaves out test
classes, `*.deploy.php` files, `node_modules`, and `tests`.

### Ignoring lines from coverage

Sometimes you need to leave code out of coverage. For example, when testing
a module that uses a third-party library, you don't need to test the library
itself.

To ignore a method from coverage, add a `@codeCoverageIgnore` annotation to
the method docblock.

```php
/**
 * @codeCoverageIgnore
 */
public function myMethod() {
  // ...
}
```

To ignore a block of lines from coverage, add `@codeCoverageIgnoreStart`
before the first line and `@codeCoverageIgnoreEnd` after the last one.

```php
// @codeCoverageIgnoreStart
$a = 1;
$b = 2;
// @codeCoverageIgnoreEnd
```

## Continuous integration

In the continuous integration pipeline, PHPUnit runs on the first container
only (see [Test
parallelism](../../continuous-integration/README.mdx#test-parallelism)). It
runs with coverage by default, and the pipeline stores the coverage reports
as artifacts. The pipeline also collects the JUnit report to track test
performance and stability: GitHub Actions publishes it as [test
results](../../continuous-integration/github-actions.mdx#test-results), and
CircleCI stores it with the job's test results.

If you chose Codecov as the code coverage provider during installation, the
pipeline also uploads the coverage reports to Codecov when `CODECOV_TOKEN`
is set.

### Coverage threshold

CI fails the build when line coverage drops below a minimum percentage. Set
`VORTEX_CI_CODE_COVERAGE_THRESHOLD` to configure it (default: `90`). The
check reads the line rate from `cobertura.xml`. It has no ignore-failure
variable of its own, so it still runs, and can still fail the build, when
you ignore PHPUnit failures.

On pull requests, CI posts the coverage summary as a PR comment, with the
threshold and a collapsible per-class breakdown. Each new report replaces
the previous one: older comments are minimized to keep the PR timeline
clean. GitHub Actions and CircleCI tag their comments with separate hidden
markers, so each provider minimizes only its own comments.

CircleCI posts the comment only when a `GITHUB_TOKEN` environment variable
is set, and skips the step without one. GitHub Actions also writes the
coverage percentage to the job summary. Set
`VORTEX_CI_CODE_COVERAGE_PR_COMMENT_SKIP` to `1` to turn the comment off.

### Ignoring failures

Set `VORTEX_CI_PHPUNIT_IGNORE_FAILURE` to `1` to let the build pass despite
failing tests. PHPUnit still runs and reports the failure in the job log,
and the [coverage threshold](#coverage-threshold) check still applies. See
[Ignore tool
failures](../../continuous-integration/README.mdx#ignore-tool-failures).
