# Testing

import AsciinemaPlayer from '@site/src/components/AsciinemaPlayer';

This page helps developers on a project built from **Vortex** pick the
right test framework, run it, and find its results. Visual regression
testing has a page of its own; see
[Visual regression](../visual-regression.mdx).

**Vortex** ships 3 test frameworks, configured and wired into the
continuous integration pipeline, so the first test you add runs in CI with
no extra setup. Each covers a different layer of the site:

| Framework              | Covers                                                                                                                           | Command         |
|------------------------|----------------------------------------------------------------------------------------------------------------------------------|-----------------|
| [PHPUnit](phpunit.mdx) | Your custom PHP code, through unit, kernel, functional, and functional JavaScript tests                                          | `ahoy test`     |
| [Behat](behat.mdx)     | Behavior-Driven Development (BDD) scenarios, run end to end against the site, in a real browser when a scenario needs JavaScript | `ahoy test-bdd` |
| [Jest](jest.mdx)       | The JavaScript behaviors in your custom modules, tested in isolation                                                             | `ahoy test-js`  |

➡️ See [PHPUnit > Writing tests](phpunit.mdx#writing-tests), [Behat >
Writing tests](behat.mdx#writing-tests), and [Jest > Test file
structure](jest.mdx#test-file-structure) for where a new test goes.

## Running

Run the tests with the following Ahoy commands:

```shell
ahoy test                        # Run all PHPUnit test suites.
ahoy test-unit                   # Run PHPUnit unit tests.
ahoy test-kernel                 # Run PHPUnit kernel tests.
ahoy test-functional             # Run PHPUnit functional tests.
ahoy test-functional-javascript  # Run PHPUnit functional JavaScript tests.
ahoy test-bdd                    # Run Behat tests.
ahoy test-js                     # Run Jest tests.
```

Each framework page lists the Docker Compose equivalents and the options for
running a single file, a tag, or a filter.

### Run unit, kernel, and functional tests

`ahoy test` runs all the PHPUnit test suites: unit, kernel, functional, and
functional JavaScript.

## Reports and coverage

Each framework writes its reports under `.logs/`, and the continuous
integration pipeline stores them as artifacts:

- [PHPUnit](phpunit.mdx#reports) writes its JUnit report to
  `.logs/test_results/phpunit/phpunit.xml` and its [coverage
  reports](phpunit.mdx#coverage) to `.logs/coverage/phpunit/`.
- [Behat](behat.mdx#reports) writes its JUnit reports to
  `.logs/test_results/behat/`.
- [Jest](jest.mdx#coverage) writes its coverage reports to
  `.logs/coverage/jest/`.

## Continuous integration

Tests run in the `build` job of the continuous integration pipeline, which
runs on 2 parallel containers by default. PHPUnit and Jest run on the first
container, and Behat spreads its scenarios across every container (see [Test
parallelism](../../continuous-integration/README.mdx#test-parallelism)).

Each framework has a variable that lets the build pass despite failing
tests. Set it to `1`, and the tool still runs and reports every failure in
the job log:

- `VORTEX_CI_PHPUNIT_IGNORE_FAILURE`
- `VORTEX_CI_BEHAT_IGNORE_FAILURE`
- `VORTEX_CI_JEST_IGNORE_FAILURE`

The PHPUnit [coverage threshold](phpunit.mdx#coverage-threshold) check has
no such variable, so it can still fail the build.

➡️ See [Ignore tool
failures](../../continuous-integration/README.mdx#ignore-tool-failures).

## Project conventions

Your project's own test writing conventions live in its `docs/testing.md`
file, which your project team keeps up to date. It covers the following
topics:

- PHPUnit: test class structure, base test classes, test data, data
  providers, and kernel tests for services
- Behat: user story format, standard user types, test data, an example
  feature file, and the process for testing a content type

**Vortex** ships the file in the project's `docs/` directory, and the
installer keeps it unless you decline its
**Preserve project documentation?** prompt. Declining it removes the whole
`docs/` directory.
