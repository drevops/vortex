# Contributed modules

**Vortex** ships the contributed modules most Drupal projects need,
pre-configured and wired into the environment-aware settings and the
provisioning scripts. This page lists all 26 shipped modules in alphabetical
order: what each one does, why it ships, and how it's configured.

➡️ See [Overview](README.mdx) for the mechanisms that require, configure,
and install these modules.

## ClamAV

[ClamAV](https://www.drupal.org/project/clamav) scans uploaded files for
malware with the ClamAV engine before they're saved. Ships only when the
ClamAV service is selected.

### Configuration

[`settings.clamav.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.clamav.php)
selects daemon or executable mode and points the daemon at the ClamAV
service, but only when `DRUPAL_CLAMAV_ENABLED` is set to `1`. The shipped
`.env` file sets it, with `DRUPAL_CLAMAV_MODE` set to `daemon`.

| Variable                     | Purpose                                                              |
|------------------------------|----------------------------------------------------------------------|
| `DRUPAL_CLAMAV_ENABLED`      | Applies the override only when set to `1`                            |
| `DRUPAL_CLAMAV_MODE`         | `daemon` or `0` selects daemon mode, any other value executable mode |
| `CLAMAV_HOST`, `CLAMAV_PORT` | Daemon host and port, `clamav:3310` by default                       |

## Config Split

[Configuration Split](https://www.drupal.org/project/config_split) splits
configuration into sets that are imported conditionally, so each environment
can carry its own configuration, such as development-only modules.

### Configuration

[`settings.config_split.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.config_split.php)
enables the split matching the detected environment (`local`, `ci`, `dev`,
or `stage`), so each environment imports only its own set. The template
ships empty `config/local`, `config/ci`, `config/dev`, and `config/stage`
directories but no splits, so create a split with the matching machine name
before the override has anything to enable.

## Environment Indicator

[Environment
Indicator](https://www.drupal.org/project/environment_indicator) shows a
colored banner identifying the current environment to prevent accidental
changes on the wrong site.

### Configuration

[`settings.environment_indicator.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.environment_indicator.php)
names the indicator after the detected environment and colors it per
environment: red for production, yellow for stage, and green for dev. Every
other environment, `local` and `ci` included, gets a dark green banner with
white text. It also turns on the toolbar integration and the favicon marker.

## Fast 404

[Fast 404](https://www.drupal.org/project/fast_404) answers requests for
missing files without bootstrapping Drupal. Drupal core already returns a
lightweight 404 for the same file extensions, but only after a full
bootstrap. On a site serving many such requests, the saving is the bootstrap
itself.

- **Installed:** Never enabled as a Drupal module. The handler runs from the
  settings file during the settings load, before the module system exists,
  so requiring the package is all that's needed.

### Configuration

[`settings.fast_404.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.fast_404.php)
applies only when the module's code is present. It sets the file extensions
to intercept and whitelists `index.php`, `rss.xml`, `cron.php`, and
`xmlrpc.php`. It brings image style derivatives under the same rules, so
anonymous requests can't force derivative generation, and calls
`fast404_preboot()` with those settings. Path checking against the router
and the URL aliases is off, because it queries the database before Drupal
has connected to it. The redirect check that goes with the path check is
off too.

## Redis

[Redis](https://www.drupal.org/project/redis) integrates Drupal with the
Redis in-memory store for cache and lock backends. Ships only when the Redis
service is selected.

### Configuration

[`settings.redis.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.redis.php)
points the connection at the Redis service, makes Redis the default cache
backend, registers the module's container YAML files, and swaps the
bootstrap container over. Nothing applies until the module's code is
present and `DRUPAL_REDIS_ENABLED` is set to `1`, so a 2-stage deployment
can provision the service before switching the cache. The cache changes
also need the `redis` PHP extension, or `VORTEX_REDIS_EXTENSION_LOADED` set
to `1` in its place.

| Variable                           | Purpose                                   |
|------------------------------------|-------------------------------------------|
| `DRUPAL_REDIS_ENABLED`             | Applies the override only when set to `1` |
| `REDIS_HOST`, `REDIS_SERVICE_PORT` | Connection host and port                  |
| `VORTEX_REDIS_EXTENSION_LOADED`    | Forces the cache changes when set to `1`  |

## Reroute Email

[Reroute Email](https://www.drupal.org/project/reroute_email) intercepts
outgoing emails and redirects them to a configurable address instead of the
intended recipients. You can then test email features in non-production
environments without accidentally delivering mail to real users.

- **Installed:** During development provisioning by
  [`scripts/provision-10-enable-dev-modules.sh`](https://github.com/drevops/vortex/blob/main/scripts/provision-10-enable-dev-modules.sh),
  so the safety net survives the demo script being adapted or removed.

### Configuration

[`settings.reroute_email.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.reroute_email.php)
excludes the module from the exported configuration and enables rerouting in
every environment except `local`, `ci`, and `prod`.

Rerouting replaces the recipient of an outgoing message with the configured
address, unless that recipient matches `DRUPAL_REROUTE_EMAIL_ALLOWED`. With
rerouting disabled, every message reaches its intended recipient. Rerouting
is therefore disabled only where that delivery is either wanted or already
intercepted by other means.

**Environment behavior:**

| Environment | Rerouting enabled | Reason                                                          |
|-------------|-------------------|-----------------------------------------------------------------|
| Local       | No                | [Pygmy](../environment/pygmy.mdx) already catches outgoing mail  |
| CI          | No                | The [mail collector](../testing/behat.mdx#email) stores messages instead of sending them |
| Dev         | **Yes**           | Prevents accidental delivery to real users                      |
| Stage       | **Yes**           | Stage runs a copy of production content, so any address that survives database sanitization is a real one |
| Prod        | No                | Production emails must reach actual recipients                  |

Rerouting is the fall-through default, so it's also enabled in any custom
environment type, such as one set through `ENVIRONMENT_TYPE`. Lagoon and
Acquia usually detect pull request environments as `dev`, so those get
rerouting like any other `dev` environment. A custom environment type gets
the module only once you add the type to the provisioning scripts, and until
then nothing reroutes its mail. ➡️ See
[Provision](../provision.mdx#development-modules)

Rerouting is off in `ci` so that tests can assert on the address a message
was sent to. With rerouting on, every message would carry the rerouting
address instead of the intended one.

A site that deselects this module during
[installation](../../installation.mdx) still sends no mail from `ci`,
because the mail collector stores messages there regardless. That site does
send mail to real recipients in `dev`, `stage`, and custom environments.

**Environment variables:**

| Variable                       | Default                            | Purpose                                              |
|--------------------------------|------------------------------------|------------------------------------------------------|
| `DRUPAL_REROUTE_EMAIL_ADDRESS` | `webmaster@your-site-domain.example` | Address to receive all rerouted emails               |
| `DRUPAL_REROUTE_EMAIL_ALLOWED` | `*@your-site-domain.example`         | Pattern for addresses allowed to bypass rerouting    |

**Overriding default behavior:**

Set `DRUPAL_REROUTE_EMAIL_DISABLED` to `1` to disable email rerouting in an
environment where it would otherwise be enabled. This is the supported way
for a `stage` environment to send real mail during UAT.

## RobotsTxt

[RobotsTxt](https://www.drupal.org/project/robotstxt) serves `robots.txt`
from Drupal and lets you edit it in the admin UI, which helps when the file
can't live on disk, for example in multisite setups. **Vortex** keeps core's
static `robots.txt` out of the webroot through the `drupal-scaffold` file
mapping in `composer.json`, so the module answers every request for it.

### Configuration

[`settings.robotstxt.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.robotstxt.php)
serves a `Disallow: /` file outside production, so non-production
environments aren't indexed.

## Security Kit

[Security Kit](https://www.drupal.org/project/seckit) adds configurable
security-hardening HTTP headers, including Content Security Policy and

- **Installed:** Required only, not installed during provisioning. Enable it

## Shield

[Shield](https://www.drupal.org/project/shield) restricts access to your
site by requiring HTTP authentication credentials.

### Configuration

[`settings.shield.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.shield.php)
forces Shield on in non-production environments other than `local` and `ci`,
where it's forced off. Production is left untouched, so Shield stays under
UI control there.

**Environment behavior:**

| Environment | Shield enabled | Reason                                            |
|-------------|----------------|---------------------------------------------------|
| Local       | No             | No need for HTTP auth during local development    |
| CI          | No             | Automated tests must access the site freely       |
| Dev         | **Yes**        | Protects development environments from crawlers   |
| Stage       | **Yes**        | Protects staging environments from public access  |
| Prod        | Not enforced   | Left to the site configuration: enable or disable it through the UI |

**Environment variables:**

| Variable                             | Default | Purpose                                             |
|--------------------------------------|---------|-----------------------------------------------------|
| `DRUPAL_SHIELD_USER`                 |         | HTTP authentication username                        |
| `DRUPAL_SHIELD_PASS`                 |         | HTTP authentication password                        |
| `DRUPAL_SHIELD_PRINT`                |         | Message shown in the authentication popup (module default when unset) |
| `DRUPAL_SHIELD_ALLOW_ACME_CHALLENGE` |         | Set to `1` to keep the `/.well-known/acme-challenge/*` path open for Let's Encrypt certificate generation |

**Overriding default behavior:**

Set `DRUPAL_SHIELD_DISABLED` to `1` to disable Shield in an environment
where it would otherwise be enabled. This is useful for temporary access
during debugging or when an environment doesn't require protection.

## Stage File Proxy

[Stage File Proxy](https://www.drupal.org/project/stage_file_proxy) fetches
media files from a remote site on demand, so local environments don't need a
full copy of the files directory.

### Configuration

[`settings.stage_file_proxy.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.stage_file_proxy.php)
sets the origin from `DRUPAL_STAGE_FILE_PROXY_ORIGIN` outside production and
injects the Shield credentials into that URL when they're set, so a shielded
origin still serves files. It also turns off redirects to the origin, so the
module downloads each requested file and keeps a local copy.

## Storybook

[Storybook](https://www.drupal.org/project/storybook) renders the custom
theme's component stories through Drupal, so the
[component library](../themes.mdx#storybook) shows the markup the site
produces. Ships only when Storybook is selected during installation, which
requires a custom theme.

[`scripts/provision-10-enable-dev-modules.sh`](https://github.com/drevops/vortex/blob/main/scripts/provision-10-enable-dev-modules.sh)
installs it with the other development modules. Later in provisioning,
`scripts/provision-50-storybook.sh` builds the static component library in
the `local`, `ci`, and `dev` environments.

### Configuration

[`settings.storybook.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/modules/settings.storybook.php)
excludes it from the exported configuration. In the `local`, `ci`, and `dev`
environments, it also loads `services.storybook.yml`, which turns on the
module's development mode and lets the Storybook development server on
`localhost` fetch story renders.

➡️ See [Storybook](../themes.mdx#storybook) for the component library and
its commands.
