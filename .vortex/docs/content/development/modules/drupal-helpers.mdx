# Drupal helpers

Deploy hooks and update scripts often create taxonomy trees, place blocks
or import redirects from a CSV file.
[Drupal helpers](https://www.drupal.org/project/drupal_helpers) turns each
of those jobs into a method on a static facade. A deploy hook
then reads as a short list of changes instead of entity API boilerplate.

This page is for developers writing deploy hooks on a project built from
**Vortex**. It shows how to call the helpers, which facades exist and how
to spread a large job across several deploy hook passes. The [module
documentation](https://git.drupalcode.org/project/drupal_helpers/-/blob/HEAD/README.md)
is the reference for its full API.

**Vortex** requires the module, and only the `ys_demo` demo module installs
it, as a dependency. Declare the same dependency in the `.info.yml` file of
every module whose code calls the helpers, so they stay available without
the demo module:

```yaml
dependencies:
  - drupal_helpers:drupal_helpers
```

## Helper facade

The `Helper` class hands out the helper services without dependency
injection, so a deploy hook can call them directly:

```php
use Drupal\drupal_helpers\Helper;

// Create taxonomy terms.
Helper::term()->createTree('tags', ['News', 'Events', 'Blog']);

// Create menu links.
Helper::menu()->createTree('main', [
  'About' => '/about',
  'Contact' => '/contact',
]);

// Delete all entities of a type.
Helper::entity()->deleteAll('node', 'page');
```

4 helpers declare a module they need, and the facade checks that module
before it returns the helper. When the module is missing, the facade throws
a `RuntimeException` that names it, for example
`Required modules not installed: redirect.` The deploy hook then stops
before that helper changes anything.

The following facades run the check:

- `Helper::block()` needs the Block module.
- `Helper::redirect()` needs the Redirect module.
- `Helper::role()` needs the User module.
- `Helper::translation()` needs the Locale module.

## Available helpers

The following table lists all 13 facades. The **Examples** column names
some of the methods each one exposes, and the module documentation lists
them all.

| Helper | Access | Examples |
|--------|--------|----------|
| Term | `Helper::term()` | `createTree()`, `deleteAll()`, `find()` |
| Menu | `Helper::menu()` | `createTree()`, `deleteTree()`, `findItem()`, `updateItem()` |
| Entity | `Helper::entity()` | `create()`, `update()`, `deleteAll()`, `batchQuery()` |
| Config | `Helper::config()` | `get()`, `set()`, `import()`, `setFrontPage()` |
| User | `Helper::user()` | `create()`, `createMultiple()`, `assignRoles()`, `removeRoles()` |
| Redirect | `Helper::redirect()` | `create()`, `deleteBySource()`, `importFromCsv()` |
| Field | `Helper::field()` | `delete()`, `deleteInstance()` |
| Module | `Helper::module()` | `install()`, `uninstall()` |
| Alias | `Helper::alias()` | `create()`, `findByPath()`, `updateByPath()`, `deleteAll()`, `importFromCsv()` |
| Block | `Helper::block()` | `place()`, `remove()`, `createContent()`, `deleteContent()` |
| Role | `Helper::role()` | `create()`, `delete()`, `grantPermissions()`, `revokePermissions()` |
| Display | `Helper::display()` | `setFormComponent()`, `setViewComponent()`, `hideFormComponent()`, `hideViewComponent()` |
| Translation | `Helper::translation()` | `set()` |

The class has 2 more static methods. `Helper::report()` returns a summary
of what the helpers did and resets the tally, so a deploy hook that ends
with `return Helper::report();` reports only its own work.
`Helper::reporter()` returns the reporter service behind that summary.

## Batched operations

The following facades accept the deploy hook's `$sandbox` array as their
first argument:

- `Helper::term()`
- `Helper::menu()`
- `Helper::field()`
- `Helper::entity()`
- `Helper::user()`
- `Helper::redirect()`
- `Helper::alias()`
- `Helper::block()`

With a sandbox, `batch()` and `batchEntity()` spread large datasets across
multiple deploy hook passes:

```php
function ys_base_deploy_update_pages(array &$sandbox): ?string {
  return Helper::entity($sandbox)->batchEntity('node', 'page', function ($node) {
    $node->set('field_migrated', TRUE);
    $node->save();
  });
}
```

Without a sandbox, both methods process every item in 1 pass. The
`batchEntity()` method builds the entity query itself from the type, the
bundle and optional conditions. The `batch()` method takes any array of
items.

Both methods return `NULL` while batches remain. After the last batch, they
return the completion message for Drush to print, such as
`Processed 120 node entities.` Each pass handles 50 items by default. To
change the batch size, pass a second argument to the facade, for example
`Helper::entity($sandbox, 100)`.

## Example in Vortex

The
[`ys_demo.deploy.php`](https://github.com/drevops/vortex/blob/main/web/modules/custom/ys_demo/ys_demo.deploy.php)
file uses `Helper::menu()` to add a `Pages` link to the main navigation
during deployment. It looks for the link with `findItem()` first, as an
extra guard. In its default safe mode, `createTree()` already matches links
by title within their parent and creates only the missing ones. Running the
hook again therefore creates no duplicate.
