# Themes

**Vortex** ships a [theme
scaffold](https://github.com/drevops/vortex/tree/main/web/themes/custom/your_site_theme):
a working Drupal theme called `your_site_theme`. The build, lint and test
tooling already work with it, so the commands on this page run on it
without any setup.

This page is for developers who build the front end of a **Vortex**
project. It covers the theme's build commands and file layout, the sample
Single Directory Component, the tests scaffold and the optional Storybook
component library.

The installer keeps the scaffold when you pick **Custom (next prompt)** at
its **Theme** prompt, which is the default. Picking Olivero, Claro or Stark
removes the scaffold, and most of this page then doesn't apply.

The installer renames `your_site_theme` to the name you enter at the
**Custom theme machine name** prompt. That name defaults to the site's
machine name. Custom modules use a shorter module prefix, such as `ys_` for
`your_site`. The theme extends the core Olivero theme.

Front-end theming often follows project and team preferences. The scaffold
shows how a custom theme _integrates_ with the **Vortex** tooling and
automations. Adapt it, or replace it with a theme of your own.

## Build system

The theme builds its assets with `npm` scripts that call
[Sass](https://sass-lang.com/), [PostCSS](https://postcss.org/) with
Autoprefixer, [Terser](https://terser.org/) and
[chokidar](https://github.com/open-cli-tools/chokidar-cli). The build system
covers the following:

- SCSS compilation
- JavaScript concatenation and minification
- CSS auto-prefixing for browser compatibility
- Linting for both CSS ([Stylelint](https://stylelint.io/)) and JavaScript
  ([ESLint](https://eslint.org/))
- Watch mode for development
- Copying of `images/` and `fonts/` into `build/`

The production build compresses the CSS. Terser minifies the concatenated
JavaScript and strips its `console` calls. The development build skips
minification and writes source maps instead. Autoprefixer targets the
browsers in the `browserslist` key of `package.json`. `npm ci` applies any
patches in `patches/` through `patch-package`.

The CLI container image runs `npm ci` and `npm run build` for the theme
during the image build, so the image carries compiled assets. To build the
assets on the host or during deployment instead, set
`VORTEX_FRONTEND_BUILD_SKIP=1` in `.env`, which ships with `0`.
`docker-compose.yml` passes the variable to the image as a build argument,
so the change applies on the next image build, for example on `ahoy build`.

### Build commands

To run the theme's npm scripts, open a shell in the CLI container with
`ahoy cli`, then run them from the theme directory:

```shell
cd web/themes/custom/your_site_theme

# Install dependencies
npm ci

# Build production assets
npm run build

# Build development assets (unminified)
npm run build-dev

# Run linting
npm run lint

# Auto-fix linting issues
npm run lint-fix

# Watch for changes during development
npm run watch
```

From the host, the Ahoy commands run the same npm scripts in the theme
directory:

```shell
# Install front-end dependencies
ahoy fei

# Build production assets
ahoy fe

# Build development assets (unminified)
ahoy fed

# Watch for changes during development
ahoy few

# Lint front-end code
ahoy lint-fe

# Fix front-end lint issues
ahoy lint-fe-fix
```

Both sets of commands run inside the container, so every development
environment uses the same Node.js and tools. 3 of the Ahoy commands also
reach beyond the theme:

- `ahoy fei` also installs the npm dependencies of the project root.
- `ahoy lint-fe` and `ahoy lint-fe-fix` also run Twig CS Fixer and the root
  `lint` or `lint-fix` script, which covers the custom modules.

To replace the scaffold with your own theme, keep the npm script names in
its `package.json`: `build`, `build-dev`, `watch`, `lint` and `lint-fix`.
The Ahoy commands, the CLI image build and the CI lint step call those
scripts in the theme that `DRUPAL_THEME` names. `.env` sets `DRUPAL_THEME`
and `DRUPAL_MAINTENANCE_THEME`, and the installer writes your theme's name
into both. Point both variables at the new theme.

Neither variable sets Drupal's default theme. The
`ys_base_deploy_install_active_theme()` deploy hook in `ys_base.deploy.php`
does that. It installs Olivero and the theme named in the hook, then makes
that theme the default. The installer writes your theme's machine name into
the hook.

Provisioning runs deploy hooks with `drush deploy:hook`, which runs each
hook once per site. To make a new theme the default:

1. In `ys_base_deploy_install_active_theme()`, change the theme machine
   name, so fresh installs pick up the new theme.
2. Add a deploy hook to `ys_base.deploy.php` that installs the new theme and
   sets it as the default. This hook covers sites where the first hook
   already ran.

## File structure

The following tree shows the main directories and files. It leaves out
build outputs, static assets and the configuration and lock files:

```text
your_site_theme/
├── .storybook/                    # Storybook configuration
│   ├── main.mjs                   # Story sources and framework
│   └── preview.js                 # Story render endpoint
├── components/                    # Single Directory Components (SDC)
│   └── button/                    # Sample button component
│       ├── button.component.yml   # Component schema (props and slots)
│       ├── button.twig            # Component template
│       ├── button.stories.twig    # Component stories
│       └── button.css             # Component styles
├── scss/                          # Sass source files
│   ├── _variables.scss            # Theme variables
│   ├── _mixins.scss               # Sass mixins
│   ├── _fonts.scss                # Font definitions
│   ├── _rem.scss                  # REM unit utilities
│   ├── styles.scss                # Main stylesheet
│   └── components/                # Component-specific styles
│       └── _header.scss           # Header component styles
├── js/                            # JavaScript source files
│   └── your_site_theme.js         # Main theme JavaScript
├── templates/                     # Twig template overrides
│   └── layout/
│       └── region--footer-bottom.html.twig  # Renders the button component
├── tests/                         # Theme tests
│   └── src/
│       ├── Unit/                  # Unit tests
│       ├── Kernel/                # Kernel tests
│       ├── Functional/            # Functional tests
│       └── FunctionalJavascript/  # Functional JavaScript tests
├── your_site_theme.info.yml       # Theme definition
├── your_site_theme.libraries.yml  # Asset libraries
├── your_site_theme.theme          # Theme functions
├── package.json                   # Node.js dependencies
└── logo.svg                       # Theme logo
```

## Libraries

The theme defines 1 asset library, `global-styling`, in
`your_site_theme.libraries.yml`. `your_site_theme.info.yml` attaches it to
every page. The library loads the compiled
`build/css/your_site_theme.min.css` and `build/js/your_site_theme.min.js`.
It depends on `core/jquery`, `core/drupal` and `core/drupalSettings`.

## Single Directory Components

The theme ships a sample [Single Directory
Component](https://www.drupal.org/docs/develop/theming-drupal/using-single-directory-components)
(SDC) in `components/button`.
`templates/layout/region--footer-bottom.html.twig` uses it to render a
"back to top" link whenever the footer region has content.

The button component takes the following props and slot:

- `label`: required, the visible text
- `url`: optional, turns the button into a link
- `modifier`: optional, a class suffix for variant styling
- `content`: a slot that replaces the label

`ahoy lint-sdc` exists when you select the SDC Devel module during
installation. To validate the components with
[SDC Devel](https://www.drupal.org/project/sdc_devel) on a provisioned site,
run the following command:

```shell
ahoy lint-sdc
```

The command fails when the validator reports critical issues, errors or
warnings.

➡️ See [SDC Devel](code-quality/sdc-devel.mdx) for how the validator is set
up and where it runs.

## Storybook

[Storybook](https://storybook.js.org/) documents the theme's components.
Drupal renders every story through the
[Storybook module](https://www.drupal.org/project/storybook), so the library
shows the same markup the site renders.

To turn Storybook on, answer **Yes** at the installer's
**Storybook component library?** prompt. The installer asks only when you
pick the custom theme, and the default answer is **No**. To add Storybook
to a project installed without it, run `ahoy update-vortex --interactive`
and answer **Yes** at that prompt. That run also updates the rest of the
project's **Vortex** files, as [Updating Vortex](../updating-vortex.mdx)
describes.

You write stories in Twig next to the component they document, as
`<component>.stories.twig`. Drush compiles them into
`<component>.stories.json` with `drush storybook:generate-all-stories`. The
root `.gitignore` keeps the compiled files out of Git.

### Working with Storybook

The Storybook commands run inside the CLI container and use the theme
dependencies installed there. The following 2 commands start the
development server and rebuild the library:

```shell
# Develop components: regenerate stories as they change and serve them live
ahoy storybook

# Refresh the component library served at /storybook
ahoy storybook-build
```

`ahoy storybook` first stops any server or watcher left from an earlier
session. It then generates the stories and starts a development server.
When the server is ready, the command prints its address, such as
`Storybook is ready at http://localhost:55197`.

The command keeps running until you press <kbd>Ctrl+C</kbd>. While it runs,
it regenerates the stories whenever a `*.stories.twig` file changes, so new
and edited stories appear without a restart. Docker assigns the host port
when the container starts, and `ahoy info` shows it next to the library
address.

A third command, `ahoy storybook-stories`, only generates the stories. Add
`--watch` to keep regenerating them as the Twig story templates change.

The development server runs on its own origin. In the `local`, `ci` and
`dev` environments, `services.storybook.yml` shares story renders with
`localhost` and `127.0.0.1` origins on any port. In those environments, it
replaces the `cors.config` from `services.yml`. If your site already shares
responses with other origins, list them in `services.storybook.yml` too.

The component library at `/storybook` is a static copy built during
provisioning. The build fixes the list of stories and their arguments.
Drupal renders each story's markup when you open it. After you add, remove
or rename a story, or change its arguments, run `ahoy storybook-build` to
update `/storybook`. The development server picks up those changes on its
own.

In the `local` environment, provisioning turns on Twig development mode. An
edit to a component template then shows up in the development server and in
`/storybook` on the next render. It needs no cache rebuild and no library
build.

### Customizing locations

The `ahoy` commands and provisioning run `vendor/bin/vortex-storybook`,
which reads its locations from environment variables. To move the theme or
its stories, set the following variables in `.env`:

- `VORTEX_STORYBOOK_DIR`: the directory with the Storybook configuration and
  its npm scripts
- `VORTEX_STORYBOOK_STORIES_PATTERN`: the Twig story templates to watch
- `VORTEX_STORYBOOK_DEV_SCRIPT`: the npm script that starts the development
  server
- `VORTEX_STORYBOOK_BUILD_SCRIPT`: the npm script that builds the library
- `VORTEX_STORYBOOK_PORT`: the development server port inside the container
- `STORYBOOK_SERVER_URL`: the site that renders stories for the development
  server, by default the first URL in `LOCALDEV_URL`
- `VORTEX_STORYBOOK_BUILD_SERVER_URL`: the site that renders stories for the
  static library, when that site isn't the one serving the library
- `VORTEX_STORYBOOK_LIBRARY_PATH`: the path in the library address that the
  build prints

The [variables reference](variables.mdx) lists their defaults.

The web server reads none of these variables.
`.docker/config/nginx/storybook.conf` hardcodes the `/storybook` path and
the theme's `storybook-static` directory. On Lagoon, the `storybook` volume
path in `docker-compose.yml` is hardcoded too. To move either location,
edit those files as well.

### Running Storybook on the host

The theme's `node_modules` directory is shared with the CLI container, so it
holds dependencies installed for the container's architecture. To run
Storybook on the host, reinstall the dependencies there and keep the stories
regenerating in the container. Point the development server at the site's
local URL, which `ahoy info` shows:

```shell
cd web/themes/custom/your_site_theme
rm -rf node_modules && npm ci

# In a second terminal: regenerate the stories as they change
ahoy storybook-stories --watch

STORYBOOK_SERVER_URL=http://your-site.docker.amazee.io npm run storybook
```

Confirm that the development server answers at `http://localhost:6006`.
Before you use the `ahoy` front-end commands again, run `ahoy fei` to
reinstall the container's own dependencies.

### Published component library

Provisioning installs the Storybook module with the other development
modules. It then generates the stories and builds the static application
into the theme's `storybook-static` directory. The web server serves that
directory at `/storybook`.

The build runs only in the `local`, `ci` and `dev` environments, where the
story render route is reachable. It's also skipped when the theme's
dependencies aren't installed. To skip the build and shorten provisioning,
set `DRUPAL_STORYBOOK_SKIP=1`. Then run `ahoy storybook-build` when you need
the library.

In the `dev` environment, [Shield](modules/contributed-modules.mdx#shield)
protects the story render route, so a story renders only after the browser
has the Shield credentials. The web server serves the static application at
`/storybook` and its story index directly, so Shield doesn't protect them.

On Lagoon, the CLI and web containers run in separate pods. A dedicated
persistent `storybook` volume shares the `storybook-static` directory
between them. Acquia deployment artifacts carry no theme dependencies, so
the application isn't built on Acquia.

## Tests scaffold

The `tests` directory holds a working example test for each test type, to
start your own from: unit, kernel, functional and functional JavaScript.
PHPUnit picks them up through the matching test suites in `phpunit.xml`.

Each test type also has a base class that pulls in the following helper
traits from the `ys_base` module's tests:

- `ArrayTrait`
- `AssertTrait`
- `MockTrait`
- `ReflectionTrait`
- `BrowserHtmlDebugTrait`, in the functional JavaScript base class only

Remove the parts of the scaffold you don't need.
