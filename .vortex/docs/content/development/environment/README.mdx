# Environment

Your local environment is a Docker Compose stack built from [Lagoon
container images](https://github.com/uselagoon/lagoon-images), the images
Lagoon runs in production. Ahoy wraps the longer `docker compose` commands
into short ones.

This section is for developers working day to day on a project built from
**Vortex**. After reading this page, you can do the following:

- Tell which files Git, the image build and the deployment artifact leave
  out
- Switch branches without a full rebuild
- Reset the project to a clean state
- Change an environment variable and get the new value into the containers

## Ignored files

**Vortex** writes its 3 ignore files as deny lists. Every file is included
by default, and each ignore file lists only what must stay out of its
target. This follows the "avoid silent errors" principle: a file you add is
visible by default. With an allow list, a new file would stay excluded
until someone remembered to allow it.

The `.gitignore` file controls which paths Git ignores in the project
repository. It excludes the following:

- Directories that Composer and npm generate, such as `web/core`,
  `web/modules/contrib`, `vendor` and `node_modules`
- The Drupal scaffold files that the build copies into `web/`
- Compiled theme assets in `web/themes/**/build`
- With Storybook, the generated `*.stories.json` files and the
  `storybook-static` output
- Local overrides: `.env.local`, `.ahoy.local.yml`,
  `docker-compose.override.yml`, `settings.local.php` and
  `services.local.yml`
- Content files and test artifacts in `web/sites/*/files` and
  `web/sites/simpletest`
- Caches, data, logs and temporary artifacts in `.artifacts`, `.data`,
  `.logs`, `.phpunit.cache` and `.twig-cs-fixer.cache`

`.gitignore` keeps 2 sections as small allow lists, because a deny rule
can't express them:

- `recipes/` - Composer installs contributed recipes next to your custom
  ones, so each custom recipe is un-ignored explicitly.
- `.claude/` - Claude writes machine-local state here, so only
  `.claude/settings.json` and `.claude/skills/` are un-ignored by default.
  This section is present when the installer adds the AI agent instructions.

The other 2 ignore files apply the same deny-list model to different
targets:

- `.dockerignore` controls the container image build context. ➡️ See [Build
  context and `.dockerignore`](docker.mdx#build-context-and-dockerignore)
- `.gitignore.artifact` controls the deployment artifact. ➡️ See
  [Deployment >
  Artifact](../../deployment/artifact.mdx#artifact-file-control)

A new file or directory that no entry matches reaches all 3 targets. Git
tracks it after you commit it, and the image build and the deployment
artifact include it. Add an entry to an ignore file only when a file must
stay out of that target.

## Switching branches

After you switch branches, skip the full rebuild. Run only the commands
that match what changed:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    # Update Composer packages (only if composer.json/composer.lock changed)
    ahoy composer install
    # Rebuild frontend assets (only if theme files changed)
    ahoy fe
    # Provision site (only if database or configuration changes expected)
    ahoy provision
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    # Update Composer packages (only if composer.json/composer.lock changed)
    docker compose exec cli composer install
    # Rebuild frontend assets (only if theme files changed)
    docker compose exec cli bash -c \
      "cd \${WEBROOT}/themes/custom/\${DRUPAL_THEME} && npm run build"
    # Provision site (only if database or configuration changes expected)
    docker compose exec cli ./vendor/bin/vortex-provision
    ```
  </TabItem>
</Tabs>

If the branch changes `docker-compose.yml` or a file in `.docker/`, rebuild
the images and recreate the containers. Run `ahoy up --build`, or
`docker compose up -d --build` without Ahoy.

Confirm that the stack is healthy: `ahoy doctor` ends with
`[ OK ] All required checks have passed.`

## Resetting

`ahoy reset` takes the stack down and deletes what the build installed, so
your next `ahoy build` starts clean. After you confirm, it runs `ahoy down`.
That removes the containers and their volumes, your local database
included. `ahoy reset` then deletes the following:

- `vendor`
- Every `node_modules` directory
- `web/core`
- The `contrib` directories in `web/modules`, `web/profiles` and
  `web/themes`

`ahoy reset --hard` also returns the repository to a freshly cloned state
at the current commit. After the soft reset, it runs these steps:

1. Deletes every untracked file that `.gitignore` matches.
2. Discards uncommitted changes to tracked files (`git reset --hard`).
3. Removes the remaining untracked files (`git clean -f -d`).
4. Removes empty directories.

The hard reset deletes your `.env.local`, the database dumps in `.data` and
every other local override. Copy out anything you want to keep first.

The following commands run each kind of reset:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    # Reset local environment
    ahoy reset
    # Fully reset repository to a state as if it was just cloned
    ahoy reset --hard
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    # Reset local environment
    docker compose down --remove-orphans --volumes
    ./vendor/bin/vortex-reset
    # Fully reset repository to a state as if it was just cloned
    docker compose down --remove-orphans --volumes
    ./vendor/bin/vortex-reset --hard
    ```
  </TabItem>
</Tabs>

Confirm that the reset finished: the last line it prints is
`[ OK ] Finished reset.`

## Environment variables

`.env` holds the values for the whole team, and `.env.local` holds the
values for your machine only. A value in `.env.local` overrides the one in
`.env`. A variable exported in your shell overrides both.

To change a variable that `docker-compose.yml` passes to the containers,
such as `DRUPAL_THEME`:

1. Set the new value in `.env.local` or in `.env`.
2. Recreate the containers. A plain restart keeps the old value:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy up
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose up -d
    ```
  </TabItem>
</Tabs>

`ahoy up` loads both files before it calls Docker Compose. Docker Compose on
its own reads only `.env`, so the Docker Compose command applies only
`.env` changes. To include `.env.local` without Ahoy, pass both files:
`docker compose --env-file .env --env-file .env.local up -d`.

Confirm that a container has the new value with
`docker compose exec cli printenv VARIABLE_NAME`. Replace `VARIABLE_NAME`
with the name of the variable you changed.

Drupal also reads variables that `docker-compose.yml` doesn't pass, such as
`DRUPAL_CLAMAV_ENABLED`. For web requests, PHP-FPM loads them from `.env`
when its container starts. It never reads `.env.local`. To apply a change
to `.env`, run `ahoy restart` or `docker compose restart`.
`ahoy up` recreates a container only when its configuration changes. These
variables aren't part of that configuration.

To set such a variable on your machine only, such as a credential that
must stay out of the committed `.env`:

1. Pass the variable to the `php` service in `docker-compose.override.yml`:

   ```yaml title="docker-compose.override.yml"
   services:
     php:
       environment:
         DRUPAL_EXAMPLE_API_KEY: ${DRUPAL_EXAMPLE_API_KEY:-}
   ```

2. Set its value in `.env.local`.
3. Run `ahoy up`.

The `vendor/bin/vortex-*` scripts read both files each time they start. A
variable that only those scripts use, such as
`VORTEX_PROVISION_OVERRIDE_DB`, takes effect without recreating anything.
The [Docker page](docker.mdx#container-environment-variables) explains how
each value reaches a container.

➡️ See [Variables](../variables.mdx) for the full variable reference.
