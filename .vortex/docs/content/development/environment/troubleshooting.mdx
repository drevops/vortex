# Troubleshooting

This page is for developers whose local stack misbehaves. It covers these
symptoms:

- A site that doesn't load
- Database connection errors
- Files in the project that end up owned by `root`

For failures in CI or on a hosting environment, see [Continuous
integration](../../continuous-integration/README.mdx) and
[Hosting](../../hosting/README.mdx) instead.

When the local environment misbehaves, run [Doctor](doctor.mdx) first. It
finds the broken layer before you start guessing: the tooling, the
containers or the site itself.

## Site not loading

A stopped Pygmy service, a stopped container or a web server that doesn't
answer keeps the site from loading. Doctor checks all 3. If Doctor reports
a stopped container, run `ahoy up` as it suggests, or `docker compose up -d`
without Ahoy. Either command starts the container and keeps your database.

If the site still doesn't load, restart the whole stack with the following
commands:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    # Check for common issues
    ahoy doctor
    # Restart containers
    ahoy down && ahoy up
    # Verify URLs and ports
    ahoy info
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    # Check for common issues
    ./vendor/bin/vortex-doctor
    # Restart containers
    docker compose down && docker compose up -d
    # Verify URLs and ports
    docker compose exec cli ./vendor/bin/vortex-info
    ```
  </TabItem>
</Tabs>

After either `down` command, the stack comes back with a fresh database.
That's why `ahoy down` asks you to confirm first. The database lives on an
anonymous volume. Plain `docker compose down` leaves that volume on disk,
but the next `up` doesn't mount it again.

Provision the site again with `ahoy provision`. Without Ahoy, run
`docker compose exec cli ./vendor/bin/vortex-provision`.

Confirm that the site is back: `ahoy doctor` ends with
`[ OK ] All required checks have passed.`, and the URL that `ahoy info`
prints loads the site.

## Database connection errors

Drupal can't connect to the database when the `database` container has
stopped or keeps restarting. Check the container first, and rebuild only as
a last resort:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    docker compose ps      # Check if the database container is running
    ahoy build             # Last resort: rebuild everything
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose ps      # Check if the database container is running
    docker compose down --volumes && docker compose up -d  # Last resort
    ```
  </TabItem>
</Tabs>

If `docker compose ps` shows the `database` container stopped or
restarting, read its log. Run `ahoy logs database`, or
`docker compose logs database` without Ahoy. The log usually says why the
container stopped.

Both last resorts wipe the local database. `ahoy build` provisions the site
again. After the Docker Compose commands, provision the site yourself with
`docker compose exec cli ./vendor/bin/vortex-provision`.

Confirm that `docker compose ps` shows the `database` container with a
status that starts with `Up`.

## Permission issues

The `cli` container runs as `root`. On Linux, files it creates in the
project can end up owned by `root` on your machine, such as a freshly
installed `vendor` directory. See [Default user](docker.mdx#default-user).

To take ownership back, run the following command:

```shell
# Fix file permissions (Linux/Mac)
sudo chown -R $USER:$USER .
```

Confirm that `ls -ld vendor` lists your user as the owner.
