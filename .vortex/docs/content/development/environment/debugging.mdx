# Debugging

When the logs don't explain a problem, these 3 tools get you closer:
step-debugging PHP with Xdebug, requesting authenticated pages with curl,
and inspecting the containers directly.

## Xdebug

https://xdebug.org/

> Xdebug is an extension for PHP, and provides a range of features to
> improve the PHP development experience.

**Vortex** comes with Xdebug pre-installed and configured for local
development thanks to [Lagoon
images](https://github.com/uselagoon/lagoon-images).

Code coverage doesn't need Xdebug. The CLI image also installs PCOV, a
coverage-only PHP extension, and PHPUnit collects coverage through PCOV
whenever it's loaded, so tests report coverage with Xdebug turned off.

➡️ See [PHPUnit](../testing/phpunit.mdx)

### Usage

Xdebug is off by default. `ahoy debug` turns it on by recreating the `cli`,
`php`, and `nginx` containers with `XDEBUG_ENABLE=true`. If Xdebug is
already on, it says so and changes nothing:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy debug    # Restart containers with Xdebug enabled.
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    # Restart containers with Xdebug enabled.
    XDEBUG_ENABLE=true docker compose up -d cli php nginx
    ```
  </TabItem>
</Tabs>

To turn it off, recreate the containers without the variable:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy up   # Restart containers with Xdebug disabled.
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    # Restart containers with Xdebug disabled.
    docker compose up -d cli php nginx
    ```
  </TabItem>
</Tabs>

`ahoy info` shows whether Xdebug is on at the moment.

### CLI

Step-debugging a command-line PHP script works the same way as debugging a
web page, as long as the script runs inside the `cli` container.

Drush is the exception you're most likely to hit. Its shell wrapper,
`vendor/bin/drush`, sets `XDEBUG_MODE=off` before it starts PHP, for
performance, unless you pass `--xdebug`: run `ahoy drush --xdebug <command>`
to keep Xdebug on.

Other command-line tools may switch Xdebug off in their own way, so check
their documentation if a breakpoint never fires.

### IDE configuration

#### PhpStorm

By default, PhpStorm interrupts on incoming debug connections it can't map
to a project, as long as the `Start listening for PHP Debug Connections`
button (the one with a little bug) is on. It then asks you to map the
incoming connection to a project.

To use Xdebug on the project for the first time, starting from a fully
working site, follow these steps:

1. Install the Xdebug helper extension for your browser:
     - [Chrome Xdebug Helper by
       JetBrains](https://chromewebstore.google.com/detail/xdebug-helper-by-jetbrain/aoelhdemabeimdhedkidlnbkfhnhgnhm)
       extension.
     - [Firefox Xdebug Helper by
       JetBrains](https://addons.mozilla.org/en-US/firefox/addon/xdebug-helper-by-jetbrains/)
       extension.
     - [Edge Xdebug Helper by
       JetBrains](https://microsoftedge.microsoft.com/addons/detail/xdebug-helper-by-jetbrain/kddfioocjgjmmambaijldfbpiaecmoco)
       add-on.

2. Enable Xdebug in your browser (see instructions for your
   extension/add-on).
3. Set a breakpoint in your IDE. `index.php` in your web root is a good
   place to start.
4. Run `ahoy debug` or
   `XDEBUG_ENABLE=true docker compose up -d cli php nginx` to enable Xdebug.
5. Refresh the page in your browser.
6. PhpStorm stops on your breakpoint and asks you to map the incoming
   connection to a directory in your project. It asks because the code runs
   in the container, which counts as a remote server, so PhpStorm needs to
   know which local directory matches `/app` in the container. You set the
   mapping once, and PhpStorm remembers it.

![PhpStorm server settings with the path mapping to the project root within
the container](/img/xdebug-phpstorm.png)

For more detail, see:

- https://www.jetbrains.com/help/phpstorm/configuring-xdebug.html#debugging-with-phpstorm
- https://docs.lagoon.sh/using-lagoon-advanced/setting-up-xdebug-with-lagoon/

#### Tips and tricks

Once your first Xdebug session works, a few changes to PhpStorm's Debug
settings make everyday debugging smoother:

- Disable the following options:
  - `Break at first line in PHP scripts`
  - `Force break at first line when no path mapping specified`
  - `Force break at first line when a script is outside the project`
- Increase `Max. simultaneous connections` to `5` or more, so a debug
  session can't get stuck without showing up in the IDE.

## Testing authenticated pages with curl

Use `curl` with session cookies to request pages that need a login, such as
admin pages and protected routes, without opening a browser. It's a tool for
ad-hoc debugging; automated tests belong in Behat or PHPUnit.

### When to use

- Quick ad-hoc debugging of admin page errors (500 errors, permission
  issues)
- Investigating issues without spinning up a browser
- Verifying page content during troubleshooting
- One-off checks that don't warrant a formal test

### Step-by-step process

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    # Step 1: Get the site URL from project info
    ahoy info
    # Note the URL (e.g., http://your-project.docker.amazee.io)
    # Step 2: Get a one-time login URL
    ahoy login
    # Output example:
    # http://your-project.docker.amazee.io/user/reset/1/1234567890/abc123/login
    # Step 3: Authenticate and save session cookies
    # Replace LOGIN_URL with the full URL from Step 2
    curl -k -c .data/cookies.txt -L "LOGIN_URL"
    # Step 4: Access any authenticated page using saved cookies
    # Replace SITE_URL with your site URL from Step 1
    curl -k -b .data/cookies.txt "SITE_URL/admin/content"
    # Step 5: Check for specific errors in page output
    curl -k -b .data/cookies.txt "SITE_URL/admin/content" \
      | grep -iE "(error|exception|warning|notice)"
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    # Step 1: Get the site URL from project info
    docker compose exec cli ./vendor/bin/vortex-info
    # Note the URL (e.g., http://your-project.docker.amazee.io)
    # Step 2: Get a one-time login URL
    docker compose exec cli drush uli
    # Output example:
    # http://your-project.docker.amazee.io/user/reset/1/1234567890/abc123/login
    # Step 3: Authenticate and save session cookies
    # Replace LOGIN_URL with the full URL from Step 2
    curl -k -c .data/cookies.txt -L "LOGIN_URL"
    # Step 4: Access any authenticated page using saved cookies
    # Replace SITE_URL with your site URL from Step 1
    curl -k -b .data/cookies.txt "SITE_URL/admin/content"
    # Step 5: Check for specific errors in page output
    curl -k -b .data/cookies.txt "SITE_URL/admin/content" \
      | grep -iE "(error|exception|warning|notice)"
    ```
  </TabItem>
</Tabs>

### Curl flags reference

| Flag | Purpose |
|------|---------|
| `-k` | Ignore SSL certificate errors (required for self-signed local certs) |
| `-c FILE` | Save cookies to FILE after request |
| `-b FILE` | Send cookies from FILE with request |
| `-L` | Follow redirects (required for login flow) |

### Important notes

- Store cookies in the `.data/` directory: Git ignores it, so a session
  cookie doesn't end up in a commit.
- Cookies expire after the session timeout, so regenerate them as needed.
- Login URLs have the format
  `http://SITE/user/reset/UID/TIMESTAMP/HASH/login`.
- Login URLs from `ahoy login` can only be used once. `ahoy login` also
  unblocks user 1 before it generates the link, which a plain `drush uli`
  doesn't.

## Container debugging

To see what a container is doing, or to open a shell or a database prompt
inside it:

```shell
# Check container status
docker compose ps

# View container logs
docker compose logs [service_name]
# Examples:
docker compose logs cli
docker compose logs database

# Access container shell
docker compose exec cli bash
docker compose exec database mysql -u drupal -p drupal
```

The database name, user, and password are all `drupal` in the local stack,
so enter `drupal` when `mysql` asks for the password.
