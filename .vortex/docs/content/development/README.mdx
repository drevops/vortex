# Development

import AsciinemaPlayer from '@site/src/components/AsciinemaPlayer';

This section covers the day-to-day work on a **Vortex** project. That means
running the local environment, managing the database and dependencies,
working with the Drupal application, and checking your code with linters and
tests.

Each page covers 1 task or tool and everything about it: daily usage,
configuration, and how it behaves in the continuous integration pipeline.
Bigger topics get a subsection, with an overview page that ties its pages
together. This page walks through the overall process and points you to the
right page for each task.

## Typical development process

1. Pull the latest changes from the remote repository.
2. [Fetch the latest database dump](provision.mdx#database) from the
   production environment.
3. [Build the project](environment/README.mdx).
4. Start a new feature or bugfix branch:
    - Create a new branch from `develop` (see
      [Releasing > GitFlow](../releasing/gitflow.mdx) for the branch
      structure).
    - Implement the feature or fix the bug.
5. [Run tests](testing/README.mdx):
    - Run automated tests locally.
    - Fix any failing tests.
6. [Run code quality checks](code-quality/README.mdx):
    - Run static code analysis locally.
    - Fix any issues reported.
7. Commit changes to the branch and push it to the remote repository.
8. Create a pull request:
    - Create a pull request from the branch to `develop`.
    - Assign reviewers.
    - Wait for the [continuous integration
      pipeline](../continuous-integration/README.mdx) to pass.

## Common commands

Each video is a live recording, captured on a demo consumer project that
uses **Vortex**.

### Build the project

`ahoy build` rebuilds the project from scratch. Once you confirm, it removes
the containers, the installed dependencies, and the database, then builds
and starts fresh containers. It installs the Composer and front-end
dependencies, compiles the custom theme's assets, and provisions the site.
It finishes by printing the project information with a one-time login link.

### Show project information

`ahoy info` prints what you need to reach the running project: the site URL,
the database credentials and host port, and the mail catcher and Selenium
VNC addresses. The VNC address lets you watch the browser tests run. It also
shows whether Xdebug is on, plus the Solr and Storybook addresses when your
project uses them.

### Run linters

`ahoy lint` runs the back-end linters (PHPCS, PHPStan, and Rector), the
front-end linters (Twig CS Fixer, ESLint, and Stylelint), and Gherkin Lint
for the Behat feature files. `ahoy lint-fix` applies the automatic fixes
that Rector, PHPCBF, Twig CS Fixer, ESLint, and Stylelint support.

SDC Devel validates the custom theme's components against a provisioned
site, so it runs separately as `ahoy lint-sdc`. DCLint and Hadolint have no
Ahoy command: continuous integration runs them from their Docker images.

### Run unit, kernel, and functional tests

`ahoy test` runs every PHPUnit suite: unit, kernel, functional, and
functional JavaScript. To run 1 suite, use `ahoy test-unit`,
`ahoy test-kernel`, `ahoy test-functional`, or
`ahoy test-functional-javascript`.

`ahoy test-bdd` runs the Behat tests against the provisioned site. Scenarios
tagged `@javascript` drive a real browser in the `chrome` container, and the

### Re-provision the site

`ahoy provision` runs provisioning again in the running stack. When
`VORTEX_PROVISION_OVERRIDE_DB` is `1`, as `.env.local.example` sets it for
local work, it replaces the current database with the dump from
`.data/db.sql`. Otherwise, an existing site keeps its database. Either way,
it then runs the provisioning steps, from the database updates and the
configuration import to the deploy hooks and your custom
`scripts/provision-*.sh` scripts. It finishes with a one-time login link.
