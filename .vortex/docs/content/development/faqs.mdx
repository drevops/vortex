## How to connect to the database?

<!-- markdownlint-disable MD046 -->
<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    On macOS with [Sequel Ace](https://sequel-ace.com/) installed, open the
    database in it:

    ```shell
    ahoy db
    ```

    Otherwise:

    1. Run `ahoy info` and grab the DB host port number.
    2. Use the connection details below.
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    1. Run `docker compose port database 3306` to get the host port, or
       find the database port mapping in `docker compose ps`.
    2. Use the connection details below.
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

Connection details:

- Host: `127.0.0.1`
- Username: `drupal`
- Password: `drupal`
- Database: `drupal`
- Port: the port from the preceding step

➡️ See [Environment > Docker](environment/docker.mdx)

## How to use Xdebug?

<!-- markdownlint-disable MD046 -->

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    1. Run `ahoy debug`.
    2. Turn on listening for incoming debug connections in your IDE.
    3. If your IDE asks for a server URL, give it the URL as it appears in
       the browser.
    4. Turn on the Xdebug flag in the requests from your browser, with one
       of the extensions or by adding `?XDEBUG_SESSION_START=1` to the URL.
    5. Set a breakpoint in your IDE and load the page in your browser.

    Use the same commands to debug CLI scripts.

    To turn Xdebug off, run `ahoy up`.
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    1. Run `XDEBUG_ENABLE=true docker compose up -d cli php nginx`.
    2. Turn on listening for incoming debug connections in your IDE.
    3. If your IDE asks for a server URL, give it the URL as it appears in
       the browser.
    4. Turn on the Xdebug flag in the requests from your browser, with one
       of the extensions or by adding `?XDEBUG_SESSION_START=1` to the URL.
    5. Set a breakpoint in your IDE and load the page in your browser.

    Use the same commands to debug CLI scripts.

    To turn Xdebug off, run `docker compose up -d cli php nginx`.
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

➡️ See [Environment > Debugging](environment/debugging.mdx)

## How to use Xdebug with Behat?

<!-- markdownlint-disable MD046 -->

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    1. Enable debugging: `ahoy debug`
    2. Enter CLI container: `ahoy cli`
    3. Run Behat tests:

    ```shell
    vendor/bin/behat --xdebug path/to/test.feature
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    1. Enable debugging:
       `XDEBUG_ENABLE=true docker compose up -d cli php nginx`
    2. Enter CLI container: `docker compose exec cli bash`
    3. Run Behat tests:

    ```shell
    vendor/bin/behat --xdebug path/to/test.feature
    ```
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

Behat restarts itself without Xdebug unless you pass `--xdebug` or a debug
session is already active.

➡️ See [Environment > Debugging](environment/debugging.mdx) and [Testing >

## What should I do to switch to a "clean" branch environment?

If your stack is already running:

<!-- markdownlint-disable MD046 -->

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    1. Switch to your branch.
    2. `ahoy composer install`
    3. `ahoy fe`, if the branch changes theme files.
    4. `ahoy provision`

    You don't need to rebuild the full stack with `ahoy build` every time
    you switch branches. `ahoy provision` updates the environment to match
    the current branch, applying its database updates and configuration.

    When you need a fully clean environment, use `ahoy build`.
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    1. Switch to your branch.
    2. `docker compose exec cli composer install`
    3. Rebuild the theme assets with `npm run build` in the theme directory
       inside the CLI container, if the branch changes theme files.
    4. `docker compose exec cli ./vendor/bin/vortex-provision`

    You don't need to rebuild the full stack every time you switch branches.
    The provision script updates the environment to match the current
    branch.

    When you need a fully clean environment, run:

    ```shell
    docker compose down
    ./vendor/bin/vortex-reset
    docker compose up -d --build --force-recreate
    docker compose exec cli composer install
    docker compose exec cli ./vendor/bin/vortex-provision
    ```
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

➡️ See [Environment > Switching
branches](environment/README.mdx#switching-branches)

## How to import a database without running updates?

The import drops the current database and loads the dump without running
database updates or importing configuration. If your stack is already
running:

<!-- markdownlint-disable MD046 -->

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    Import from the default dump file at `.data/db.sql`:

    ```shell
    ahoy import-db
    ```

    Import from a specific dump file:

    ```shell
    ahoy import-db .data/db_custom.sql
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    Import from the default dump file at `.data/db.sql`:

    ```shell
    docker compose exec cli ./vendor/bin/vortex-import-db
    ```

    Import from a specific dump file:

    ```shell
    docker compose exec cli ./vendor/bin/vortex-import-db .data/db_custom.sql
    ```
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

➡️ See [Provision > Database](provision.mdx#database)

## How to add patches for Drupal modules?

1. Add the patch to `extra.patches` in `composer.json`, under the package's
   name, with the patch description as the key and the patch URL or local
   path as the value:

   ```json
   "extra": {
       "patches": {
           "drupal/somepackage": {
               "Remote patch description": "https://www.drupal.org/files/issues/issue.patch",
               "Local patch description": "patches/package-description.patch"
           }
       }
   }
   ```

2. Regenerate the patches lock file, re-apply the patches, and update
   `composer.lock`:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer patches-relock
    ahoy composer patches-repatch
    ahoy composer update --lock
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer patches-relock
    docker compose exec cli composer patches-repatch
    docker compose exec cli composer update --lock
    ```
  </TabItem>
</Tabs>

➡️ See [Composer > Patching](composer.mdx#patching) for the full patching
workflow, including removing patches.

## What should I do when `composer audit` reports a security vulnerability?

**Vortex** doesn't let security advisories block installation by default, so
`composer install` and `composer update` keep working. `composer audit`
reports the advisories instead, both when you run it locally and in the CI
security audit workflow. When it reports one:

1. Try updating the affected package to a newer version that resolves the
   advisory: `composer update vendor/package-name`.
2. Run `composer audit` to review the advisory details and assess whether it
   affects your project.
3. If no fixed version exists yet, or the vulnerability doesn't affect your
   use case, add the advisory to the `config.policy.advisories.ignore-id`
   list in `composer.json` with a documented reason.
4. To let CI pass while you address the advisory, set
   `VORTEX_CI_COMPOSER_AUDIT_IGNORE_FAILURE` to `1`.

➡️ See [Security > Dependency audit](security/dependency-audit.mdx) for the
full `config.policy` reference and guidance on choosing the right settings
for your project.

## What should I do when `npm audit` reports a security vulnerability?

The CI security audit workflow runs `npm audit` through `audit-ci` against
the root and the custom theme's dependency trees, and fails on advisories
rated `high` or higher. When it reports one:

1. Try updating the affected package to a newer version that resolves the
   advisory: `npm update <package-name>`.
2. Run `npm audit` to review the advisory details, including which direct
   dependency pulls the affected package in, and assess whether it affects
   your project.
3. When the affected package isn't a direct dependency, pin a patched
   version of it with an `overrides` entry in `package.json`, then run
   `npm install`.
4. If no fixed version exists or the vulnerability doesn't affect you, add
   it to the `allowlist` in `audit-ci.jsonc` with notes and an expiry date.
5. To let CI pass while you address the advisory, set
   `VORTEX_CI_NPM_AUDIT_IGNORE_FAILURE` to `1`.

➡️ See [Security > Dependency
audit](security/dependency-audit.mdx#javascript-dependencies) for the
severity threshold, the `overrides` mechanism, and the allowlist format.

## How to set a custom maintenance theme?

To set a custom theme for Drupal's maintenance mode (when the site is
offline for updates), set the `DRUPAL_MAINTENANCE_THEME` environment
variable:

```shell
# In .env file
DRUPAL_MAINTENANCE_THEME=my_custom_theme
```

Drupal uses this theme while the site is in maintenance mode. When
`DRUPAL_MAINTENANCE_THEME` isn't set, `settings.php` falls back to the value
of `DRUPAL_THEME`, and to Claro when neither is set.

Use a valid Drupal theme that's already installed and enabled on your site.

➡️ See [Environment > Environment
variables](environment/README.mdx#environment-variables)

## Behat tests with `@javascript` tag sometimes get stuck

A scenario tagged `@javascript` sometimes hangs for about 10 minutes and
then fails. The Chrome container gets stuck at random, for reasons nobody
has pinned down yet.

Restart the Chrome container with `docker compose restart chrome`, or with
`ahoy restart chrome`.

➡️ See [Testing > Behat](testing/behat.mdx)
