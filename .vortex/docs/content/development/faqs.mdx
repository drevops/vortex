# FAQs

import Tabs from '@theme/Tabs';
import TabItem from '@theme/TabItem';

This page answers the questions developers ask most often while they work
on a **Vortex** project. Each answer links to the page that covers its topic
in full.

## How do I list the available `ahoy` commands?

To list the commands with their descriptions, run the following command:

```shell
ahoy help
```

➡️ See [Environment > Ahoy](environment/ahoy.mdx)

## How do I pass CLI arguments to commands?

Add the arguments after the command name. The `--` separator is optional,
because Ahoy removes it before it runs the command:

```shell
ahoy mycommand -- myarg1 myarg2 --myoption1 --myoption2=myvalue
```

➡️ See [Environment > Ahoy](environment/ahoy.mdx)

## How do I clear the Drupal cache?

To rebuild the Drupal caches, run the following command:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy drush cr
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli drush cr
    ```
  </TabItem>
</Tabs>

➡️ See [Environment > Drush](environment/drush.mdx)

## How do I log in to a Drupal site?

To unblock user 1 and print a one-time login link for it, run the following
command:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy login
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    # Unblocks user 1 and generates a one-time login link, like
    # `ahoy login`.
    docker compose exec cli ./vendor/bin/vortex-login
    ```
  </TabItem>
</Tabs>

➡️ See [Environment > Drush](environment/drush.mdx)

## How do I connect to the database?

To connect, first get the port that the database uses on your host:

<!-- markdownlint-disable MD046 -->
<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    On macOS with [Sequel Ace](https://sequel-ace.com/) installed, open the
    database in it:

    ```shell
    ahoy db
    ```

    Otherwise, follow these steps:

    1. Run `ahoy info`, which prints the port as `DB port on host`.
    2. Use the following connection details.
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    1. Run `docker compose port database 3306` to get the host port, or
       find the database port mapping in `docker compose ps`.
    2. Use the following connection details.
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

Connect with these details:

- Host: `127.0.0.1`
- Username: `drupal`
- Password: `drupal`
- Database: `drupal`
- Port: the port from the preceding step

➡️ See [Environment > Docker](environment/docker.mdx)

## How do I use Xdebug?

Turn Xdebug on in the containers, then start a debug session from your IDE:

<!-- markdownlint-disable MD046 -->

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    1. Run `ahoy debug`. When the CLI container's `php -v` lists Xdebug,
       the command prints
       `Enabled debug configuration. Use 'ahoy up' to disable.` To check
       the state later, run `ahoy info`: its `Xdebug` line reads
       `Enabled ('ahoy up cli' to disable)` while Xdebug is on.
    2. Turn on listening for incoming debug connections in your IDE.
    3. If your IDE asks for a server URL, give it the URL as it appears in
       the browser.
    4. Turn on the Xdebug flag in the requests from your browser, with an
       Xdebug browser extension or by adding `?XDEBUG_SESSION_START=1` to
       the URL.
    5. Set a breakpoint in your IDE and load the page in your browser.

    Use the same commands to debug CLI scripts.

    To turn Xdebug off, run `ahoy up`. The `ahoy info` line suggests
    `ahoy up cli` instead, but that command recreates only the `cli`
    container, so web requests still run with Xdebug in the `php` container.
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    1. Run `XDEBUG_ENABLE=true docker compose up -d cli php nginx`. To
       check that Xdebug loaded, run `docker compose exec cli php -v` and
       look for Xdebug in its output.
    2. Turn on listening for incoming debug connections in your IDE.
    3. If your IDE asks for a server URL, give it the URL as it appears in
       the browser.
    4. Turn on the Xdebug flag in the requests from your browser, with an
       Xdebug browser extension or by adding `?XDEBUG_SESSION_START=1` to
       the URL.
    5. Set a breakpoint in your IDE and load the page in your browser.

    Use the same commands to debug CLI scripts.

    To turn Xdebug off, run `docker compose up -d cli php nginx`.
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

➡️ See [Environment > Debugging](environment/debugging.mdx)

## How do I use Xdebug with Behat?

Turn Xdebug on, then run Behat with the `--xdebug` flag inside the CLI
container:

<!-- markdownlint-disable MD046 -->

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    1. Enable debugging: `ahoy debug`
    2. Enter CLI container: `ahoy cli`
    3. Run Behat tests:
       `vendor/bin/behat --xdebug path/to/test.feature`
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    1. Enable debugging:
       `XDEBUG_ENABLE=true docker compose up -d cli php nginx`
    2. Enter CLI container: `docker compose exec cli bash`
    3. Run Behat tests:
       `vendor/bin/behat --xdebug path/to/test.feature`
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

Behat restarts itself without Xdebug unless you pass `--xdebug` or a debug
session is already active.

➡️ See [Environment > Debugging](environment/debugging.mdx) and [Testing >
Behat](testing/behat.mdx)

## What should I do to switch to a "clean" branch environment?

If your stack is already running, follow these steps:

<!-- markdownlint-disable MD046 -->

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    1. Switch to your branch.
    2. Run `ahoy composer install`.
    3. If the branch changes theme files, run `ahoy fe`.
    4. Run `ahoy provision`.

    `ahoy provision` brings the environment in line with the current branch
    by applying its database updates and configuration. Save `ahoy build`
    for when you need a fully clean environment.

    `ahoy provision` asks you to confirm first. It then keeps an existing
    site's database, because `.env` sets `VORTEX_PROVISION_OVERRIDE_DB` to
    `0`. `ahoy provision` replaces the database in the following cases:

    - `VORTEX_PROVISION_OVERRIDE_DB` is `1`, as `.env.local.example` sets
      it.
    - `VORTEX_DB_IMAGE` is set. `ahoy provision` then reloads the database
      container from that image first.

    To see which case applies to you, also check both variables in
    `.env.local`: a value there overrides the one in `.env`.
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    1. Switch to your branch.
    2. Run `docker compose exec cli composer install`.
    3. If the branch changes theme files, rebuild the theme assets with
       `npm run build` in the theme directory inside the CLI container.
    4. Run `docker compose exec cli ./vendor/bin/vortex-provision`.

    The provision script updates the environment to match the current
    branch. Like `ahoy provision`, it keeps an existing site's database by
    default, but it skips the confirmation and never reloads the database
    container.

    For a fully clean environment, run the following commands, which mirror
    the steps of `ahoy build`. `vortex-reset` deletes every `node_modules`
    directory, so the commands reinstall the frontend dependencies and
    rebuild the theme before they provision the site:

    ```shell
    docker compose down --remove-orphans --volumes
    ./vendor/bin/vortex-reset
    docker compose up -d --build --force-recreate
    docker compose exec cli composer install
    docker compose exec cli npm ci
    docker compose exec cli bash -c \
      "npm --prefix=\${WEBROOT}/themes/custom/\${DRUPAL_THEME} ci"
    docker compose exec cli bash -c \
      "cd \${WEBROOT}/themes/custom/\${DRUPAL_THEME} && npm run build"
    docker compose exec cli ./vendor/bin/vortex-provision
    ```
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

➡️ See [Environment > Switching
branches](environment/README.mdx#switch-branches)

## How do I import a database without running updates?

The import drops the current database and loads the dump without running
database updates or importing configuration. If your stack is already
running, pick the command for your dump file:

<!-- markdownlint-disable MD046 -->

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    Import from the default dump file at `.data/db.sql`:

    ```shell
    ahoy import-db
    ```

    Import from a specific dump file:

    ```shell
    ahoy import-db .data/db_custom.sql
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    Import from the default dump file at `.data/db.sql`:

    ```shell
    docker compose exec cli ./vendor/bin/vortex-import-db
    ```

    Import from a specific dump file:

    ```shell
    docker compose exec cli ./vendor/bin/vortex-import-db .data/db_custom.sql
    ```
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD046 -->

`ahoy import-db` asks you to confirm before it replaces the database.
Confirm that the output ends with `Finished database import.`

➡️ See [Provision > Database](provision.mdx#database)

## How do I add Drupal modules?

To add a module's code to the project, require it with Composer:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer require drupal/module_name
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer require drupal/module_name
    ```
  </TabItem>
</Tabs>

Then install the module with `drush pm:install` and export the
configuration with `drush config:export`, so the next configuration import
keeps the module installed.

➡️ See [Composer > Install dependencies](composer.mdx#install-dependencies)
and [Modules](modules/README.mdx)

## How do I add patches for Drupal modules?

To patch a module, follow these steps:

1. Add the patch to `extra.patches` in `composer.json`, under the package's
   name, with the patch description as the key and the patch URL or local
   path as the value:

   ```json
   "extra": {
       "patches": {
           "drupal/somepackage": {
               "Remote patch description": "https://www.drupal.org/files/issues/issue.patch",
               "Local patch description": "patches/package-description.patch"
           }
       }
   }
   ```

2. Regenerate the patches lock file, re-apply the patches and update
   `composer.lock`:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer patches-relock
    ahoy composer patches-repatch
    ahoy composer update --lock
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer patches-relock
    docker compose exec cli composer patches-repatch
    docker compose exec cli composer update --lock
    ```
  </TabItem>
</Tabs>

Confirm that the `patches-repatch` output has a `- Patching` line with the
name of the patched package.

➡️ See [Composer > Patch dependencies](composer.mdx#patch-dependencies) for
the full patching workflow, including removing patches.

## What should I do when `composer audit` reports a security vulnerability?

**Vortex** sets `config.policy.advisories.block` to `false` in
`composer.json`, so security advisories don't block `composer update`,
`composer require` or `composer remove`. `composer install` installs
exactly what the lock file pins, so advisories never block it.
`composer audit` reports the advisories instead, both when you run it
locally and in the CI security audit workflow. When it reports an
advisory, follow these steps:

1. Try updating the affected package to a newer version that resolves the
   advisory: `composer update vendor/package-name`.
2. Run `composer audit` to review the advisory details and assess whether it
   affects your project.
3. If no fixed version exists or the vulnerability doesn't affect you, add
   the advisory to the `config.policy.advisories.ignore-id` list in
   `composer.json`, with a documented reason.
4. Optional: To let CI pass while you address the advisory, set
   `VORTEX_CI_COMPOSER_AUDIT_IGNORE_FAILURE` to `1`. Set it as a repository
   variable on GitHub Actions or as an environment variable in the CircleCI
   project settings.

➡️ See [Security > Dependency audit](security/dependency-audit.mdx) for the
full `config.policy` reference and guidance on choosing the right settings
for your project.

## What should I do when `npm audit` reports a security vulnerability?

The CI security audit workflow runs `npm audit` through `audit-ci` against
the root and the custom theme's dependency trees, and fails on advisories
rated `high` or higher. The `Audit npm packages` step checks the root, and
`Audit npm packages of the theme` checks the theme in
`web/themes/custom/your_site_theme`. When a step reports an advisory,
follow these steps in the directory it checks:

1. Try updating the affected package to a newer version that resolves the
   advisory: `npm update <package-name>`.
2. Run `npm audit` to review the advisory details, including which direct
   dependency pulls the affected package in, and assess whether it affects
   your project.
3. When the affected package isn't a direct dependency, pin a patched
   version with an `overrides` entry in `package.json`, then run
   `npm install`.
4. If no fixed version exists or the vulnerability doesn't affect you, add
   the advisory to the `allowlist` in that directory's
   `package-audit.jsonc`, with notes and an expiry date. The root and theme
   files each apply only to their own tree.
5. Optional: To let CI pass while you address the advisory, set
   `VORTEX_CI_NPM_AUDIT_IGNORE_FAILURE` to `1`. Set it as a repository
   variable on GitHub Actions or as an environment variable in the CircleCI
   project settings.

➡️ See [Security > Dependency
audit](security/dependency-audit.mdx#javascript-dependencies) for the
severity threshold, the `overrides` mechanism and the allowlist format.

## How do I set a custom maintenance theme?

To set a custom theme for Drupal's maintenance mode (when the site is
offline for updates), set the `DRUPAL_MAINTENANCE_THEME` environment
variable:

```shell
# In .env file
DRUPAL_MAINTENANCE_THEME=my_custom_theme
```

Drupal uses this theme while the site is in maintenance mode. The installer
sets it in `.env` to the theme you chose for the site. When
`DRUPAL_MAINTENANCE_THEME` isn't set, `settings.php` falls back to the value
of `DRUPAL_THEME`, and to Claro when neither is set.

Use a valid Drupal theme that's already installed and enabled on your site.

➡️ See [Environment > Environment
variables](environment/README.mdx#environment-variables)

## Behat tests with `@javascript` tag sometimes get stuck

A scenario tagged `@javascript` sometimes hangs and then fails, because the
Chrome container stops responding. The hang happens at random, and its
cause is unknown. To recover, restart the Chrome container with
`docker compose restart chrome` or `ahoy restart chrome`.

Confirm that the scenario passes when you run the Behat tests again.

➡️ See [Testing > Behat](testing/behat.mdx)
