# Rector - instant upgrades and automated refactoring

https://github.com/rectorphp/rector

> Rector instantly upgrades and refactors the PHP code of your application.

Every Drupal major release removes the APIs that the previous one
deprecated. Rector rewrites your code to replace them, moves it onto PHP 8.4
language features, and applies the same refactorings across the whole
codebase at once. Keep it running and a major upgrade arrives with the
deprecations already gone.

**Vortex** comes with a [pre-configured Rector
configuration](https://github.com/drevops/vortex/blob/main/rector.php) for
Drupal projects, based on the configuration provided by [Drupal
Rector](https://github.com/palantirnet/drupal-rector).

Run Rector before a Drupal major upgrade to clear the remaining
deprecations, and every week or month during development to catch new ones
early. It also runs in the CI pipeline as one of the code quality checks, so
code that Rector would change fails the `lint` job. When you refactor
legacy code, run it to modernize older code in bulk.

:::note

Many projects run Rector ad hoc, for a single round of bulk refactoring.

**Vortex** runs it as a regular code quality tool instead: `ahoy lint-be`
checks for deprecated code at any time, and `ahoy lint-be-fix` fixes what
it finds. Running it continuously keeps the codebase up to date between
major upgrades.

:::

### Cache management

Rector caches parsed file information and analysis results in the system
temp directory, `/tmp/rector_cached_files` inside the CLI container, so
later runs reuse the results for files that haven't changed.

Clear the cache after you change the `rector.php` configuration (its rules,
skip list, or paths) or update the `rector/rector` or
`palantirnet/drupal-rector` packages. Clear it too after you switch to a Git
branch with a different Rector configuration, and whenever the results look
stale.

To clear the cache and check for violations:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy cli vendor/bin/rector process --clear-cache --dry-run
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli vendor/bin/rector process \
      --clear-cache --dry-run
    ```
  </TabItem>
</Tabs>

To clear the cache and apply changes:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy cli vendor/bin/rector process --clear-cache
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli vendor/bin/rector process --clear-cache
    ```
  </TabItem>
</Tabs>

## Configuration

See [configuration reference](https://getrector.com/documentation).

All global configuration lives in the
[`rector.php`](https://github.com/drevops/vortex/blob/main/rector.php) file.

Targets include custom modules and themes, settings, and tests. Unlike
PHPCS and PHPStan, Rector leaves the `scripts` directory alone.

### Config sets

Rector provides [config sets](https://getrector.com/documentation/set-lists)
that enable or disable rules in bulk. **Vortex** enables these:

- The PHP sets for the PHP version in `composer.json`, through
  `withPhpSets()` called without an argument.
- The Drupal sets from [Drupal
  Rector](https://github.com/palantirnet/drupal-rector), resolved from the
  installed `drupal/core` version, so the rules track core upgrades without
  changes to `rector.php`.
- The `codeQuality`, `codingStyle`, `deadCode`, `naming`, `privatization`,
  and `typeDeclarations` prepared sets.
- The Behat attribute sets, which convert Behat annotations to PHP 8
  attributes. They ship only when Behat is selected during installation.

On top of the sets, it adds the `DeclareStrictTypesRector` rule and, when
PHPUnit is selected, `YieldDataProviderRector`, which turns array-returning
data providers into generators. It also leaves class names unimported, so
Rector doesn't add `use` statements to the files it changes.

Adjust the config sets to suit your project. The [Rules
overview](https://getrector.com/documentation/rules-overview) page lists
all the available config sets.

## Ignoring

See more on the [Ignoring Rules Or
Paths](https://getrector.com/documentation/ignoring-rules-or-paths) page.

To skip a rule across the project, add it to `withSkip()` in the
[`rector.php`](https://github.com/drevops/vortex/blob/main/rector.php) file:

```php
->withSkip([
  SimplifyIfReturnBoolRector::class,
])
```

The shipped `withSkip()` list already skips 20 rules based on the project's
coding standards. It also skips `RemoveUnusedPublicMethodParameterRector`
for the `src/Hook` classes of custom modules and themes, and
`StringClassNameToClassConstantRector` for the settings includes. The list
also skips the `vendor` and `node_modules` directories.

To skip all Rector rules for a file:

```php
->withSkip([
  'file.php',
  '*/other_file.php',
])
```

To skip a specific rule for a file:

```php
->withSkip([
  SimplifyIfReturnBoolRector::class => ['file.php'],
])
```

Rector doesn't support ignoring code blocks.

## Continuous integration

Rector runs in the `lint` job of the [continuous integration
pipeline](../../continuous-integration/README.mdx) and fails the build on
violations.

### Ignoring failures

Set `VORTEX_CI_RECTOR_IGNORE_FAILURE` to `1` to let the build pass anyway.
Rector still runs and prints the changes it would make in the job log, so
you can see what you're letting through.

➡️ See [Continuous integration > Ignore tool
failures](../../continuous-integration/README.mdx#ignore-tool-failures)
