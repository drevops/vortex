# Stylelint - CSS linter

The [Stylelint website](https://stylelint.io/) describes the tool as
follows:

> A mighty CSS linter that helps you avoid errors and enforce conventions.

Stylelint catches mistakes in stylesheets, such as unknown properties,
invalid property values, and duplicate selectors. It also enforces the
conventions that keep them consistent, such as alphabetically ordered
declarations. **Vortex** comes with a [pre-configured Stylelint
ruleset](https://github.com/drevops/vortex/blob/main/.stylelintrc.js) for
Drupal projects.

This page is for developers who write CSS in custom modules or SCSS in the
custom theme. It shows how to run Stylelint and fix what it reports, what
the root and theme configurations enforce, and how to ignore a rule.

In **Vortex**, the root `lint-css` script lints the CSS in custom modules
only (`web/modules/custom`). The custom theme keeps its own configuration
in its directory, described under [Theme
configuration](#theme-configuration).

## Usage

### Check for violations

import Tabs from '@theme/Tabs';
import TabItem from '@theme/TabItem';

To check the stylesheets, run 1 of the following commands:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    # Lint all front-end code: Twig, JavaScript and CSS.
    ahoy lint-fe
    # Lint only CSS in custom modules.
    ahoy cli "npm run lint-css"
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli npm run lint-css
    ```
  </TabItem>
</Tabs>

Confirm that the check passed: Stylelint lists no problems, and `echo $?`,
run straight after the command, prints `0`.

### Fix violations

Stylelint fixes many violations automatically using the `--fix` flag. To
apply the fixes, run 1 of the following commands:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    # Fix all front-end lint issues.
    ahoy lint-fe-fix
    # Fix only CSS issues in custom modules.
    ahoy cli "npm run lint-fix-css"
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli npm run lint-fix-css
    ```
  </TabItem>
</Tabs>

`ahoy lint-fe` and `ahoy lint-fe-fix` also run the `lint` and `lint-fix`
scripts of the custom theme, which lint the theme's JavaScript and SCSS
together. To lint or fix only the theme's stylesheets, run its own
`lint-css` and `lint-css-fix` scripts:

```shell
ahoy cli "npm run --prefix=web/themes/custom/your_site_theme lint-css"
ahoy cli "npm run --prefix=web/themes/custom/your_site_theme lint-css-fix"
```

## Configuration

See the [Stylelint configuration
reference](https://stylelint.io/user-guide/configure).

All global configuration lives in the
[`.stylelintrc.js`](https://github.com/drevops/vortex/blob/main/.stylelintrc.js)
file.

By default, Stylelint uses the following shared configuration and plugin:

- `stylelint-config-standard` - the standard shareable configuration
- `stylelint-order` - plugin that provides the `order/*` rules

The following rules are set on top of the standard configuration:

- `order/properties-alphabetical-order` - declarations within a block must
  be in alphabetical order
- `at-rule-no-unknown` - unknown at-rules are reported, except the Sass
  at-rules `@extend`, `@at-root`, `@debug`, `@warn`, `@error`, `@if`,
  `@else`, `@for`, `@each`, `@while`, `@include`, `@mixin`, `@function`,
  `@return`, and `@content`
- `selector-class-pattern`, `selector-id-pattern`,
  `custom-property-pattern`, and `keyframes-name-pattern` - disabled, so
  class, ID, custom property, and keyframes names aren't forced into a
  naming pattern
- `no-descending-specificity` - disabled
- `font-family-no-missing-generic-family-keyword` - disabled

Targets include custom modules only. The `--allow-empty-input` flag makes
the run exit without an error when the glob matches no files:

```json
{
  "scripts": {
    "lint-css": "stylelint --allow-empty-input \"web/modules/custom/**/*.css\"",
    "lint-fix-css": "stylelint --allow-empty-input \"web/modules/custom/**/*.css\" --fix"
  }
}
```

To add or remove targets, change the globs in the `lint-css` and
`lint-fix-css` scripts in `package.json`. The following `lint-css` script
also lints `web/sites/default`:

```json
{
  "scripts": {
    "lint-css": "stylelint --allow-empty-input \"web/modules/custom/**/*.css\" \"web/sites/default/**/*.css\""
  }
}
```

The root `package.json` lists the `stylelint`, `stylelint-config-standard`,
and `stylelint-order` packages in its `devDependencies`, and `ahoy fei`
installs them.

### Theme configuration

The custom theme ships its own
[`.stylelintrc.json`](https://github.com/drevops/vortex/blob/main/web/themes/custom/your_site_theme/.stylelintrc.json)
and its own `package.json`, because a theme carries its own front-end
tooling and can be moved into a separate repository.

The theme configuration extends `stylelint-config-standard` and
`stylelint-config-standard-scss`, loads the `stylelint-scss` plugin, uses
the `string` formatter, and sets the following rules:

- `scss/at-extend-no-missing-placeholder` - `@extend` must target a
  placeholder selector
- `scss/comment-no-empty` - disabled
- `scss/dollar-variable-pattern` - `$variable` names must match
  `^_?[a-z]+([a-z0-9-]+[a-z0-9]+)?$`

Unlike the root configuration, it doesn't load `stylelint-order`, so the
theme's SCSS doesn't have to list declarations in alphabetical order.

The theme's `lint-css` script targets `scss/**/*.scss`, and the
configuration ignores `scss/_components.scss`, `fonts/**/*.scss`, and
`build/.*` through the `ignoreFiles` key.

## Ignoring

To ignore paths globally, list them in the `ignoreFiles` key of the
configuration file, as the theme configuration does:

```json
{
  "ignoreFiles": [
    "scss/_components.scss",
    "fonts/**/*.scss",
    "build/.*"
  ]
}
```

To ignore all Stylelint rules in a file, add this comment to the file
header:

```css
/* stylelint-disable */
```

To ignore specific rules in a file, add this comment to the file header:

```css
/* stylelint-disable selector-max-id, declaration-no-important */
```

To ignore rules for a block of code, put it between a `disable` and an
`enable` comment:

```css
/* stylelint-disable declaration-no-important */
a {
  color: red !important;
}
/* stylelint-enable declaration-no-important */
```

To ignore rules for the next line only, add this comment on the line before
it:

```css
a {
  /* stylelint-disable-next-line declaration-no-important */
  color: red !important;
}
```

To ignore rules for a single line, add this comment at the end of it:

```css
a {
  color: red !important; /* stylelint-disable-line declaration-no-important */
}
```

## Continuous integration

Stylelint runs in the `lint` job of the [continuous integration
pipeline](../../continuous-integration/README.mdx) and fails the build on
violations. CI lints the custom modules and the custom theme in separate
steps, and skips the theme step when
[`VORTEX_FRONTEND_BUILD_SKIP`](../variables.mdx#vortex_frontend_build_skip)
is set to `1`. On GitHub Actions, the theme step reads a repository
variable of that name, not the value in `.env`. Stylelint runs after ESLint
in each step, and the `lint` script stops at the first linter that fails,
so it reports nothing until ESLint passes.

### Ignoring failures

To let the build pass anyway, set the `VORTEX_CI_NODEJS_LINT_IGNORE_FAILURE`
CI variable to `1`. Stylelint still runs and prints its violations in the
job log, as long as ESLint passes first. The variable is shared with
[ESLint](eslint.mdx), which runs in the same step.

➡️ See [Continuous integration > Ignore tool
failures](../../continuous-integration/README.mdx#ignore-tool-failures)
