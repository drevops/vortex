# Composer

import TabItem from '@theme/TabItem';

[Composer](https://getcomposer.org/) is the dependency manager for PHP.
Drupal projects use it for everything from core to contributed modules. You
declare the packages your project needs in `composer.json`. Composer
resolves compatible versions, installs them and records the exact result in
`composer.lock`.

This page is for developers who manage the packages of a project built from
**Vortex**. It shows how to require, update, patch and audit packages. It
ends with a key-by-key [reference of the shipped `composer.json`
file](#composerjson-reference).

## Installing

Add a package with `composer require`. Composer adds the package to
`composer.json`, resolves its dependencies and installs them all. To add the
Devel module, for example, run the following command:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer require drupal/devel
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer require drupal/devel
    ```
  </TabItem>
</Tabs>

By default, Composer installs only stable releases. To install a pre-release
of a package, such as an `alpha`, `beta` or `RC`, add a stability flag to
its version constraint:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer require drupal/devel:^1.0.0@beta
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer require drupal/devel:^1.0.0@beta
    ```
  </TabItem>
</Tabs>

The flag applies to that package alone. When the pre-release needs unstable
versions of its own dependencies, pick 1 of 2 fixes:

- Require each of those dependencies with a stability flag too.
- Lower `minimum-stability` in `composer.json`.

A stability level allows itself and everything more stable. A
`minimum-stability` of `beta` allows `beta`, `RC` and stable releases. It
rejects `alpha` and `dev`:

```json
{
    "minimum-stability": "beta"
}
```

**Vortex** ships `prefer-stable` set to `true`. Keep it, so Composer still
picks a stable release whenever a stable release satisfies the constraint.

## Add JavaScript and CSS libraries (npm packages)

To install a JavaScript or CSS library as a Drupal library with Composer,
define it as an [inline Composer
package](https://getcomposer.org/doc/04-schema.md#repositories) with the
`drupal-library` type. The `installer-paths` entry for that type puts it in
`web/libraries/`, where Drupal looks for libraries.

:::warning Avoid Asset Packagist

Don't use [Asset Packagist](https://asset-packagist.org) to install
frontend libraries. Drupal.org distributes its Composer packages under
established security policies. Asset Packagist is a third-party service
without the safeguards that protect against supply chain attacks. Define the
packages inline, as the following steps show.

:::

To add the jQuery Easing library, for example, follow these steps:

1. Define the package in `composer.json` under the `repositories` section:

   ```json
   {
       "repositories": [
            {
               "type": "package",
               "package": {
                   "name": "gdsmith/jquery.easing",
                   "type": "drupal-library",
                   "version": "1.4.1",
                   "source": {
                       "type": "git",
                       "url": "https://github.com/gdsmith/jquery.easing",
                       "reference": "1.4.1"
                   }
               }
           }
       ]
   }
   ```

2. Require the package with Composer:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer require gdsmith/jquery.easing
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer require gdsmith/jquery.easing
    ```
  </TabItem>
</Tabs>

Confirm that the library's files are in `web/libraries/jquery.easing/`.

## Updating

To update all dependencies, run the following command:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer update
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer update
    ```
  </TabItem>
</Tabs>

:::note Updates and patches

If your project [patches](#patching) its dependencies, an update can fail
when a patch no longer applies to the new version of a dependency. Composer
then stops with `No available patcher was able to apply patch`, followed by
the patch URL and the package name.

A common fix is to remove the patch entries from `composer.json`, run the
update and then reapply each patch in turn.
:::

To update a specific package and its dependencies, run the following
command:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer update vendor/package-name --with-dependencies
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer update vendor/package-name \
      --with-dependencies
    ```
  </TabItem>
</Tabs>

To update Drupal core, run the following command:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer update "drupal/core-*" --with-dependencies
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer update "drupal/core-*" \
      --with-dependencies
    ```
  </TabItem>
</Tabs>

Review the result with `git diff` and commit it as a single commit. Look
closely at the scaffold files that core updates, such as `web/index.php` and
`web/sites/default/default.settings.php`. **Vortex** ships its own
`web/.htaccess` and keeps it out of scaffolding, so a core update never
overwrites it. When a core release changes `.htaccess`, port the change by
hand.

### Dependency bumping

[Dependency bumping](https://getcomposer.org/doc/03-cli.md#bump) raises the
version constraints in `composer.json` to the versions you have installed.
Adding a package then can't downgrade a package you already have. Composer
also has fewer versions to consider, so dependency resolution runs faster.

**Vortex** turns this on with the `bump-after-update` setting, so every
`composer update` raises your constraints to the versions it installed.

:::note

**Vortex** bumps automatically because it's built for Drupal sites. On an
application project like a site, you control the whole dependency tree.

A library, which is a reusable package, keeps its constraints as broad as
possible to spare downstream users [dependency
hell](https://getcomposer.org/doc/articles/versions.md). If you're building
a library, pick 1 of these options:

- Set `bump-after-update: "dev"` to bump only the development dependencies.
- Turn automatic bumping off and run `composer bump --dev-only` yourself.

:::

#### Manual bumping

The following commands bump the constraints by hand:

```shell
# Bump all dependencies
composer bump

# Bump specific package
composer bump drupal/core-recommended

# Bump only development dependencies
composer bump --dev-only

# Preview changes without modifying files
composer bump --dry-run
```

Run them in the `cli` container, or prefix them with `ahoy`, as in
`ahoy composer bump`.

## Overriding paths

To install a package somewhere other than the default location for its
type, add an entry to `installer-paths` in `composer.json`:

```json
{
    "extra": {
        "installer-paths": {
            "web/libraries/jquery-easing": [
                "gdsmith/jquery.easing"
            ],
            "web/libraries/{$name}": [
                "type:drupal-library"
            ]
        }
    }
}
```

The first entry sends 1 package to a custom directory. The second entry is
the catch-all that sends every other `drupal-library` package to
`web/libraries/{$name}`. Composer uses the first entry that matches, so a
package-specific path must come before the catch-all for its type.

## Vortex tooling package

**Vortex** ships its operational scripts as the
[`drevops/vortex-tooling`](https://github.com/drevops/vortex-tooling)
Composer package. They include the database, provisioning, deployment and
notification scripts. The scripts live in
`vendor/drevops/vortex-tooling/src/`. Composer exposes each entry-point
script as a binary under `vendor/bin/vortex-*`, such as
`vendor/bin/vortex-provision` or `vendor/bin/vortex-fetch-db`.

See [Architecture > Automation
scripts](../architecture.mdx#automation-scripts) for how the scripts are
structured and how the router scripts dispatch to the provider-specific
logic.

`composer.json` requires the package with a tilde constraint:

```json
{
    "require": {
        "drevops/vortex-tooling": "~1.5.0"
    }
}
```

The `~` constraint accepts patch releases but holds the minor version, so
`composer update` never moves you to a new minor release on its own.

To update the package within the constraint, run the following command:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer update drevops/vortex-tooling
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer update drevops/vortex-tooling
    ```
  </TabItem>
</Tabs>

To move to a new minor release, raise the constraint in `composer.json`
first and then run the update.

:::warning Never modify the shipped scripts

Don't edit files under `vendor/drevops/vortex-tooling/src/`. Git ignores
`vendor/`, so your changes never reach the repository. Composer also
replaces the files whenever it reinstalls or updates the package. Customize
the scripts through their [environment variables](variables.mdx), or add
your own scripts under `scripts/`, such as
[custom provision scripts](provision.mdx#running-custom-scripts). When
neither is enough, apply a [patch](#patching). Composer applies it again
whenever it installs or updates the package.

:::

## Patching

**Vortex** patches Composer dependencies with
[`cweagans/composer-patches`](https://github.com/cweagans/composer-patches)
2.x. Version 2.x applies patches with `git apply`, so they behave the same
on every platform. For the official documentation, see [Composer Patches
Recommended
Workflows](https://docs.cweagans.net/composer-patches/usage/recommended-workflows/).

### The `patches.lock.json` file

Composer Patches 2.x generates a `patches.lock.json` file. For each patch,
the file records the following:

- The package it applies to, its description and its URL
- A SHA-256 checksum of the patch file
- The depth used to apply it

Commit this file to version control, like `composer.lock`. With it, builds
apply the same patches across your team and in CI/CD. The checksums in the
file verify each patch's integrity.

### Add a patch

To add a patch, follow these steps:

<!-- markdownlint-disable MD029 -->

1. Define the patch in `composer.json` under `extra.patches`:

    ```json
    "extra": {
        "patches": {
            "drupal/foobar": {
                "Fix for issue #123": "https://www.drupal.org/files/issues/fix-123.patch"
            }
        }
    }
    ```

2. Regenerate `patches.lock.json`:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer patches-relock
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer patches-relock
    ```
  </TabItem>
</Tabs>

The output ends with `patches.lock.json has been recreated successfully.`

:::warning
`composer patches-repatch` uninstalls every patched package from its
directory, such as `web/modules/contrib/` or `vendor/`. It then runs
`composer install` to put the packages back, so any local edits in them are
lost.
:::

3. Remove and reinstall patched packages:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer patches-repatch
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer patches-repatch
    ```
  </TabItem>
</Tabs>

4. Update `composer.lock`:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer update --lock
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli composer update --lock
    ```
  </TabItem>
</Tabs>

<!-- markdownlint-enable MD029 -->

Confirm that the `patches-repatch` output in step 3 has a
`- Patching drupal/foobar` line for the patched package.

### Remove a patch

To remove a patch, follow these steps:

<!-- markdownlint-disable MD029 -->

1. Delete the patch definition from `composer.json`.

2. Regenerate `patches.lock.json`:

<Tabs>

4. Reinstall without the patch:

  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">

    ```shell
    docker compose exec cli composer patches-repatch
    ```
  </TabItem>

5. Update `composer.lock`:

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy composer update --lock
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">

Confirm that `patches.lock.json` lists the package only when it still has
other patches.

## Security auditing

`composer audit` checks the installed packages against published security
advisories and reports abandoned packages. **Vortex** configures Composer's
`config.policy` so that advisories never block `composer install`,
`composer update` or `composer require`. `composer audit` itself still
fails when it finds an advisory, so vulnerabilities stay visible locally
and in CI.

➡️ See [Dependency audit](security/dependency-audit.mdx) for the full policy
reference, the audit commands and how to ignore assessed advisories.

## `composer.json` reference

### File overview

**Vortex** ships a pre-configured `composer.json` with the packages a Drupal
project needs and the development tools that check your code quality.

The `composer.json` file is Composer's core configuration file. It declares
your project's dependencies, where they install and how Composer behaves.
The `lint` job in continuous integration checks it with
`composer validate --strict` and `composer normalize --dry-run`. After you
edit the file by hand, run `ahoy composer normalize`.

This section describes each part of the file and its role.

  <CodeBlock language="json">{ComposerJsonSource}</CodeBlock>

</details>

#### `name`

[`name`](https://getcomposer.org/doc/01-basic-usage.md#package-names)
identifies the project in Composer's ecosystem, as a vendor name and a
project name joined by a slash. The installer replaces the template's
`your_org/your_site` with your organization and site machine names.

#### `description`

`description` holds a short summary of the project's purpose. The installer
fills in your site and organization names.

#### `type`

`type` sets how Composer and the tools built on it treat the package. The
type can change how the package is installed and used. **Vortex** sets it to
`project`, the type for an application.

#### `license`

[`license`](https://getcomposer.org/doc/04-schema.md#license) states the
project's license. **Vortex** sets it to `proprietary`, because the sites
built from the template are usually proprietary. The [SPDX Open Source
License Registry](https://spdx.org/licenses/) lists the identifiers for
other licenses.

#### `repositories`

The [`repositories`](https://getcomposer.org/doc/04-schema.md#repositories)
section adds package repositories beyond Packagist, the default source. The
template declares the following 2 repositories:

| Repository | Type | Description |
|------------|------|-------------|
| [`packages.drupal.org/8`](https://www.drupal.org/docs/develop/using-composer/using-packagesdrupalorg) | `composer` | The official source for Drupal modules, themes and distributions, which aren't published on Packagist. |
| [`.vortex/tooling`](https://getcomposer.org/doc/05-repositories.md#path) | `path` | Resolves the in-tree tooling package while developing **Vortex** itself. The installer removes this entry during site creation, so your project installs [`drevops/vortex-tooling`](https://github.com/drevops/vortex-tooling) from Packagist instead. |

#### `require`

The [`require`](https://getcomposer.org/doc/04-schema.md#require) section
lists the packages your project needs to run.

The **Documentation** column links to the page covering that package in more
depth. A [Settings](settings.mdx#per-module-overrides) link means **Vortex**
ships a per-module override file that applies environment-aware defaults for
that module. Some modules still need a running service or
environment-specific values on top of those defaults.

The installer removes some packages based on your answers:

- It leaves out `drupal/storybook`, `drupal/migrate_plus` and
  `drupal/migrate_tools` unless you turn on Storybook or the migration
  database.
- It drops the module of each service you deselect: `drupal/clamav`,
  `drupal/redis` or `drupal/search_api_solr`.
- It lets you deselect any of the other contributed modules except
  `drupal/search_api`, which always stays.

➡️ See [Contributed modules](modules/contributed-modules.mdx) for what each
override configures and where each module is installed.

#### `require-dev`

The [`require-dev`](https://getcomposer.org/doc/04-schema.md#require-dev)
section lists packages you need only during development, such as the code
quality and testing tools. The container image build runs
`composer install --no-dev`, so these packages stay out of production and
the deployment stays smaller.

The installer removes the packages of each development tool you deselect,
with 2 exceptions:

- `softcreatr/jsonpath` stays when you deselect Behat.
- `mikey179/vfsstream` stays when you deselect PHPUnit.

The following table describes each package in `require-dev`:

#### `conflict`

The [`conflict`](https://getcomposer.org/doc/04-schema.md#conflict) section
declares every version of `drupal/drupal`, the standalone Drupal package,
incompatible with the project. Composer refuses to install it next to the
core packages, so core versions don't clash and core files stay consistent.

#### `minimum-stability`

The
[`minimum-stability`](https://getcomposer.org/doc/04-schema.md#minimum-stability)
setting is the lowest stability that Composer accepts when it resolves
dependencies. **Vortex** sets it to `"stable"`, so Composer ignores the
pre-releases of every package unless its constraint in `require` or
`require-dev` carries a stability flag. For example,
`"friends-of-behat/mink-extension": "^3.0@alpha"` lets that package install
as an alpha.

#### `prefer-stable`

The
[`prefer-stable`](https://getcomposer.org/doc/04-schema.md#prefer-stable)
setting, when set to `true`, makes Composer choose a stable release over a
pre-release whenever a stable release satisfies the constraint. A
requirement with a stability flag, such as
`"drupal/config_update": "^2@alpha"`, then gets an alpha only while no
stable 2.x release exists. The same applies when
you lower `minimum-stability` for a fix that's only in a pre-release. Every
package with a stable release still gets that stable release.

#### `config`

The [`config`](https://getcomposer.org/doc/04-schema.md#config) section
configures how Composer behaves in the project. **Vortex** sets the
following keys:

- [`allow-plugins`](https://getcomposer.org/doc/06-config.md#allow-plugins):
  Lists the Composer plugins that are allowed to run. Composer won't run an
  unlisted plugin without your approval, so untrusted plugin code stays
  out. **Vortex** allows these 10 plugins:
  - `composer/installers`
  - `cweagans/composer-patches`
  - `dealerdirect/phpcodesniffer-composer-installer`
  - `drupal/core-composer-scaffold`
  - `ergebnis/composer-normalize`
  - `php-http/discovery`
  - `phpstan/extension-installer`
  - `pyrech/composer-changelogs`
  - `symfony/runtime`
  - `tbachert/spi`
- [`policy`](https://getcomposer.org/doc/06-config.md#policy): Controls
  security auditing and version blocking of dependencies, and requires
  Composer 2.10.0 or later. **Vortex** sets `advisories.block` to `false`,
  `advisories.audit` to `"fail"` and `abandoned.audit` to `"report"`.
  Advisories never block installs but still fail `composer audit`, so
  vulnerabilities stay visible without breaking reproducible builds.
  Abandoned packages show up in the report without failing it. ➡️ See
  [Dependency audit](security/dependency-audit.mdx) for the option values,
  how to ignore advisories and the CI integration.
- [`bump-after-update`][bump-after-update]:
  Runs `composer bump` after every `composer update`, which raises the
  version constraints in `composer.json` to the installed versions.
  **Vortex** sets it to `true` to bump all dependencies. The available
  values are `true` (all dependencies), `false` (disabled), `"dev"` (only
  development dependencies) and `"no-dev"` (only non-development
  dependencies).
- [`discard-changes`][discard-changes]:
  When set to `true`, Composer discards local changes in dependencies that
  were installed from source, such as a Git checkout. The setting applies
  only when Composer runs non-interactively, for example in CI or with
  `--no-interaction`. An interactive run asks you what to do.
- [`platform`](https://getcomposer.org/doc/06-config.md#platform): Tells
  Composer which PHP version to resolve dependencies for, regardless of the
  PHP version that runs Composer. Set it as an exact version number, such as
  the `8.4.27` that **Vortex** ships. Keep it in sync with the PHP version
  in the [Docker containers](environment/docker.mdx).
- [`sort-packages`](https://getcomposer.org/doc/06-config.md#sort-packages):
  When set to `true`, `composer require` keeps the package lists in
  `composer.json` sorted by name. Sorted lists are easier to read and cause
  fewer merge conflicts. The setting doesn't affect `composer.lock`.

[discard-changes]: https://getcomposer.org/doc/06-config.md#discard-changes

#### `autoload-dev`

The [`autoload-dev`](https://getcomposer.org/doc/04-schema.md#autoload-dev)
section tells Composer how to autoload the classes that only development
needs, so no file has to `include` or `require` them by hand. **Vortex**
adds `tests/phpunit/` to its `classmap`, which covers the project-level
PHPUnit tests, such as the settings tests, and their base classes.

#### `extra`

The [`extra`](https://getcomposer.org/doc/04-schema.md#extra) section holds
configuration for Composer plugins, which read their settings from here to
fit the structure of your Drupal project. **Vortex** sets the following
keys:

- [`drupal-scaffold`][drupal-scaffold]:
  Controls the Drupal scaffold files:
  - `locations`: Sets the web root (the directory containing the `index.php`
    file), `web/` in **Vortex**.
  - `file-mapping`: Decides which scaffold files the plugin manages.
    **Vortex** turns off 14 of the files that core provides. It ships its
    own `.htaccess`, `.editorconfig` and `.gitattributes`. It leaves out
    others, such as `update.php` and `robots.txt`. Set an entry to `false`
    to stop core from overwriting that file.
- [`installer-paths`][installer-paths]:
  Sets where each package type installs:
  - Drupal core: `web/core`
  - Contributed modules, themes and profiles: `web/modules/contrib`,
    `web/themes/contrib` and `web/profiles/contrib`
  - Custom modules, themes and profiles: `web/modules/custom`,
    `web/themes/custom` and `web/profiles/custom`
  - Libraries: `web/libraries`
  - Recipes: `recipes`
  - Drush command packages: `drush/Commands/contrib`

  ➡️ See [Overriding paths](#overriding-paths)
- `patchLevel`: Holds `-p2` for `drupal/core`. The `-p` option of a patch
  command (for example, `-p1` or `-p2`) is the number of leading directories
  to strip from the file paths in the patch. Version 2.x of
  `cweagans/composer-patches` doesn't read this key. It takes the depth from
  the first of these that's set:
  - The patch's own `depth`
  - `extra.composer-patches.package-depths` for the package
  - Its built-in default for the package, which is 2 for `drupal/core`
  - `extra.composer-patches.default-patch-depth`, which defaults to 1
- `patches`: Lists the patches to apply to each package. The template ships
  it empty. The applied patch state lives in the generated
  `patches.lock.json` file, which you commit like `composer.lock`. ➡️ See
  [Patching](#patching)
