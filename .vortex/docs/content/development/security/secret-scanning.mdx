# Secret scanning

A password or API token committed to Git stays in the history long after
someone deletes the line, so you want to catch it before it merges.
[Gitleaks](https://github.com/gitleaks/gitleaks) does that: it scans the
code for hardcoded secrets like passwords, API keys, and tokens, and fails
the security audit when it finds one.

:::note

**Vortex** doesn't install Gitleaks locally. Follow the
[instructions](https://github.com/gitleaks/gitleaks#installing) to install
it on your system.

In CI, Gitleaks runs from its official Docker image as part of the [security
audit workflow](../../continuous-integration/README.mdx#security-audit).

:::

## Usage

```shell
gitleaks dir .
```

Run it from the project root: Gitleaks reads `.gitleaks.toml` from the
directory it scans. It prints only the number of findings by default; add
`-v` to see each finding. `gitleaks dir` scans the files on disk, the same
as CI, and doesn't look at the Git history. To scan the history too, for
example before you make a repository public, run `gitleaks git .`.

## Configuration

Global configuration lives in the
[`.gitleaks.toml`](https://github.com/drevops/vortex/blob/main/.gitleaks.toml)
file at the repository root (see the [configuration
documentation](https://github.com/gitleaks/gitleaks#configuration)). It
extends Gitleaks' default rule set and allowlists the paths that hold
third-party, generated, or local-only files: `.artifacts/`, `.data/`,
`.git/`, `.logs/`, `node_modules/`, `vendor/`, `web/core/`,
`web/libraries/`, `web/modules/contrib/`, `web/sites/default/files/`, and
`web/themes/contrib/`. The scan then covers the code your team writes, so a
clean install reports no findings while Gitleaks still detects real secrets.

## Ignoring

To ignore a single line, add a `gitleaks:allow` comment to it:

```php
$settings['example'] = 'not-a-real-secret'; // gitleaks:allow
```

To ignore a path or a known-safe value that recurs across the codebase, add
an allowlist entry to the `.gitleaks.toml` file. To ignore 1 specific
finding, add its fingerprint to a `.gitleaksignore` file at the repository
root.

## Continuous integration

Gitleaks runs in the [security audit
workflow](../../continuous-integration/README.mdx#security-audit) and fails
that workflow if there are any violations. The installer turns it on by
default; answering "no" to its Gitleaks prompt removes the CI steps and the
`.gitleaks.toml` file.

### Ignoring failures

Set `VORTEX_CI_GITLEAKS_IGNORE_FAILURE` to `1` to let the workflow pass
anyway. Gitleaks still runs and reports how many findings it made. In
GitHub Actions, the details reach code scanning and the `security-findings`
artifact; in CircleCI, run `gitleaks dir . -v` locally to see them.

➡️ See [Ignore tool
failures](../../continuous-integration/README.mdx#ignore-tool-failures).

### Where findings appear

In GitHub Actions, the workflow also uploads Gitleaks findings to the
repository's **Security → Code scanning** tab under the `gitleaks` category.
Each finding becomes an alert naming the rule that matched, located at the
line it was found on.

➡️ See [Code
scanning](../../continuous-integration/README.mdx#code-scanning).

### Dismissing a finding

Dismissing an alert in the **Security → Code scanning** tab records a reason
against that finding and removes it from the open list. That's the right
tool for tracking an assessment.

It doesn't change what the scan does. Gitleaks still matches the value and
still fails the workflow until you ignore it as described in
[Ignoring](#ignoring). That takes a `gitleaks:allow` comment on the line, an
allowlist entry in `.gitleaks.toml`, or the finding's fingerprint in
`.gitleaksignore`.
