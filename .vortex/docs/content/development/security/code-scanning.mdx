# Code vulnerability scanning

Code your team writes can carry a vulnerability that no linter flags, such
as a file path built from request input. This page is for developers and
leads on a project built from **Vortex**. It shows what the vulnerability
scanners check, how to run Semgrep locally, how to ignore a false positive
and where the findings appear in continuous integration (CI).

2 static analysis tools read the code without running it:

| Tool | Code it scans | Providers |
|------|---------------|-----------|
| [CodeQL](https://codeql.github.com/) | GitHub Actions workflows, JavaScript and TypeScript | GitHub Actions |
| [Semgrep](https://semgrep.dev/) | PHP, with the [`p/php`](https://semgrep.dev/p/php) rule set | GitHub Actions and CircleCI |

CodeQL has no PHP analyzer, so Semgrep covers the PHP code.

## Usage

**Vortex** doesn't install Semgrep locally. Run it from its Docker image in
the project root, with the same version and flags as CI:

```shell
docker run --rm -v "${PWD}:/src" -w /src semgrep/semgrep:1.185.0 semgrep scan --config p/php --metrics=off --error
```

Semgrep scans only the files tracked by Git. It skips test directories,
dependency directories and the other paths in its [default ignore
list](https://semgrep.dev/docs/ignoring-files-folders-code#understand-semgrep-defaults).
`--error` makes the command exit with `1` when it finds a vulnerability. On
a clean codebase, the scan ends with `0 findings`.

CodeQL runs only in GitHub Actions.

## Ignore findings

To ignore a Semgrep finding on a line you've assessed, add a `nosemgrep`
comment with the rule ID from the finding to that line:

```php
phpinfo(); // nosemgrep: php.lang.security.phpinfo-use.phpinfo-use
```

To skip a path, list it in a `.semgrepignore` file at the project root.
That file replaces Semgrep's default ignore list, so also add the default
paths you still want skipped, such as `tests/`.

CodeQL findings have no in-code exception. Dismiss them in code scanning,
as described in [Dismiss a finding](#dismiss-a-finding).

## Continuous integration

The scanners run in the [security audit
workflow](../../continuous-integration/README.mdx#security-audit). In
GitHub Actions, they run in the workflow's `sast` job, next to the `audit`
job. In CircleCI, Semgrep runs in the `audit` job.

A Semgrep finding fails the workflow. CodeQL reports its findings to code
scanning only, so a CodeQL finding leaves the workflow passing.

### Ignore failures

Set `VORTEX_CI_SEMGREP_IGNORE_FAILURE` to `1` to let the workflow pass
despite Semgrep findings. In GitHub Actions, set it as a repository
variable. In CircleCI, set it as an environment variable. Semgrep still
runs and prints every finding in the job log.

➡️ See [Ignore tool
failures](../../continuous-integration/README.mdx#ignore-tool-failures).

### Skip CodeQL

CodeQL on a private repository requires a GitHub Code Security license. To
turn CodeQL off, set the `VORTEX_CI_CODEQL_SKIP` repository variable to `1`.
Semgrep keeps running.

### Where findings appear

In GitHub Actions, the findings reach the repository's
**Security > Code scanning** tab:

- CodeQL uploads its findings under 1 category per language,
  `/language:actions` and `/language:javascript-typescript`.
- Semgrep findings go under the `semgrep` category.

The `sast` job also attaches every report to the run as the `sast-findings`
artifact. In CircleCI, the findings appear only in the job log.

➡️ See [Code
scanning](../../continuous-integration/README.mdx#code-scanning).

### Dismiss a finding

Dismissing an alert in the **Security > Code scanning** tab records a reason
against that finding and removes it from the open list. For a CodeQL
finding, dismissing is the way to record a false positive.

A dismissed Semgrep alert still fails the workflow. To stop the failure,
add a `nosemgrep` comment as described in
[Ignore findings](#ignore-findings).
