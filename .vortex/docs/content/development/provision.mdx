# Provision

Provisioning turns an assembled codebase into a working Drupal site. By
default it imports the database dump; switch the provision type to `profile`
and it installs Drupal from a profile instead. Either way, it then runs the
database updates and the configuration import, so the site matches your
code. A site that's already installed keeps its database unless you ask for
a fresh one.

A single script does the whole job: `vortex-provision`, shipped in the
[`drevops/vortex-tooling`](https://packagist.org/packages/drevops/vortex-tooling)
Composer package and installed at `vendor/bin/vortex-provision`. Your
machine, CI, and every hosting environment run that same script. The steps
stay the same everywhere, and only the environment variables and the
detected environment type change what they do.

## Provisioning flow

The diagram follows the default `database` provision type. With
`VORTEX_PROVISION_TYPE=profile`, the branches at the top collapse into 1
decision. A site that isn't installed yet gets a fresh installation from the
profile. An installed site keeps its database and skips sanitization, unless
`VORTEX_PROVISION_OVERRIDE_DB=1` asks for a reinstall. Everything after the
installation runs the same way for both types.

Before any of this, the script checks that the configuration directory in
`$settings['config_sync_directory']` exists, and stops with an error if it
doesn't.

### Customizing flow

These environment variables steer the flow:

1. `VORTEX_PROVISION_SKIP=1`<br/>
   A kill switch. The script exits as soon as it starts and leaves the site
   alone, which helps in an emergency when every kind of automation has to
   stop.<br/><br/>
2. `VORTEX_PROVISION_TYPE=profile`<br/>
   Install Drupal from the profile in `DRUPAL_PROFILE` (default `standard`)
   instead of importing a `database` dump. With exported configuration
   present, it runs `drush site:install --existing-config`, so the site
   installs from your configuration. That suits sites without a persistent
   database, and it tests that your configuration installs cleanly from
   scratch. Any value other than `profile` counts as `database`, the
   default.<br/><br/>
3. `VORTEX_PROVISION_OVERRIDE_DB=1`<br/>
   Replace the database of a site that's already installed. The script drops
   it and imports the dump again, or reinstalls from the profile. Without
   it, an installed site keeps its database and only the later steps run.
   `.env` ships with `0`, the usual choice for hosted environments, and
   `.env.local.example` sets `1`, so local provisioning starts from a fresh
   copy.<br/><br/>
4. `VORTEX_PROVISION_FALLBACK_TO_PROFILE=1`<br/>
   Fall back to a profile installation when the database dump file is
   missing, or when the container image holds no usable database. The script
   installs the profile in `DRUPAL_PROFILE` without your exported
   configuration and enables the Shield module to protect the environment.
   It then skips every post-provision operation, from database updates to
   custom scripts. The result is a minimal working Drupal site when no
   database is available. It applies to the `database` provision type
   only.<br/><br/>
5. `VORTEX_PROVISION_POST_OPERATIONS_SKIP=1`<br/>
   Stop right after the database import or profile installation, and skip
   every later step, from maintenance mode to the final configuration check.
   CI uses it to cache a database in the state it was fetched, before any
   updates run.<br/><br/>
6. `VORTEX_PROVISION_USE_MAINTENANCE_MODE=1`<br/>
   Put the site into maintenance mode once it can bootstrap, and take it out
   again at the end, so visitors don't reach a site that's halfway through
   provisioning. It's on by default: `.env` sets `1`, and so does the
   script when the variable isn't set.<br/><br/>
7. `VORTEX_PROVISION_VERIFY_CONFIG_UNCHANGED_AFTER_UPDATE=1`<br/>
   Fail the provisioning when `drush updatedb` changes active configuration.
   The script exports the configuration before and after the updates and
   compares the 2 copies, so `drush config:import` can't silently overwrite
   what an update hook changed. On failure, it lists the changed files and
   keeps both exports for you to review. The check needs exported
   configuration files and is off by default.<br/><br/>
8. `VORTEX_PROVISION_CACHE_REBUILD_AFTER_DB_UPDATE_SKIP=1`<br/>
   Skip the cache rebuild between the database updates and the
   configuration import. By default, the script runs
   `drush updatedb --no-cache-clear` and then rebuilds the caches itself, so
   the configuration import starts from a clean state.<br/><br/>
9. `VORTEX_PROVISION_CONFIG_IMPORT_REPEAT=1`<br/>
   Run the configuration import a second time, straight after the first.
   It helps when update hooks introduce configuration that changes what a
   later import does (for example, new `config_split` settings). It's off by
   default, and like the import itself it needs exported
   configuration.<br/><br/>
10. `VORTEX_PROVISION_SANITIZE_DB_SKIP=1`<br/>
    Skip database sanitization.
    [Database sanitization](#database-sanitization) explains when it runs
    otherwise.<br/><br/>
11. `VORTEX_PROVISION_VERIFY_CONFIG_UNCHANGED_AFTER_PROVISION=1`<br/>
    Fail the provisioning when the post-provision operations leave active
    configuration different from the exported files. The check runs last,
    after the configuration imports, deployment hooks, and custom provision
    scripts. It fails if `drush config:status` reports any item in the
    `Different` state. Items that exist only in the database or only in the
    sync directory don't count, because a site can legitimately carry
    either. Like the update check, it needs exported configuration files and
    is off by default.

A few more variables shape what gets provisioned:

- `VORTEX_DB_DIR` and `VORTEX_DB_FILE` locate the dump (`./.data/db.sql` by
  default). `VORTEX_PROVISION_DB_DIR` and `VORTEX_PROVISION_DB_FILE`
  override them for provisioning only, and `VORTEX_PROVISION_DB` takes a
  full path to the dump.
- `VORTEX_DB_IMAGE`, or `VORTEX_PROVISION_DB_IMAGE` for provisioning only,
  names the container image when the database ships inside one. Setting it
  sends the flow down the "Container image set?" branches of the diagram.
- `DRUPAL_PROFILE`, `DRUPAL_SITE_NAME`, `DRUPAL_SITE_EMAIL`, and
  `DRUPAL_ADMIN_EMAIL` feed the profile installation. The administrator
  account is always named `admin`.
- `VORTEX_PROVISION_SCRIPTS_DIR` sets where the
  [custom scripts](#running-custom-scripts) live.
- `VORTEX_PROVISION_LOG=1` saves the output as `provision.log` in
  `VORTEX_NOTIFY_LOG_DIR`, where deployment notifications collect it.

The [Variables reference](variables.mdx) lists the script's variables with
their defaults.

:::tip

Set these variables in `.env` to apply them everywhere, or in your CI or
hosting provider's environment variables to change a single environment.

:::

### Maintenance mode

Maintenance mode keeps visitors out while the database updates and
configuration imports run, so nobody browses a site that's halfway between
2 versions. It's on by default: `.env` sets
`VORTEX_PROVISION_USE_MAINTENANCE_MODE=1`, and the script falls back to `1`
when the variable isn't set at all. Set it to `0` in `.env`, or in your
hosting provider's environment variables, to keep the site online during
provisioning.

If a step fails partway through, the script exits with the site still in
maintenance mode. Fix the problem and provision again, or turn maintenance
mode off by hand:

```shell
drush maint:set 0
```

### Database sanitization

Sanitization replaces real user data with safe values, so a copy of
production can't email real people from a test run or show their details to
the team. The script runs `drush sql:sanitize`, which replaces account email
addresses and passwords, scrubs user field values and comment author
details, and empties the sessions table.

:::warning

Sanitization changes the imported database, not the dump file, so anyone
with access to the dump can still read the sensitive data in it.

If your database holds highly sensitive data, sanitize the dump before it
can be downloaded (sanitize on export). Tools such as
[Drush GDPR Dumper](https://github.com/robiningelbrecht/drush-gdpr-dumper)
or [MTK](https://github.com/skpr/mtk) do this, and they fit into
**Vortex**-based projects without changes to the provisioning process.

:::

Sanitization runs by default whenever provisioning brings in a fresh
database: a dump import, a profile installation, or a database container
image. It's skipped whenever the script keeps an existing database, and that
includes a database the hosting platform copied in, for example from
production. Production keeps its own database between deployments, so it
isn't sanitized, and `.lagoon.yml` also sets
`VORTEX_PROVISION_SANITIZE_DB_SKIP=1` in production explicitly.

To turn sanitization off, set `VORTEX_PROVISION_SANITIZE_DB_SKIP=1` in the
`.env` file or in your hosting provider's environment variables.

#### Customizing database sanitization

Set these variables in the `.env` file or in your hosting provider's
environment variables to adjust what sanitization does:

1. `VORTEX_PROVISION_SANITIZE_DB_EMAIL=user_%uid@your-site-domain.example`\
   Replace every account email address with this pattern. Drush substitutes
   `%uid` with the user ID, and also accepts `%mail` and `%name`. `.env`
   ships with this value; without it, the script uses
   `user+%uid@localhost`.<br/><br/>
2. `VORTEX_PROVISION_SANITIZE_DB_PASSWORD=<random or exact>`\
   Replace account passwords with this exact value. By default the script
   generates a random number on each run, so no production password works
   on the sanitized copy.<br/><br/>
3. `VORTEX_PROVISION_SANITIZE_DB_REPLACE_USERNAME_WITH_EMAIL=1`\
   Replace each username with the user's sanitized email address, so the
   usernames don't give real names away either. It's off (`0`) by
   default.<br/><br/>
4. `VORTEX_PROVISION_SANITIZE_DB_ADDITIONAL_FILE=./scripts/sanitize.sql`\
   Run the SQL queries in this file after the Drush sanitization. This path
   is the default, and **Vortex** ships `scripts/sanitize.sql` with an
   example query that blocks user 1. The script skips this step when the
   file doesn't exist, so deleting the file turns it off.

Whatever you configure, the script then empties the name and email of the
anonymous user (user 0). When `DRUPAL_ADMIN_EMAIL` is set, it also sets
user 1's email back to that address.

## Database

The running site's database lives inside the `database` container. The
`.data/db.sql` file on your machine is only a dump that imports read and
exports write. Remove the container (`ahoy reset` does, for example) and the
live database goes with it; the next build re-creates it from the dump.

Fetching and exporting run on the host, because they move dump files
around. Refreshing runs inside the containers, because it imports into the
running database. The tabs below follow that split.

### Fetching database

`ahoy fetch-db` downloads the latest dump of the production database into
the `.data` directory, from the source set in `VORTEX_FETCH_DB_SOURCE`.

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    # Fetch latest database dump
    ahoy fetch-db
    # Force a fresh fetch regardless of cache
    ahoy fetch-db --fresh
    ```
  </TabItem>
  <TabItem value="host" label="Host">
    ```shell
    # Fetch latest database dump
    ./vendor/bin/vortex-fetch-db
    # Force a fresh fetch regardless of cache
    VORTEX_FETCH_DB_FRESH=1 VORTEX_FETCH_DB_FORCE=1 \
      ./vendor/bin/vortex-fetch-db
    ```
  </TabItem>
</Tabs>

When `.data` already holds a dump, the fetch keeps it and stops, whatever
its age. `VORTEX_FETCH_DB_FORCE=1` downloads a new copy anyway, and
`.env.local.example` sets it, so a `.env.local` copied from that file always
downloads. `--fresh` sets it too, along with `VORTEX_FETCH_DB_FRESH=1`. That
second variable makes Acquia create a new backup instead of downloading the
latest one. On Lagoon, it creates a new dump instead of reusing the one made
earlier that day.

:::note

The database dump is stored in the `.data` directory instead of being
directly imported into the local environment, so it can be cached and
reused. You don't need to fetch it every time you refresh the local
environment.

You can also fetch the dump from the production environment by hand: name
it `db.sql` and place it in the `.data` directory.

:::

### Refreshing database

You can load the dump from `.data` into the running database container in 2
ways, depending on what you need.

#### Import and run updates (`ahoy provision`)

`ahoy provision` runs the whole [provisioning flow](#provisioning-flow)
inside the CLI container:

- Database import from dump or profile installation
- Database updates via `drush updatedb`
- Configuration import via `drush config:import` (if config files present)
- Cache rebuilds
- Deployment hooks
- Database sanitization
- Post-provisioning custom scripts

Use it whenever you want the local environment back in a fully updated
state: a configured site that's ready for development or deployment.

It asks for confirmation first, reloads the database container from its
image when `VORTEX_DB_IMAGE` is set, and prints a one-time login link at the
end. The dump replaces the current database only when no site is installed
yet or `VORTEX_PROVISION_OVERRIDE_DB=1` is set, which `.env.local.example`
does. Otherwise the site keeps its database and only the later steps run.

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    ahoy provision
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    docker compose exec cli ./vendor/bin/vortex-provision
    ```
  </TabItem>
</Tabs>

#### Import only (`ahoy import-db`)

`ahoy import-db` imports the raw dump without running any updates,
configuration imports, or scripts:

- Imports the database dump
- Skips configuration imports
- Skips database updates
- Skips post-provisioning scripts

Use it to quickly reset the database contents to the state captured in the
dump. It asks for confirmation, then drops the current database and loads
the dump. A missing or unreadable dump file stops it before anything is
dropped.

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    # Import database only from default dump in .data/db.sql
    ahoy import-db
    # Import database only from a specific dump file
    ahoy import-db path/to/dump.sql
    ```
  </TabItem>
  <TabItem value="docker-compose" label="Docker Compose">
    ```shell
    # Import database only from default dump in .data/db.sql
    docker compose exec cli ./vendor/bin/vortex-import-db
    # Import database only from a specific dump file
    docker compose exec cli ./vendor/bin/vortex-import-db path/to/dump.sql
    ```
  </TabItem>
</Tabs>

:::tip When to use which command

Use `ahoy import-db` when you want the raw database data without any
configuration changes or updates.

Use `ahoy provision` when you want the full setup, including configuration
and updates.

:::

### Exporting database

`ahoy export-db` saves the current local database as a timestamped dump in
`.data`, with a name such as `export_db_20260101_120000.sql`.

<Tabs>
  <TabItem value="ahoy" label="Ahoy" default>
    ```shell
    # Export current database to .data directory
    ahoy export-db
    ```
  </TabItem>
  <TabItem value="host" label="Host">
    ```shell
    # Export current database to .data directory
    ./vendor/bin/vortex-export-db
    ```
  </TabItem>
</Tabs>

These dumps let you return the local environment to a known state later:
rename one to `.data/db.sql` and run `ahoy import-db`, or pass its path to
`ahoy import-db` directly. To pick the filename yourself, pass it to the
export: `ahoy export-db db.sql` writes `.data/db.sql`. With
`VORTEX_DB_IMAGE` set, the command exports a database container image
instead of a file.

Cache tables are exported with their structure but without their data,
because Drupal rebuilds them on demand and their contents would only inflate
the dump. Set `VORTEX_EXPORT_DB_FILE_STRUCTURE_TABLES` to a comma-separated
list of table names, each of which may use the `*` wildcard, to choose which
tables are exported this way (the default is `cache*`). Set it to an empty
value to export the data of every table.

## Rationale

Drush has a command for each deployment step (`drush updatedb`,
`drush config:import`, `drush deploy:hook`), but running them by hand
assumes the site is already bootstrapped and stable. That assumption breaks
during an initial setup, and in environments that come and go, such as CI
pipelines, container builds, or multisite setups. There, something has to
run the steps in the right order and decide which of them apply.

The provision script is that orchestration:

- It bootstraps the environment by importing a database dump or installing a
  fresh Drupal instance from a profile.
- It handles conditional logic for different runtime scenarios, such as
  skipping provisioning, enforcing fresh database imports, or using
  maintenance mode.
- The same provisioning logic runs across local, CI, staging, and production
  environments.
- It runs custom post-provisioning scripts, so you can add project-specific
  logic like enabling test modules or running migrations.

## Running custom scripts

Near the end of each run, after sanitization and while the site is still in
maintenance mode, the provision script runs your custom scripts. Use them
for tasks specific to your project, such as enabling modules conditionally
or running migrations in a set order.

To add one, create a file in the `scripts` directory with the `provision-`
prefix and the `.sh` extension, and make it executable with
`chmod +x scripts/provision-50-custom.sh`. The provision script finds it on
the next run, so there's nothing to register. `VORTEX_PROVISION_SCRIPTS_DIR`
changes the directory it looks in (default `./scripts`).

Scripts run in alphabetical order, so start each name with a 2-digit number
to set the order (for example, `provision-50-custom.sh` and
`provision-60-another-custom.sh`). Every matching script runs in every
environment, production included, so each script decides for itself where
it acts; the shipped ones check the environment type first. A script that
exits with an error stops the provisioning.

**Vortex** ships the following scripts:

| Script                                | Purpose                                                  | Present when                                                                                               |
|---------------------------------------|----------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| `provision-00-enable-demo-modules.sh` | Enables the modules and content model the demo site uses | Always; the installer trims its operations to the selected modules                                          |
| `provision-10-enable-dev-modules.sh`  | Enables the development modules and generates content    | Any of `devel`, `sdc_devel`, `generated_content`, `testmode`, or `reroute_email` is selected, or Storybook is enabled; removed by the installer otherwise |
| `provision-20-migration.sh`           | Runs the content migration                               | The migration feature is selected; removed by the installer otherwise                                       |
| `provision-30-search-index.sh`        | Rebuilds the search index                                | The Solr service is selected; removed by the installer otherwise                                            |
| `provision-40-example.sh`             | A runnable example that performs no operations           | Always; copy it as a starting point or remove it                                                            |
| `provision-50-storybook.sh`           | Generates the stories and builds the Storybook component library | Storybook is selected; removed by the installer otherwise                                           |

### Conditional execution

To act only in some environments, read the environment type that the
[Drupal settings file](settings.mdx#environment-type-detection) stores in
`$settings['environment']`:

```shell
environment="$(drush php:eval "print \Drupal\Core\Site\Settings::get('environment');")"

if echo "${environment}" | grep -qxF -e local -e ci -e dev -e stage; then
  echo "> Running custom script for local, ci, dev or stage environment."
  # Place your commands here.
else
  echo "> Skipping custom script for ${environment} environment."
fi
```

To act only on a fresh database, check `VORTEX_PROVISION_OVERRIDE_DB`. The
provision script sets it to `1` for your scripts whenever the database is
new: imported from a dump, installed from a profile, or started from a
container image.

```shell
if [ "${VORTEX_PROVISION_OVERRIDE_DB:-0}" = "1" ]; then
  echo "> Fresh database detected."
else
  echo "> Existing database detected."
fi
```

### Demo modules

**Vortex** ships a `scripts/provision-00-enable-demo-modules.sh` custom
script that stands up the demo site. It creates the content model from the
`recipes/page` recipe, sets the site name, and switches the administration
interface to the core Navigation module. It then installs the contrib,
service, and custom site modules and runs their deployment hooks.

It runs first so that the content model exists before the modules that
depend on it are installed. Replace its operations with your own once the
site stops relying on the demo content.

### Development modules

**Vortex** ships a `scripts/provision-10-enable-dev-modules.sh` custom
script that installs the development modules
([Devel](https://www.drupal.org/project/devel),
[SDC Devel](https://www.drupal.org/project/sdc_devel), and
[Testmode](https://www.drupal.org/project/testmode)) and the
[Reroute Email](https://www.drupal.org/project/reroute_email) safety net.
Projects with Storybook enabled also install the
[Storybook](https://www.drupal.org/project/storybook) module here and, in
the `local` environment, turn on Twig development mode, so component
template edits show up without a cache rebuild.
`scripts/provision-50-storybook.sh` only generates the stories and builds
the component library.

These modules live in their own script so that they stay enabled after the
demo and example scripts are adapted or removed. Their settings files also
add them to `$settings['config_exclude_modules']`, which keeps them out of
the exported configuration, so provisioning is the only place that can
install them.

The demo and development modules scripts both run only in the `local`, `ci`,
`dev`, and `stage` environments, and skip every other environment type. A
project that introduces a custom environment type has to add it to both
scripts to have these modules installed there. That matters for email
rerouting in particular:
[the settings file](modules/contributed-modules.mdx#reroute-email) turns
rerouting on in every environment outside `local`, `ci`, and `prod`, but
only the development modules script installs the module. To opt out of
either set of modules, remove the corresponding script.

### Generated Content

Projects with the [Generated
Content](https://www.drupal.org/project/generated_content) module install it
from the same `scripts/provision-10-enable-dev-modules.sh` custom script,
after the development modules and before the search index is rebuilt.

The module creates content from its own `hook_modules_installed()` when
`GENERATED_CONTENT_CREATE=1` is set, so the script installs it with that
variable and the content appears as part of the install. The site modules
that provide the generated content plugins are already enabled by then, so
the module picks up their plugins.

To opt out of the content, set `DRUPAL_GENERATED_CONTENT_SKIP=1` in the
`.env` file or in your hosting provider's environment variables. The module
is still installed, so you can generate the content later from the admin
interface or with `drush generated-content:create-content`.

Installing a module that's already installed does nothing, so provisioning a
site that already holds the module leaves its content untouched. It also
means the content appears only on the provision that first installs the
module. A site provisioned once with `DRUPAL_GENERATED_CONTENT_SKIP=1`
doesn't gain the content when you unset the variable and provision again.

### Migration

Projects with the migration feature ship a
`scripts/provision-20-migration.sh` custom script that runs the content
migration in every environment except `prod`. It imports the migration
source database dump into the `database2` container, probes it for
corruption, and runs the migrations via `drush migrate:import`, with an
optional rollback before the import.

On projects with the Solr service, the script disables the search server
while the migrations run, so migrated entities aren't indexed one at a time.
The search indexing script rebuilds the index straight after.

➡️ See [Migrations](migrations.mdx#provision-script) for the script's
configuration variables and how to add your own migrations.

### Search indexing

Projects with the Solr service ship with a
`scripts/provision-30-search-index.sh` custom script that rebuilds the
search index at the end of provisioning. It resets the Search API index
tracker and re-indexes the site content.

The script runs only in the `local`, `ci`, `dev`, and `stage` environments.
They receive a database whose index tracker state doesn't match their own
(empty) search backend, while every other environment keeps its existing
index.

To opt out of search indexing, set `DRUPAL_SEARCH_INDEX_SKIP=1` in the
`.env` file or in your hosting provider's environment variables.

## Deploy hooks

Update hooks automate database schema changes, data migrations, and
environment-specific deployment tasks, so a change ships together with the
code that needs it instead of being applied by hand.

Drupal core provides the first 2 kinds of hooks below, and Drush adds the
third.

### Hook types overview

| Hook type                 | Use case                                   | Execution                        | File location            |
|---------------------------|--------------------------------------------|----------------------------------|--------------------------|
| `hook_update_N()`         | Database schema changes, data migrations   | <code>drush&nbsp;updatedb</code> | `MODULE.install`         |
| `hook_post_update_NAME()` | Entity updates and other module operations | <code>drush&nbsp;updatedb</code> | `MODULE.post_update.php` |
| `hook_deploy_NAME()`      | Environment-specific deployment tasks      | <code>drush&nbsp;deploy:hook</code> | `MODULE.deploy.php`   |

All these hooks run automatically during the
[provisioning process](#provisioning-flow): `drush updatedb` runs the update
and post-update hooks, and `drush deploy:hook` runs the deploy hooks.

For changes tied to a deployment, reach for deploy hooks. Each one runs only
once: after it runs, Drush records its name in Drupal's key-value store and
skips it from then on.

### Example deploy hook

```php
function ys_base_deploy_create_about_page(): string {
  $environment = \Drupal\Core\Site\Settings::get('environment');

  // Conditional execution based on environment.
  if ($environment === ENVIRONMENT_PROD) {
    return 'Skipped in production environment';
  }

  // Check if the About Us page already exists.
  $node = \Drupal::entityTypeManager()
    ->getStorage('node')
    ->loadByProperties(['type' => 'page', 'title' => 'About Us']);
  if (!empty($node)) {
    return 'About Us page already exists';
  }

  $node = \Drupal\node\Entity\Node::create([
    'type' => 'page',
    'title' => 'About Us',
    'body' => [
      'value' => 'This is the About Us page content.',
      'format' => 'basic_html',
    ],
  ]);

  $node->save();

  return 'Created About Us page';
}
```

The shipped [Drupal helpers](modules/drupal-helpers.mdx) module provides
static facade helpers for the common deploy hook operations. With them, a
hook stays a few lines long instead of repeating the entity API boilerplate
every time:

```php
use Drupal\drupal_helpers\Helper;

function ys_base_deploy_create_default_tags(): string {
  Helper::term()->createTree('tags', ['News', 'Events', 'Blog']);

  return 'Created the default tags.';
}
```

#### Debugging commands

```shell
# Show pending deploy hooks.
drush deploy:hook-status

# Run deploy hooks manually (for testing).
drush deploy:hook
```
