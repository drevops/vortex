# Acquia

[Acquia](https://www.acquia.com/) is a cloud hosting platform for Drupal
applications, with managed infrastructure and developer tools.

For general Acquia documentation, refer to the
[Acquia Documentation](https://docs.acquia.com/).

This page covers how the site behaves once it runs on Acquia. Acquia deploys
from a Git repository of its own, so CI builds the codebase and pushes it
there. [Artifact deployment](../deployment/artifact.mdx) covers that part.

## Integration

### Tasks

With **Vortex**, you can:

- Fetch a database from an Acquia environment for local development or CI
- Copy the database between Acquia environments (for example, refresh
  staging from production)
- Copy files between environments to synchronize uploaded content
- Purge the Varnish cache so visitors see fresh content

These tasks read the application name (`VORTEX_ACQUIA_APP_NAME`) from your
`.env` file and the Acquia Cloud API credentials (`VORTEX_ACQUIA_KEY` and
`VORTEX_ACQUIA_SECRET`) from `.env.local`.

### Deployment automation

When code is deployed, **Vortex** automatically:

1. Provisions the site: runs database updates, imports configuration,
   rebuilds caches, and runs deployment hooks
2. Purges the Varnish edge cache to serve fresh content
3. Notifies configured channels about the deployment

This is implemented using [Acquia Cloud
Hooks](https://docs.acquia.com/cloud-platform/develop/api/cloud-hooks/):
pre-configured scripts in the
[`hooks/`](https://github.com/drevops/vortex/tree/main/hooks) directory that
trigger on code deployments, code updates, and database copy operations.

The scripts live in `hooks/library/`. `hooks/common/post-code-update/` links
the 3 deployment scripts in numbered order, and the `post-code-deploy` and
`post-db-copy` directories are symlinks to it. So a code deployment, a code
update, and a database copy all run the same 3 steps. The `hooks/prod/`
directories are empty placeholders for production-only scripts, which run
after the common ones.

Set a hook's skip variable to `1` in the Acquia UI to turn it off:

| Hook                   | Variable                             |
|------------------------|--------------------------------------|
| `provision.sh`         | `VORTEX_PROVISION_ACQUIA_SKIP`       |
| `purge-cache.sh`       | `VORTEX_PURGE_CACHE_ACQUIA_SKIP`     |
| `notify-deployment.sh` | `VORTEX_NOTIFY_ACQUIA_SKIP`          |
| `copy-db.sh`           | `VORTEX_TASK_COPY_DB_ACQUIA_SKIP`    |
| `copy-files.sh`        | `VORTEX_TASK_COPY_FILES_ACQUIA_SKIP` |

`copy-db.sh` and `copy-files.sh` sit in `hooks/library/` without a link
from any event directory, so they don't run until you symlink them into
one. By default they copy from `prod` into the environment the hook runs
in, and `copy-db.sh` also needs `VORTEX_TASK_COPY_DB_ACQUIA_NAME`, the name
of the database to copy.

A hook stops with an error when a value it requires is unset or empty. As a
result, a blank field in the Acquia UI aborts the hook rather than running
it with a missing value. `purge-cache.sh` and both copy hooks require
`VORTEX_ACQUIA_KEY` and `VORTEX_ACQUIA_SECRET`, so set both in the Acquia UI
before the first deployment.

`purge-cache.sh` purges the domains listed in `hooks/library/domains.txt`.
The installer writes your domain there as `$TARGET_ENV_REMAP.<domain>`; add
a line for every other domain the site serves.

`$TARGET_ENV_REMAP` expands to `dev` on `dev`, `stage` on `test`, and
`test2` on `test2`. On `prod`, the prefix and its dot disappear. Any other
environment, on-demand ones included, purges nothing.

`notify-deployment.sh` builds the environment URL for notifications as
`https://<site>.<realm>.acquia-sites.com` from Acquia's `AH_SITE_NAME` and
`AH_REALM` variables. Set `VORTEX_NOTIFY_ENVIRONMENT_DOMAIN` in the Acquia
UI to use a custom domain instead, for example `www.example.com`.

### Environment detection

**Vortex** detects Acquia by its `AH_SITE_ENVIRONMENT` variable and then
applies the settings in
[`web/sites/default/includes/providers/settings.acquia.php`](https://github.com/drevops/vortex/blob/main/web/sites/default/includes/providers/settings.acquia.php).
That file includes Acquia's own settings file and maps the Acquia
environment to an environment type. `prod` becomes production, `stage` and
`test` become staging, and everything else, on-demand environments
included, becomes development.

It also points the configuration sync directory at `DRUPAL_CONFIG_PATH` or
Acquia's `config_vcs_directory`, turns on automatic `.htaccess` creation in
writable directories, and sets the temporary file path.

#### Acquia settings file

By default, **Vortex** includes the Acquia-provided settings file from
`/var/www/site-php/{group}/{group}-settings.inc`, where `{group}` is the
value of `AH_SITE_GROUP`. You can override this path by setting the
`DRUPAL_ACQUIA_SETTINGS_FILE` environment variable. If the file doesn't
exist, Drupal stops with an error rather than starting without Acquia's
settings.

#### Temporary file path

**Vortex** configures the path for temporary files (`file_temp_path`) with a
3-tier priority:

1. **Default**: `/tmp`
2. **Shared GFS mount**: when `DRUPAL_TMP_PATH_IS_SHARED` is `1`, the path
   is `/mnt/gfs/{group}.{env}/tmp`, a directory on Acquia's shared file
   system, mounted on each web head. Use it for operations like bulk
   uploads, which need a temporary directory shared across web heads.
   See [Acquia temporary files
   documentation](https://docs.acquia.com/acquia-cloud-platform/manage-apps/files/temporary#section-important-considerations)
   for details.
3. **Explicit override**: a non-empty `DRUPAL_TMP_PATH` wins over both.

## Routine operations

### Fetch database

Fetch a database backup from your Acquia environment for local development
or CI builds:

```shell
ahoy fetch-db
```

When the database source (`VORTEX_FETCH_DB_SOURCE`) is `acquia`, the
installer's default for Acquia projects, the command downloads the latest
Acquia backup. It takes the `VORTEX_FETCH_DB_ACQUIA_DB_NAME` database from
the `VORTEX_FETCH_DB_ENVIRONMENT` environment, which is `prod` in the
shipped `.env`. An existing local dump is reused; add `--fresh` to create a
new backup and download it anyway.

### Run a hosting task

Copying databases or files between environments and purging the edge cache
run through a single, platform-agnostic task runner. It dispatches each
operation to the implementation for the configured hosting platform:

```shell
./vendor/bin/vortex-task <operation>
```

| Operation     | Description                            |
|---------------|----------------------------------------|
| `copy-db`     | Copy the database between environments |
| `copy-files`  | Copy files between environments        |
| `purge-cache` | Purge the edge (Varnish) cache         |

The runner also accepts a fourth operation, `custom`, but only Lagoon
implements it.

The runner reads the platform from `VORTEX_PLATFORM`, or from
`VORTEX_TASK_PLATFORM` to override a single task. The Acquia hooks that run
tasks export `VORTEX_PLATFORM` themselves; set it yourself when running an
operation manually (for example, from your local machine):

```shell
VORTEX_PLATFORM=acquia ./vendor/bin/vortex-task copy-db
```

Each operation reads the application name and API credentials from your
`.env` and `.env.local` files. Outside the hooks, the environments it acts
on have no defaults, so set them for a manual run:

- `copy-db`: `VORTEX_TASK_COPY_DB_ACQUIA_SRC`,
  `VORTEX_TASK_COPY_DB_ACQUIA_DST`, and `VORTEX_TASK_COPY_DB_ACQUIA_NAME`
  (the database name).
- `copy-files`: `VORTEX_TASK_COPY_FILES_ACQUIA_SRC` and
  `VORTEX_TASK_COPY_FILES_ACQUIA_DST`.
- `purge-cache`: `VORTEX_TASK_PURGE_CACHE_ACQUIA_ENV`, plus
  `VORTEX_TASK_PURGE_CACHE_ACQUIA_DOMAINS_FILE` when the domain list isn't
  `domains.txt` in the current directory (the hook uses
  `hooks/library/domains.txt`).

Each operation also takes its own `VORTEX_TASK_<OPERATION>_ACQUIA_KEY`,
`_SECRET`, and `_APP_NAME`, where `<OPERATION>` is `COPY_DB`, `COPY_FILES`,
or `PURGE_CACHE`. They default to `VORTEX_ACQUIA_KEY`,
`VORTEX_ACQUIA_SECRET`, and `VORTEX_ACQUIA_APP_NAME`. Once a task starts,
the operation checks with Acquia every 10 seconds, up to 600 times;
`_STATUS_INTERVAL` and `_STATUS_RETRIES` change those numbers.

### Run Drush against remote environments

To run Drush commands against Acquia environments, download your Drush
aliases from the Acquia Cloud UI. See [Using Drush
aliases](https://docs.acquia.com/acquia-cloud-platform/using-drush-aliases).
