# Migrate a site to Lagoon

Follow this page to move a live Drupal site from another host, such as
Acquia, Pantheon or a virtual machine, onto Lagoon. It's for the lead or
DevOps engineer who runs the move. At the end, the site runs in the Lagoon
production environment and its domains point there.

The move runs in 3 stages:

```text
Copy the site to Lagoon
  │  database and files from the old host, while it stays live
  ▼
Test it on Lagoon
  │  repeat the copy as often as you need
  ▼
Go live
     content freeze, final copy, DNS switch, checks
```

The old host keeps serving the site until the DNS switch, so you can
repeat the first 2 stages until the copy on Lagoon works.

## Before you begin

Make sure you have the following:

- The site's codebase on **Vortex**, with **Lagoon** as the hosting
  provider. To add **Vortex** to the codebase, follow the [existing
  project
  steps](/docs/installation#install-vortex-into-an-existing-project).
- A Lagoon project set up as in [Set up the Lagoon project](setup.mdx).
- SSH access to the old host, and permission to run Drush there.
- `ssh`, `rsync` and the [Lagoon
  CLI](https://github.com/uselagoon/lagoon-cli) on your machine, and your
  SSH key loaded in your `ssh-agent`.
- Your local environment running.

The commands on this page use the project name `your_site`, the
production branch `main` and the SSH endpoint of the amazee.io cluster,
`ssh.lagoon.amazeeio.cloud` on port `32222`. Replace them with your
project's values. [Log in to an
environment](operations.mdx#log-in-to-an-environment) shows how to open a
session in an environment.

## Copy the site to Lagoon

Copy the production database and files into the Lagoon production
environment. The old host keeps serving the site while you work.

### 1. Export the database and files from the old host

Bring the old site's data to your machine first, into the paths that
**Vortex** uses locally:

1. Log in to the old host and go to the old site's Drupal root.
2. Export the production database without cache data to your home
   directory, outside the web root:

   ```shell
   drush sql:dump --structure-tables-list='cache*' > ~/db.sql
   ```

3. Find the old site's public and private files directories:

   ```shell
   drush status --fields=files,private
   ```

4. On your machine, copy the dump into `.data/db.sql`:

   ```shell
   rsync user@old-host.example.com:db.sql .data/db.sql
   ```

   Then delete `~/db.sql` on the old host.

5. Copy the old site's public files into `web/sites/default/files`:

   ```shell
   rsync -rltz user@old-host.example.com:/path/to/files/ web/sites/default/files/
   ```

6. Copy the old site's private files into
   `web/sites/default/files/private`:

   ```shell
   rsync -rltz user@old-host.example.com:/path/to/private/ web/sites/default/files/private/
   ```

   Replace `user@old-host.example.com` with your SSH login on the old host.
   Replace the paths with the directories from step 3.

On Lagoon, **Vortex** keeps private files in
`web/sites/default/files/private`, inside the persistent files storage.
That keeps the `private://` files the database refers to working after
the copy.

### 2. Rehearse the provisioning locally

Run the old database through the same provisioning steps that Lagoon runs
on each deployment, so you fix failures before they reach Lagoon:

1. Import `.data/db.sql` into your local database:

   ```shell
   ahoy import-db
   ```

2. Provision the imported database:

   ```shell
   ahoy cli ./vendor/bin/vortex-provision
   ```

   The command runs the provisioning script directly, so a project that
   stores its database in a container image keeps the imported database.
   It runs database updates, imports configuration, rebuilds caches and
   runs deploy hooks. Fix the codebase until the command finishes with no
   `[FAIL]` line.

Step 4 uploads the `.data/db.sql` file, so changes to your local database
stay local.

### 3. Create the production environment

Deploy the production branch to create the Lagoon environment:

```shell
lagoon deploy branch --project your_site --branch main
```

If CI already deployed `main`, skip this command. The new environment
starts with an empty database. The production deployment never fetches a
database, so its provisioning step stops with
`Unable to import database from file.` The next step fills the database.

### 4. Upload the database and files

To replace the production database and files on Lagoon with your local
copy:

1. Copy the dump into the environment:

   ```shell
   rsync -e "ssh -p 32222" .data/db.sql your_site-main@ssh.lagoon.amazeeio.cloud:/tmp/db.sql
   ```

2. Upload the files:

   ```shell
   rsync -rltz --exclude /css --exclude /js --exclude /php --exclude /styles -e "ssh -p 32222" web/sites/default/files/ your_site-main@ssh.lagoon.amazeeio.cloud:/app/web/sites/default/files/
   ```

   The `--exclude` options skip the directories that Drupal regenerates on
   demand. The upload adds and updates files. It deletes nothing on
   Lagoon, so it keeps the production backups in
   `private/pre_deployment_backups`. A file deleted on the old site after
   an earlier copy stays on Lagoon until you delete it there.

3. [Log in](operations.mdx#log-in-to-an-environment) to the `main`
   environment.
4. Replace the database with the dump, then delete the dump:

   ```shell
   drush sql:drop -y
   drush sql:cli < /tmp/db.sql
   rm /tmp/db.sql
   ```

### 5. Redeploy production

Redeploy the environment, so provisioning runs against the imported
database:

```shell
lagoon deploy latest --project your_site --environment main
```

Provisioning finds the existing site and keeps its content. It runs
database updates, imports configuration, rebuilds caches, runs deploy
hooks and turns maintenance mode off. Confirm that the deployment shows as
complete in the Lagoon UI.

## Test the site on Lagoon

Test the site on its Lagoon route before any domain points at it. The
Lagoon UI lists the route of each environment, such as
`https://nginx-php.main.your_site.au2.amazee.io`.

Check the parts of the site that depend on the host:

- Pages, images and documents load.
- You can log in, and editors can save content.
- A private file downloads for a user with access to it.
- Forms send email.
- Cron runs. Under **Reports > Status report**, the **Cron maintenance
  tasks** row shows a run within the last 15 minutes, the interval set in
  `.lagoon.yml`.
- Search returns results. If the site uses Search API, reindex it first.

To fix a problem, change the codebase, then repeat the copy from [step
1](#1-export-the-database-and-files-from-the-old-host) as often as you
need.

Other environments copy their database from production on each
deployment, so deploy `develop` and pull request branches only after
step 5. [Deployment automation](README.mdx#deployment-automation) lists
the steps.

## Go live

Plan the switch for a quiet time, and tell editors when the content freeze
starts.

1. At least 1 day ahead, lower the time to live (TTL) of each domain's DNS
   records to 300 seconds, so the switch reaches visitors within minutes.
2. Add the production domains to `.lagoon.yml` and deploy them. See [Add
   the domains](domains.mdx#add-the-domains).
3. Freeze content on the old site. Ask every editor to stop. Then log in
   to the old host and, in the old site's Drupal root, put the site in
   maintenance mode:

   ```shell
   drush state:set system.maintenance_mode 1 --input-format=integer
   ```

4. Repeat [step 1](#1-export-the-database-and-files-from-the-old-host),
   [step 4](#4-upload-the-database-and-files) and [step
   5](#5-redeploy-production) to copy the final content. The dump keeps
   the old site's maintenance mode, and the redeployment turns it off on
   Lagoon.
5. Point each domain's DNS records at Lagoon. See [Point DNS at
   Lagoon](domains.mdx#point-dns-at-lagoon).
6. Wait 5 minutes, the TTL you set in the first step of this list, so the
   domains resolve to Lagoon. Then confirm that Lagoon issued a
   certificate for each domain. The following command prints the
   certificate's issuer and expiry date:

   ```shell
   curl -svI https://www.your-site-domain.example 2>&1 | grep -E "issuer|expire date"
   ```

   Lagoon requests a Let's Encrypt certificate after the domain resolves
   to Lagoon, which can take a few minutes.

7. Repeat the checks from [Test the site on
   Lagoon](#test-the-site-on-lagoon) on the production domains.

Keep the old site in maintenance mode and its hosting active until you
no longer need to roll back. To roll back:

1. Ask every editor to stop, including users who can access the site in
   maintenance mode. Then log in to the `main` environment and put the
   site in maintenance mode:

   ```shell
   drush maint:set 1
   ```

2. Copy the content that editors created on Lagoon after the switch to
   the old site by hand.
3. Point the DNS records back at the old host.
4. Log in to the old host and, in the old site's Drupal root, turn
   maintenance mode off:

   ```shell
   drush state:set system.maintenance_mode 0 --input-format=integer
   ```
