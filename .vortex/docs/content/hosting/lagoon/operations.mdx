# Routine operations

Follow this page to run the day-to-day operations on Lagoon environments.
It covers logging in, running Drush, fetching databases and files, running
tasks, taking an environment offline and moving the login page. It's for
the developer or DevOps engineer who maintains a site built from **Vortex**
on Lagoon.

## Log in to an environment

Each environment runs a `cli` container with the codebase, Drush and the
files. To run commands in an environment, log in to its `cli` container
over SSH. Your Lagoon user's SSH key must be loaded in your `ssh-agent`.

```shell
ssh -p 32222 -t your_site-develop@ssh.lagoon.amazeeio.cloud
```

The SSH user is the project name and the environment name joined with a
hyphen. Replace `your_site` with your project name and `develop` with the
environment, such as `main` or `pr-123`. On a cluster other than
amazee.io's, use its SSH host and port.

Confirm that you're logged in. Run `drush status` in the session, and the
output shows the environment's site URI and database.

## Run Drush

Log in to the environment, then run Drush commands there, for example:

```shell
drush cron
```

To run a single command from your machine, use the Drush aliases instead.
The shipped `drush/sites/lagoon.site.yml` file defines an alias for every
environment of the project, such as `@lagoon.develop` or `@lagoon.pr-123`.
[Drush aliases](../../development/environment/drush.mdx#aliases) shows how
to load your SSH key and run commands with them.

## Fetch database

To fetch a database dump from your Lagoon environment for local development
or CI builds, run the following command:

```shell
ahoy fetch-db
```

When the database source (`VORTEX_FETCH_DB_SOURCE`) is `lagoon`, the
command connects over SSH to the `VORTEX_FETCH_DB_ENVIRONMENT` environment.
For Lagoon projects, the installer sets the source to `lagoon` and the
environment to `main`. Both settings live in `.env`. The command dumps the
database in that environment and downloads the dump. It reuses a dump made
earlier the same day, and an existing local dump too. To make a new dump,
add `--fresh`.

## Fetch files

To copy the public files of your Lagoon environment into
`web/sites/default/files`, run the following command:

```shell
ahoy fetch-files
```

For Lagoon projects, the installer sets the files source
(`VORTEX_FETCH_FILES_SOURCE`) to `lagoon`. The command connects over SSH
and copies the files with `rsync`, adding new files and updating changed
ones. The environment comes from `VORTEX_FETCH_FILES_ENVIRONMENT`, or from
`VORTEX_FETCH_DB_ENVIRONMENT` when the first variable is empty. See
[Fetch the files](../../development/provision.mdx#fetch-the-files) for the
directories it skips.

## Run a custom task

The `custom` operation of the `vortex-task` runner runs a command in a
Lagoon environment through the Lagoon CLI. Use it from automation, such as
a CI job, where nobody logs in. Run it from the project root with an SSH
key that your Lagoon user accepts:

```shell
VORTEX_PLATFORM=lagoon \
VORTEX_TASK_CUSTOM_LAGOON_BRANCH=develop \
VORTEX_TASK_CUSTOM_LAGOON_COMMAND="drush cron" \
./vendor/bin/vortex-task custom
```

`VORTEX_TASK_CUSTOM_LAGOON_BRANCH` selects the environment.
`VORTEX_TASK_CUSTOM_LAGOON_COMMAND` holds the command to run there. The
task reads the project name and SSH configuration from your `.env` and
`.env.local` files. Its other settings have defaults:

- `VORTEX_TASK_CUSTOM_LAGOON_NAME` - the task name shown in Lagoon
  (default: `Automation task`)
- `VORTEX_TASK_CUSTOM_LAGOON_PROJECT` - the Lagoon project (default: the
  value of `LAGOON_PROJECT`)
- `VORTEX_TASK_CUSTOM_LAGOON_INSTANCE`,
  `VORTEX_TASK_CUSTOM_LAGOON_INSTANCE_GRAPHQL`,
  `VORTEX_TASK_CUSTOM_LAGOON_INSTANCE_HOSTNAME` and
  `VORTEX_TASK_CUSTOM_LAGOON_INSTANCE_PORT` - the Lagoon instance, with the
  same defaults as the [Lagoon
  deployment](../../deployment/lagoon.mdx#environment-variables)
- `VORTEX_TASK_CUSTOM_LAGOON_SSH_FINGERPRINT` and
  `VORTEX_TASK_CUSTOM_LAGOON_SSH_FILE` - the SSH key (default file:
  `~/.ssh/id_rsa`)
- `VORTEX_TASK_CUSTOM_LAGOON_CLI_PATH`,
  `VORTEX_TASK_CUSTOM_LAGOON_CLI_VERSION` and
  `VORTEX_TASK_CUSTOM_LAGOON_CLI_FORCE_INSTALL` - the Lagoon CLI's install
  directory (default: `/tmp`), its version (default: `v0.32.0`) and a flag
  that reinstalls it when it's already on the path

Confirm that Lagoon accepted the task. With the default name, the output
shows a `Created` line for the task, then ends with the finish line:

```text
[ OK ] Created Automation task: project: your_site, branch: develop.
[ OK ] Finished Lagoon task Automation task.
```

These lines confirm that Lagoon queued the task, not that the command
succeeded, because the Lagoon CLI returns as soon as the task exists.
Follow the task and its output in the environment's tasks in the Lagoon
UI. When Lagoon rejects the request, the script stops with the Lagoon
CLI's error before the `Created` line.

The runner's other operations, `copy-db`, `copy-files` and `purge-cache`,
exist only for Acquia. On Lagoon, they stop with an error that says the
operation `is not supported on the "lagoon" platform`.

## Serve a maintenance page

A static maintenance page takes an environment offline when Drupal must
stay down, for example during a database migration or an incident. The
`nginx` container answers every request with HTTP status 503 and the page,
so no request reaches PHP. Drupal's own [maintenance
mode](../../development/provision.mdx#maintenance-mode) runs in PHP and
needs a working database.

Lagoon applies a changed variable on the next deployment, so each switch is
a variable change followed by a redeployment. To turn the page on, here
on the `main` production environment:

1. Set `VORTEX_WEBSERVER_MAINTENANCE_MODE` to `1` on the environment:

   ```shell
   lagoon add variable --project your_site --environment main \
     --scope runtime --name VORTEX_WEBSERVER_MAINTENANCE_MODE --value 1
   ```

   Only the value `1` turns the page on.

2. Redeploy the environment:

   ```shell
   lagoon deploy latest --project your_site --environment main
   ```

3. Confirm that the environment answers with `503`:

   ```shell
   curl -s -o /dev/null -w "%{http_code}\n" https://www.your-site-domain.example
   ```

To bring the site back:

1. Delete the variable:

   ```shell
   lagoon delete variable --project your_site --environment main \
     --name VORTEX_WEBSERVER_MAINTENANCE_MODE
   ```

2. Redeploy the environment:

   ```shell
   lagoon deploy latest --project your_site --environment main
   ```

`nginx` serves the page for every request that reaches it, including
static files, `robots.txt` and Lagoon's `/.lagoonhealthz` check. Lagoon
checks the container's health on a separate status port, so the environment
stays healthy. Shield runs in Drupal, so the page is public even on
environments that Shield protects.

The page is `.docker/config/nginx/maintenance.html`. The `maintenance.conf`
file in the same directory holds the rules that serve it. Requests for
other files get the maintenance page too, so keep the page self-contained,
with inline styles and images. To preview your changes locally:

1. Rebuild and recreate the `nginx` container with the variable set:

   ```shell
   VORTEX_WEBSERVER_MAINTENANCE_MODE=1 ahoy up --build nginx
   ```

   The local site shows the maintenance page.

2. Recreate the container without the variable to bring the site back:

   ```shell
   ahoy up nginx
   ```

## Move the login page

[Rename Admin Paths](../../development/modules/contributed-modules.mdx#rename-admin-paths)
moves every `/user` route, including `/user/login`, to the path in
`DRUPAL_USER_PATH`. The repository holds no value for the variable, so the
path stays private. Set it on each environment that needs it, here on the
`main` production environment with the path `staff`:

1. Set `DRUPAL_USER_PATH` on the environment:

   ```shell
   lagoon add variable --project your_site --environment main \
     --scope runtime --name DRUPAL_USER_PATH --value staff
   ```

2. Redeploy the environment, so provisioning rebuilds the routes with the
   new path:

   ```shell
   lagoon deploy latest --project your_site --environment main
   ```

3. Confirm that `/user/login` answers with `404`:

   ```shell
   curl -s -o /dev/null -w "%{http_code}\n" https://www.your-site-domain.example/user/login
   ```

   The login form is at `/staff/login`.

To move the login page back to `/user/login`, delete the variable with
`lagoon delete variable` and redeploy the environment.
