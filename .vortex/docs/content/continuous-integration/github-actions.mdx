# GitHub Actions

[GitHub Actions](https://github.com/features/actions) is the continuous
integration and delivery service built into GitHub, so your pipeline runs
right next to the repository and its pull requests. **Vortex** offers it for
projects hosted on GitHub and ships the pipeline in
`.github/workflows/build-test-deploy.yml`, with the security checks in
`.github/workflows/audit.yml`.

This page covers the GitHub Actions side of that pipeline: its triggers, the
nightly schedule, runner size and disk space, manual deployments, and the
coverage and test reports. For GitHub's own reference, see the
[GitHub Actions Documentation](https://docs.github.com/en/actions).

:::info

For information about the CI workflow structure, jobs, and caching strategy,
see the [Continuous integration overview](./README.mdx).

:::

## Onboarding

GitHub Actions onboarding is part of the project setup flow. See [Set up
continuous
integration](/docs/installation?ci-provider=github-actions#7-set-up-continuous-integration)
in the Installation guide and select **GitHub Actions**.

## Maintenance

### Update trigger branches

The workflow builds pushes to the branches listed in `on.push.branches`, and
pull requests that target the branches listed in `on.pull_request.branches`.
Both lists live in `.github/workflows/build-test-deploy.yml`:

**Push triggers** (direct pushes and merges):

| Pattern | Description |
|---------|-------------|
| `production` | Production environment branch |
| `main`, `master` | Default development branches |
| `develop` | Integration branch for ongoing work |
| `release/**` | Release preparation branches (for example, `release/1.2.3`, `release/2023-04-17`) |
| `hotfix/**` | Urgent production fixes (for example, `hotfix/1.2.4`, `hotfix/2023-04-17`) |
| `project/**` | Long-lived project branches for large initiatives |

**Pull request triggers** (PRs targeting these branches):

| Pattern | Description |
|---------|-------------|
| All push branches listed earlier | Same as push triggers |
| `feature/**` | New feature branches (for example, `feature/login`, `feature/123-new-ui`) |
| `bugfix/**` | Non-urgent bug fix branches (for example, `bugfix/fix-auth`, `bugfix/456-crash`) |

The pull request list matches the branch that a pull request targets. A
pull request from `feature/login` into `develop` builds because `develop` is
listed, and the `feature/**` and `bugfix/**` entries cover pull requests
that target another feature or bugfix branch.

Short-lived `feature/**` and `bugfix/**` branches build only through their
pull requests, because their pushes aren't in the push list. Tag pushes
trigger the workflow too (`on.push.tags` is `'*'`), and the `deploy` job
deploys the tag. Pull requests opened from a `project/**` branch skip every
job, since pushes to that branch already build it.

To add or remove branches, edit both lists in the workflow file. The
`Security audit` workflow in `.github/workflows/audit.yml` carries the same
lists, so update it to match.

### Security audit workflow

The security checks live in a second workflow,
`.github/workflows/audit.yml`. It triggers on the same branches and tags as
the main workflow, though not on the nightly schedule. To start it on
demand, use **Actions → Security audit → Run workflow**.

See [Security audit](./README.mdx#security-audit) for what it runs and how
to make it block merges.

### Update nightly database schedule

A scheduled run downloads a fresh database dump every night and caches it,
so the next day's builds start from it. Only the `database` job runs on the
schedule; `lint`, `build`, and `deploy` skip scheduled runs. The scheduled
run also turns off the cache fallback and the front-end build. For a project
that stores its database in a container image, it imports the dump into a
clean base image and pushes the result to the registry.

The schedule ships only when the site provisions from a database dump. To
change when it runs, update the `schedule.cron` value
([cron format](https://crontab.guru/#0_18_*_*_*), UTC timezone):

```yaml
schedule:
  - cron: '0 18 * * *'  # 6 PM UTC daily
```

### Change runner size

Every job in `build-test-deploy.yml` and `audit.yml` runs on
`ubuntu-latest`. For faster builds, switch a job to one of GitHub's [larger
runners](https://docs.github.com/en/actions/using-github-hosted-runners/using-larger-runners)
by changing its `runs-on` value. This may affect your GitHub billing:

```yaml
runs-on: ubuntu-latest-4-cores  # Options: ubuntu-latest, ubuntu-latest-4-cores, etc.
```

Larger runners also come with more disk, which matters for projects whose
provisioning is disk-heavy. See [Runner disk space](#runner-disk-space).

### Runner disk space

GitHub-hosted runners start with most of their root volume already in use.
Measured on 1 `ubuntu-latest` image, preinstalled software occupied 59 GB of
a 72 GB volume, leaving the job around 13 GB. Pulled container images,
database dumps, and every file created while provisioning share what's
left.

**Vortex** keeps the build within that budget:

- The `build` and `database` jobs print `df -h` in a **Report disk usage**
  step, so the disk state is on the record for every run.
- The `build` job prunes the Docker build cache and dangling images once the
  stack is up.
- The `build` job removes the database dump from the runner as soon as it's
  copied into the container, so only 1 copy exists during provisioning.

#### Reclaim the preinstalled toolchains

The `build` and `database` jobs can remove the preinstalled toolchains that
no **Vortex** job uses (GHCup, Swift, PowerShell, .NET, and CodeQL) before
doing anything else. In the preceding measurement, this freed about 15 GB in
around 14 seconds, taking the job from roughly 13 GB of headroom to 28 GB.

The removal is destructive to the runner for the rest of the job, so it's
off by default. Turn it on by setting the `VORTEX_CI_FREE_DISK_SPACE`
variable to `1` in
**Settings → Secrets and variables → Actions → Variables**. Leave it unset
on a project whose workflow runs a step that needs Haskell, Swift,
PowerShell, .NET, or CodeQL.

:::note

Every figure here comes from one runner image at one moment, and GitHub
reissues that image regularly. Read the **Report disk usage** output of a
recent run for the current numbers. If the reclaimed amount has shrunk, the
path list needs revisiting.

:::

#### Free even more space

With `VORTEX_CI_FREE_DISK_SPACE` enabled, the Android SDK is the single
largest remaining tree at about 10 GB, but removing it takes around 50
seconds. That's why it ships commented out in the workflow. To enable it,
uncomment the line in the **Free up disk space on the runner** step of both
the `build` and `database` jobs:

```yaml
set -- "$@" /host/usr/local/lib/android
```

The removal runs through a container that bind-mounts the runner's root
filesystem. It has to, because the job itself runs in a container and can't
see the host's directories directly. For the same reason, the
general-purpose disk-cleanup actions on the Marketplace have no effect in a
**Vortex** job.

#### When space still runs out

If a build dies during provisioning without reporting an error, suspect the
disk and read the **Report disk usage** output. The most reliable fix is to
reduce what has to fit: a sanitized dump or a
[database container image](./README.mdx#caching-strategy) instead of a full
dump. A [larger runner](#change-runner-size) also comes with more disk.

### Change test parallelism

To get through the tests faster, add instances to the `build` job's matrix,
which ships with 2 (`instance: [0, 1]`). See [Using a matrix for your
jobs](https://docs.github.com/en/actions/using-jobs/using-a-matrix-for-your-jobs)
for more information:

```yaml
strategy:
  matrix:
    instance: [0, 1, 2, 3]  # Run tests across 4 containers
```

Every added container that runs Behat also needs a matching `pN` profile in
`behat.php`. See [Test parallelism](./README.mdx#test-parallelism) for the
full procedure, how scenarios are balanced across containers, and how to
move a tool onto a different container.

### Manual deployment

You can deploy straight from the GitHub UI, without running the `lint`,
`database`, or `build` jobs, for example to redeploy a branch or a pull
request that has already passed. Open the **Actions** tab, select the
`Database, Build, Test and Deploy` workflow, click **Run workflow**, and
fill in:

| Input           | Description                                                                                    |
|-----------------|------------------------------------------------------------------------------------------------|
| `deploy_target` | Branch name (for example, `develop`) or PR reference (for example, `PR-123`, case-insensitive) |
| `override_db`   | Override the existing database in the deployment environment                                   |

With `deploy_target` set, every other job skips and only the `deploy` job
runs. For a PR target, the workflow looks up the pull request's head branch
and commit SHA with the GitHub CLI.

With `override_db` checked, the deployment replaces the environment's
database with a fresh copy taken from the production environment. Only
Lagoon deployments act on it, and only when they redeploy an environment
that already exists.

:::note

Artifact deployments don't work with a manual deploy, because the artifact
comes from the `build` job, which a manual deploy skips.

:::

### Terminal access for debugging

The `build` job can start a `tmate` session that lets you connect to the
runner over SSH. Trigger a manual run without a `deploy_target`, check
**Enable terminal session for CI jobs** (the `enable_terminal` input), and
the job log shows the SSH connection details.

The session step runs last and starts even when an earlier step failed, so
you can inspect the failure in place. It gives up after 120 minutes,
connected or not. See
[action-tmate](https://github.com/mxschmitt/action-tmate) for more
information.

### Adjust build timeout

The shipped workflow caps 6 long-running steps at 30 minutes each:
`Fetch DB`, `Export DB`, `Deploy DB image`, `Provision site`,
`Test with Behat`, and `Deploy`. If a build times out, raise the
`timeout-minutes` value of the step that hit the limit:

```yaml
- name: Long running task
  run: ./scripts/long-task.sh
  timeout-minutes: 60  # Default is 360 (6 hours)
```

### Code coverage threshold

The `build` job fails when the line coverage that PHPUnit reports falls
below a threshold.

Set the threshold in the `VORTEX_CI_CODE_COVERAGE_THRESHOLD` variable, under
**Settings → Secrets and variables → Actions → Variables**. It defaults to
`90` (percent). Use a whole number: the check multiplies the value in shell
integer arithmetic, so a decimal such as `85.5` breaks the step.

On pull requests, the job also posts the coverage summary as a comment. Each
new report replaces the previous one, and the older comment is minimized, so
the PR timeline stays clean. To turn the comment off, set
`VORTEX_CI_CODE_COVERAGE_PR_COMMENT_SKIP` to `1`.

### Test results

PHPUnit and Behat results appear in the **Checks** tab of each run. A failed
check links straight to the failing tests and their messages, so you don't
have to download artifacts or dig through logs. The results come from the
JUnit reports the test tools already write, so there's nothing extra to set
up.

Each parallel build instance publishes its own check, named after its index:
`Test results (0)`, `Test results (1)`, and so on. To turn publishing off,
set `VORTEX_CI_TEST_RESULTS_SKIP` to `1` in
**Settings → Secrets and variables → Actions → Variables**. The full logs,
including the raw reports and screenshots, stay attached to the run as the
`test-artifacts-<instance>` artifacts.
