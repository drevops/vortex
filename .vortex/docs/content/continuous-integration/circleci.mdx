# CircleCI

[CircleCI](https://circleci.com/) is a hosted continuous integration and
delivery service. **Vortex** offers it whichever code host you use, while
GitHub Actions is offered only for repositories on GitHub. The pipeline
lives in `.circleci/config.yml`, and the security checks run there as a
separate `audit` workflow.

This page covers the CircleCI side of that pipeline: deployment branches,
the nightly schedule, resource classes, parallelism, timeouts, and the
coverage threshold. Running Renovate on CircleCI adds a second file,
`.circleci/update-dependencies.yml`, with a scheduled trigger of its own
(see [Dependency
updates](../development/dependency-updates.mdx#setting-up-the-self-hosted-service)).
For CircleCI's own reference, see the
[CircleCI Documentation](https://circleci.com/docs/).

:::info

For information about the CI workflow structure, jobs, and caching strategy,
see the [Continuous integration overview](./README.mdx).

:::

## Maintenance

### Update deployment branches

The `database`, `lint`, and `build` jobs of the `commit` workflow and the
`audit` job of the `audit` workflow run on every branch and every tag. The
`deploy` job runs only for branches that match a list of regular expressions
in the `workflows` section of `.circleci/config.yml`:

| Pattern | Description |
|---------|-------------|
| `production` | Production environment branch |
| `main`, `master` | Default development branches |
| `develop` | Integration branch for ongoing work |
| `release/**` | Release preparation branches (for example, `release/1.2.3`, `release/2023-04-17`) |
| `hotfix/**` | Urgent production fixes (for example, `hotfix/1.2.4`, `hotfix/2023-04-17`) |
| `feature/**` | New feature branches (for example, `feature/login`, `feature/123-new-ui`) |
| `bugfix/**` | Non-urgent bug fix branches (for example, `bugfix/fix-auth`, `bugfix/456-crash`) |
| `project/**` | Long-lived project branches for large initiatives |
| `ci*` | Temporary CI testing branches (for example, `ci`, `ci-debug`) |
| `N.x` | Major version branches (for example, `1.x`, `2.x`) |

The patterns in the table are shorthand for those expressions. `release/**`
and `hotfix/**` match only a version after the slash: `1.2.3`, `1.2.3-rc.1`,
`2023-04-17`, or `2023-04-17.1`. `feature/**` and `bugfix/**` match a single
name made of letters, digits, `-`, `.`, `,`, and `_`, so `feature/a/b`
doesn't deploy.

To change which branches deploy, update the regular expressions in the
`only` filter of the `deploy` job. `tests/phpunit/CircleCiConfigTest.php`
checks them against sample branch names, so update its cases to match. It
also checks that no filter pattern exceeds the 128-character limit of the
CircleCI compiler.

2 special cases apply on top of the branch filter:

- The `deploy` job halts early when a `project/*` branch builds for a pull
  request (CircleCI sets `CIRCLE_PULL_REQUEST`), so a long-lived project
  branch deploys on direct pushes but not from its pull requests.
- Tags deploy through a separate `deploy-tags` job, which runs only for tags
  named after a semantic version (`1.2.3`, `1.2.3-rc.1`) or a date
  (`2023-04-17`, `2023-04-17.1`). The `deploy` job itself ignores tags.

### Update nightly database schedule

The `nightly-db` workflow runs the `database-nightly` job: the regular
`database` job with the cache fallback turned off, so it always downloads a
fresh dump and caches it for the next day's builds. It also skips the
front-end build. For a project that stores its database in a container
image, it imports the dump into a clean base image and pushes the result to
the registry.

The workflow is scheduled against the `develop` branch, so change its branch
filter if your project doesn't use one. It ships only when the site
provisions from a database dump.

To change when it runs, update the `nightly_db_schedule` YAML anchor in
`.circleci/config.yml`: a named value near the top of the file that the
workflow's trigger reuses
([cron format](https://crontab.guru/#0_18_*_*_*), UTC timezone):

```yaml
- &nightly_db_schedule "0 18 * * *"  # 6 PM UTC daily
```

### Change runner resource class

For faster builds, raise the [runner resource
class](https://circleci.com/docs/resource-class-overview/) in the shared
`runner_config` block that every job uses. It ships as `medium`. This may
affect your CircleCI billing:

```yaml
resource_class: large  # Options: small, medium, large, xlarge
```

Resource classes scale CPU and memory only. Disk space isn't tied to the
resource class, so upgrading it doesn't help a job that runs out of space.
See [Runner disk space](./README.mdx#runner-disk-space).

### Change test parallelism

To get through the tests faster, raise the `parallelism` of the `build`
job, which ships as `2`. See [Running tests in
parallel](https://circleci.com/docs/parallelism-faster-jobs/) for more
information:

```yaml
build:
  parallelism: 4  # Run tests across 4 containers
```

Every added container that runs Behat also needs a matching `pN` profile in
`behat.php`. See [Test parallelism](./README.mdx#test-parallelism) for the
full procedure, how scenarios are balanced across containers, and how to
move a tool onto a different container.

### SSH access for debugging

CircleCI has built-in SSH access for debugging a failing build. Click the
**Rerun job with SSH** button on a failed job to get the SSH connection
details. See
[Debugging with SSH](https://circleci.com/docs/ssh-access-jobs/) for more
information.

### Adjust build timeout

CircleCI stops a step that prints nothing for 10 minutes. The shipped config
raises that limit to 30 minutes for its long, quiet steps: `Fetch DB`,
`Export DB`, `Deploy DB image`, `Provision site`, `Test with Behat`, and
`Deploy`, plus `Fetch migration DB` when the project has a migration
database. If a step still times out, increase its `no_output_timeout`:

```yaml
- run:
    name: Long running task
    command: ./scripts/long-task.sh
    no_output_timeout: 60m  # Default is 10m
```

### Code coverage threshold

The `build` job fails when the line coverage that PHPUnit reports falls
below a threshold.

Set the threshold in the `VORTEX_CI_CODE_COVERAGE_THRESHOLD` environment
variable, under **Project Settings → Environment Variables**. It defaults to
`90` (percent). Use a whole number: the check multiplies the value in shell
integer arithmetic, so a decimal such as `85.5` breaks the step.

The job can also post the coverage summary as a comment on a GitHub pull
request. That needs a `GITHUB_TOKEN` environment variable with permission
to post comments; without one, the step skips the comment. Each new report
replaces the previous one, and older comments are minimized, so the PR
timeline stays clean. To turn the comment off, set
`VORTEX_CI_CODE_COVERAGE_PR_COMMENT_SKIP` to `1`.
