# Continuous integration

**Vortex** ships a continuous integration pipeline for
[GitHub Actions](./github-actions.mdx) and [CircleCI](./circleci.mdx). Each
run lints your code, builds and provisions the site, and runs the tests. On
the branches you deploy, it then deploys the result once the `build` and
`lint` jobs pass. The pipeline has the same structure on both providers, so
pick the one your project uses and follow its setup instructions.

Every job runs in a container made from the
[`drevops/ci-runner`](https://github.com/drevops/ci-runner) image, so every
run gets the same environment on either provider. Each job that calls a
`vendor/bin/vortex-*` command first installs the
[`drevops/vortex-tooling`](https://packagist.org/packages/drevops/vortex-tooling)
package with `scripts/vortex-tooling.sh`. That script installs the tooling
package on its own, so those commands work before the codebase is assembled.

## Workflow structure

import CodeLifecycle from '../_code-lifecycle.mdx';

<CodeLifecycle/>

### 1. Lint

- Runs in parallel with the other jobs, since it doesn't wait for any of
  them
- Validates the Composer configuration with `composer validate --strict`
- Lints Dockerfiles with Hadolint and Docker Compose files with DCLint
- Starts only the `cli` container, because linting needs no database or
  other services
- Installs the development dependencies
- Checks that the Composer configuration is normalized
- Runs the code linters: PHPCS, PHPStan, Rector, Twig CS Fixer, Gherkin
  Lint, ESLint, and Stylelint

The installer removes the steps of the tools you don't select, so your
pipeline runs only the linters your project uses.

### 2. Database

- Restores the database dump that an earlier run cached, or downloads a
  fresh one when no cache matches (see
  [Caching strategy](#caching-strategy))
- After a fresh download, provisions a site from the dump to check that it
  imports, then exports it in the state it was fetched. Database updates,
  configuration import, and sanitization don't run here.
- Caches the dump, so the `build` job and the runs after it skip the
  download
- On the nightly run of a project that stores its database in a container
  image, pushes the refreshed image to the registry

The job exists only when the site provisions from a database dump. With the
`profile` provision type, the pipeline has no `database` job and no nightly
schedule.

### 3. Build

- Runs after the `database` job and restores the dump that job cached
- Validates the Composer configuration
- Builds the full stack with Docker Compose: the `cli` image build installs
  the Composer packages without development dependencies and builds the
  theme assets
- Exports that codebase for artifact deployments, before any development
  dependency is added
- Installs the development dependencies
- Provisions the site
- Runs the Jest and PHPUnit tests, checks code coverage, posts a coverage
  comment on the pull request, and validates Single Directory Components
  (first container only)
- Runs the Behat (BDD) tests across all containers (see
  [Test parallelism](#test-parallelism))
- Collects and stores the test results and artifacts
- Checks that the build left a clean working tree (see
  [Working tree check](#working-tree-check))

### 4. Deployment

- Runs once both the `build` and `lint` jobs succeed (a
  [manual deployment](./github-actions.mdx#manual-deployment) on GitHub
  Actions runs it on its own)
- Skips the branches that automated dependency updates create (`deps/*`)
- Deploys tags too: GitHub Actions handles them in the same `deploy` job,
  and CircleCI in a separate `deploy-tags` job
- For artifact deployments, ships the codebase that the `build` job
  exported, without development dependencies
- Adds the required secrets and environment variables
- Triggers the deployment through the `vortex-deploy` router script (see
  [Deployment](../deployment/README.mdx))

## Security audit

Security checks run in a workflow of their own, separate from the pipeline
described so far. A failing audit then can't be mistaken for a failing
linter, and you can re-run it on its own:

| Provider | Location |
|----------|----------|
| GitHub Actions | The `Security audit` workflow in `.github/workflows/audit.yml` |
| CircleCI | The `audit` workflow in `.circleci/config.yml` |

The workflow runs the same 4 checks on both providers. None of them needs
the application containers or installed dependencies, so the audit never
waits for a build:

- `composer audit --locked` checks the packages pinned in `composer.lock`
  against published security advisories
- `npm audit --package-lock-only`, run through
  [audit-ci](https://github.com/IBM/audit-ci), checks the packages pinned in
  `package-lock.json` and fails on advisories rated `high` or `critical`.
  Advisories allowlisted in `audit-ci.jsonc` don't count.
- the same `npm audit` runs against the custom theme's own
  `package-lock.json`, with the theme's own `audit-ci.jsonc`
- [Gitleaks](../development/security/secret-scanning.mdx) scans the codebase
  for committed secrets

Only the Composer check is always present. The root npm check ships when
your project keeps ESLint, Stylelint, or Jest, and the theme check ships
with a custom theme. The Gitleaks check ships when you turn on secret
scanning at install time.

Every check runs even if an earlier one failed, so a single run reports all
the findings at once. The workflow fails if any check failed, unless that
check's `_IGNORE_FAILURE` variable (see
[Ignore tool failures](#ignore-tool-failures)) is set to `1`.

The workflow runs on the same pushes, pull requests, and tags as the main
pipeline, though not on its nightly schedule. You can also start it on
demand. In GitHub Actions, use **Actions → Security audit → Run workflow**.
In CircleCI, re-run the `audit` workflow from the pipeline view.

:::note

The audit is a separate workflow and isn't a dependency of the `deploy` job,
so a failing audit doesn't by itself stop a deployment. To block merges on
it, add its check to the repository's branch protection rules as a required
status check.

:::

### Code scanning

On GitHub Actions, every check also writes its findings as
[SARIF](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning),
the interchange format that code scanning reads. The workflow uploads them
to the repository's **Security → Code scanning** tab, each under its own
category:

| Category | Findings |
|----------|----------|
| `composer-audit` | `composer audit` advisories, abandoned packages, and dependency policy matches |
| `npm-audit` | `npm audit` advisories for the root `package-lock.json` |
| `npm-audit-theme` | `npm audit` advisories for the custom theme's `package-lock.json` |
| `gitleaks` | Committed secrets |

Code scanning keeps a history of every finding and tracks whether it's open
or fixed. Dismissing a false positive records the reason in the alert,
instead of in a committed ignore entry.

Gitleaks writes SARIF itself. Neither `composer audit` nor `npm audit` has a
SARIF formatter, so each of those checks runs once in JSON format and pipes
its output through `tee`. That single run feeds both the job log and a
report file in `.logs/audit/`. The npm checks pass
`--output-format json --report-type full` to `audit-ci`, which then prints
npm's own report.

The `vortex-convert-audit-sarif` script from the
[Vortex tooling package](../contributing/maintenance/tooling.mdx) converts
each report file. The workflow passes the report format, `composer` or
`npm`, as the script's second argument, which takes precedence over
[`VORTEX_CONVERT_AUDIT_SARIF_FORMAT`](../development/variables.mdx#vortex_convert_audit_sarif_format).

The reporting path doesn't decide whether the workflow passes. Only the
check steps fail it on findings. They run before the conversion and upload
steps, and those later steps can't fail the workflow.

Code scanning has to be available on the repository. It's included on
public repositories and on private repositories with GitHub Advanced
Security. Where it isn't available, and on pull requests from forks where
the workflow token is read-only, the upload step fails without failing the
workflow. The checks still report their findings in the job log and still
fail the workflow. Every report is also attached to the run as the
`security-findings` artifact.

CircleCI has no code scanning destination, so the providers deliberately
differ here. On CircleCI the same checks run and fail the `audit` workflow,
but their findings live only in the job log.

➡️ See [Dependency
audit](../development/security/dependency-audit.mdx#dismissing-a-finding)
and [Secret
scanning](../development/security/secret-scanning.mdx#dismissing-a-finding)
for what dismissing a finding does and doesn't change.

## Working tree check

A build can produce files that belong in the repository, such as exported
configuration, compiled front-end assets, generated documentation, and
scaffolded files. Left unnoticed, the repository and the build output drift
apart, and whoever builds next inherits a dirty working tree they didn't
cause.

The `build` job runs `vendor/bin/vortex-check-worktree-changes` after the
tests, once their results are stored, so a dirty tree never suppresses the
results that would explain it. The step fails when the working tree holds
modified or untracked files, and it prints each one with its Git status:

```shell
[INFO] Started working tree check.
       Ignoring "docker-compose.yml".
       Ignoring "*/docker-compose.yml".
       Ignoring "db_cache_*".
       Ignoring "codecov".
       Ignoring "codecov.SHA256SUM".
       Ignoring "codecov.SHA256SUM.sig".
       The build modified or created these files:
 M config/default/core.extension.yml
?? config/default/views.view.recent_content.yml
       Run "ahoy build" locally and commit the resulting changes.
       Add paths that are generated during the build and are not committed to VORTEX_CHECK_WORKTREE_CHANGES_IGNORE.
[FAIL] The build left changes in the working tree.
```

Git never reports the files it ignores, so `.gitignore` already covers most
generated output. Everything else goes into
`VORTEX_CHECK_WORKTREE_CHANGES_IGNORE`, a comma-separated list of
[Git pathspec](https://git-scm.com/docs/gitglossary#def_pathspec) patterns.
Set it in `.env`, which the script loads:

```shell
VORTEX_CHECK_WORKTREE_CHANGES_IGNORE=docker-compose.yml,*/docker-compose.yml,db_cache_*,codecov,codecov.SHA256SUM,codecov.SHA256SUM.sig,web/sites/default/settings.generated.php
```

The default value covers what the pipeline itself drops into the working
tree:

- every `docker-compose.yml` in the tree, which the
  `Process the codebase to run in CI` step rewrites in place
- the `db_cache_*` files that hold the database cache keys
- the `codecov` uploader and its 2 signature files

Those files exist only during a continuous integration run, so they're
excluded here rather than in `.gitignore`, which every checkout carries.
Setting the variable replaces the default instead of extending it, so copy
those entries over when you add your own.

The check reads the working tree on the runner, not the codebase inside the
`cli` container.

Set `VORTEX_CI_WORKTREE_CHANGES_IGNORE_FAILURE` to `1` to report the
findings without failing the build (see
[Ignore tool failures](#ignore-tool-failures)).

## Caching strategy

Downloading the database on every run would slow builds down, so a
scheduled run fetches a fresh dump overnight and caches it. The runs that
follow restore that cached dump instead of downloading their own.

The cache key combines a version prefix, the cache source branch, the
fallback setting, and a daily timestamp. The branch comes from
`VORTEX_CI_DB_CACHE_BRANCH` (`develop` by default), and the timestamp from
`VORTEX_CI_DB_CACHE_TIMESTAMP`, a `date` format that defaults to
`+%Y%m%d`. The branch being built isn't part of the key, so every run on
any branch reads the same shared cache.

When no cache exists for the current day, a run falls back to the most
recent earlier cache for the same source branch, normally the previous
day's. `VORTEX_CI_DB_CACHE_FALLBACK` controls this and defaults to `yes`.
The scheduled run sets it to `no`, so it always downloads a fresh dump.

The 3 variables live in the CI configuration: in the container `env` block
of the `database` and `build` jobs on GitHub Actions, and in the shared
`runner_config` block on CircleCI.

:::note

Caching makes the biggest difference on projects with a lot of data.

With a large database (over 1 GB), the import itself can take a long time.
At that point it's worth packaging the dump into a container image
overnight, or using a sanitized dump that holds only the data the tests
need.

**Vortex** can both create and use a database container image with the data
built in. Use [MariaDB data container for Drupal with database captured as
Docker layers](https://github.com/drevops/mariadb-drupal-data) to create the
first image.

Other tools serve the same goal. [Drush GDPR
Dumper](https://github.com/robiningelbrecht/drush-gdpr-dumper), for example,
removes data during the Drush database export itself, with no intermediate
import step.

:::

### Reset the cache

To force a fresh cache (for example, to pull a new database dump outside the
regular schedule), increment the last segment of the version prefix in the
cache keys. The `database` and `build` jobs both use it, so change every
occurrence:

```yaml
# Before
v26.8.1
# After
v26.8.2
```

The next run finds no cache under the new prefix, so the `database` job
downloads a fresh dump and caches it.

The prefix is a calendar-style stamp (`vYY.M.Z`) that **Vortex** moves
forward when an update needs to reset every project's cache. Bumping only
its last segment keeps a project's own cache resets from colliding with the
prefix shipped by a future **Vortex** update.

## Trigger conditions

Both providers build on branch pushes, pull requests, and tag pushes, plus
a nightly schedule that refreshes the database cache (only when the site
provisions from a database dump). They deploy tags differently: GitHub
Actions deploys every tag it builds, and CircleCI deploys only tags named
after a semantic version (`1.2.3`, `1.2.3-rc.1`) or a date (`2023-04-17`,
`2023-04-17.1`).

The exact branch filters differ per provider:

- **GitHub Actions** builds pushes to long-lived branches (`production`,
  `main`, `master`, `develop`, `release/**`, `hotfix/**`, and
  `project/**`). A pull request from any branch builds when it targets one
  of those branches, or a `feature/**` or `bugfix/**` branch, which is how
  short-lived branches get built. Pull requests opened from a `project/**`
  branch skip every job, because pushes to that branch already build it. See
  [GitHub Actions](./github-actions.mdx#update-trigger-branches).
- **CircleCI** builds every pushed branch and restricts only the `deploy`
  job to a configured branch list. See
  [CircleCI](./circleci.mdx#update-deployment-branches).

## Test parallelism

The `build` job runs on 2 containers in parallel by default, to get through
the tests faster. Each container repeats the full build and provisioning,
so the pipeline splits the test work between them instead of running every
test on every container.

Code linting runs in the separate `lint` job, so the parallelism settings
don't affect it.

### What runs where

| Task | First container | Other containers |
|------|:---:|:---:|
| Jest tests | ✓ | - |
| PHPUnit tests | ✓ | - |
| Code coverage check and PR comment | ✓ | - |
| Single Directory Component validation | ✓ | - |
| Behat tests | ✓ (profile `p0`) | ✓ (profile `p1`, `p2`, and so on) |

Everything except Behat runs on the first container only, since running it
on every container would repeat the same work. Behat runs on all
containers, and its profiles decide which scenarios run where.

### Choosing which container runs what

Each tool reads a `VORTEX_CI_IS_<TOOL>_RUNNER` variable that decides whether
it runs on the current container. The variables sit together at the top of
the `build` job, so you can see and change the whole split in one place:

<Tabs queryString="ci-provider" groupId="ci-provider">
<TabItem value="gha" label="GitHub Actions">

```yaml title=".github/workflows/build-test-deploy.yml"
env:
  VORTEX_CI_RUNNER_INDEX: ${{ strategy.job-index }}
  VORTEX_CI_RUNNER_TOTAL: ${{ strategy.job-total }}
  VORTEX_CI_IS_JEST_RUNNER: ${{ matrix.instance == 0 || strategy.job-total == 1 }}
  VORTEX_CI_IS_PHPUNIT_RUNNER: ${{ matrix.instance == 0 || strategy.job-total == 1 }}
  VORTEX_CI_IS_SDC_DEVEL_RUNNER: ${{ matrix.instance == 0 || strategy.job-total == 1 }}
  VORTEX_CI_IS_BEHAT_RUNNER: true
  VORTEX_CI_BEHAT_PROFILE_OFFSET: 0
```

Each tool's step then reads its own flag:

```yaml
- name: Test with PHPUnit
  if: ${{ env.VORTEX_CI_IS_PHPUNIT_RUNNER == 'true' }}
```

</TabItem>
<TabItem value="circleci" label="CircleCI">

```yaml title=".circleci/config.yml"
- run:
    name: Set test runner roles
    command: |
      {
        echo "export VORTEX_CI_RUNNER_INDEX=${CIRCLE_NODE_INDEX:-0}"
        echo "export VORTEX_CI_RUNNER_TOTAL=${CIRCLE_NODE_TOTAL:-1}"

        echo "export VORTEX_CI_IS_PHPUNIT_RUNNER=$([ "${CIRCLE_NODE_INDEX:-0}" -eq 0 ] && echo 1 || echo 0)"
        echo "export VORTEX_CI_IS_SDC_DEVEL_RUNNER=$([ "${CIRCLE_NODE_INDEX:-0}" -eq 0 ] && echo 1 || echo 0)"
        echo "export VORTEX_CI_IS_BEHAT_RUNNER=1"

```

```yaml
- run:

```

</TabItem>

container's index and the container count, under the same names on both
providers. The Behat step subtracts `VORTEX_CI_BEHAT_PROFILE_OFFSET` from
the container index to get its profile number (see
[Giving a tool its own container](#giving-a-tool-its-own-container)).

To run a tool of your own on a specific container, add 1 more flag
alongside the others and reference it from your step:

#### Giving a tool its own container

Start by [adding a container](#adding-more-containers) for the tool to move
onto, since the default configuration has only containers `0` and `1`. Then
point the tool's flag at the new container and exclude that container from
Behat. With a third container added, it looks like this (GitHub Actions
shown; mirror the conditions in CircleCI's `Set test runner roles` step):

```yaml
VORTEX_CI_IS_PHPUNIT_RUNNER: ${{ matrix.instance == 2 }}
VORTEX_CI_IS_BEHAT_RUNNER: ${{ matrix.instance != 2 }}
```

:::warning

Point the flag at a container that exists. A flag whose condition matches no
container disables the tool everywhere, and nothing reports it: the steps
are skipped and the job still passes.

:::

Behat derives its profile number from the container index minus
`VORTEX_CI_BEHAT_PROFILE_OFFSET`, and `p0` is the catch-all that runs every
scenario without a `@pX` tag. With the dedicated container at the end, the
offset stays `0`, and the containers before it keep their profiles.

To dedicate a leading container instead, raise the offset by 1 for each
leading container you exclude from Behat, so the first Behat container still
selects the `p0` catch-all. The following example, on 3 containers, pins
every once-only tool to container `0` and keeps Behat off it:

```yaml
VORTEX_CI_IS_JEST_RUNNER: ${{ matrix.instance == 0 }}
VORTEX_CI_IS_PHPUNIT_RUNNER: ${{ matrix.instance == 0 }}
VORTEX_CI_IS_SDC_DEVEL_RUNNER: ${{ matrix.instance == 0 }}
VORTEX_CI_IS_BEHAT_RUNNER: ${{ matrix.instance != 0 }}
VORTEX_CI_BEHAT_PROFILE_OFFSET: 1
```

| Container | Role | Behat profile |
|-----------|------|:---:|
| 0 | Jest, PHPUnit, coverage, SDC validation | - |
| 1 | Behat | `p0` (catch-all) |
| 2 | Behat | `p1` |

`behat.php` stays untouched: the profiles stay numbered from `p0`, and no
feature file needs new tags.

:::warning

When `VORTEX_CI_BEHAT_PROFILE` is unset, the offset describes 1 unbroken
block of Behat containers that starts at the offset. A Behat container below
the offset derives a negative profile name such as `p-1`, and the run
fails. A gap inside the block leaves the profile at the gap's position
unselected, so its scenarios silently stop running. Setting
`VORTEX_CI_BEHAT_PROFILE` explicitly bypasses the derivation, and every
container then runs that profile.

:::

### Balancing Behat tests

The first container runs Jest, PHPUnit, and the coverage checks on top of
its share of Behat, so it has the most work to do. To keep the whole build
short, give the other containers more of the Behat scenarios.

Profile tags decide where each scenario runs. A scenario without a profile
tag runs on the first container. Tag it `@p1` to move it to the second
container, or `@smoke` to run it on every container:

```gherkin
Scenario: Quick smoke test (untagged, stays on the first container)
  Given I go to the homepage
  Then I should see "Welcome"

@p1
Scenario: Full content workflow (runs on the second container)
  Given I am logged in as a user with the role "content_editor"
  ...
```

With only 1 container, every scenario runs there whatever its tags, except
those tagged `@skipped`.

:::tip

As a rule of thumb, keep the lightweight scenarios on the first container
and move the heavier ones, or more of them, to the other containers (`@p1`,
`@p2`, and so on). The build then takes about as long as its slowest
container, instead of the sum of all the tests.

`@smoke` scenarios check that Behat itself is configured and working. They
run on every container by design, so keep them few and fast.

:::

See [Behat > Profiles](../development/testing/behat.mdx#profiles) for how
the shipped profiles map tags to runners.

### Adding more containers

Raising the container count takes 2 changes that must stay in step: the
container count itself, and a matching Behat profile for every new
container.

1. Increase the container count. See the provider-specific pages:

   - [GitHub Actions > Change test
     parallelism](./github-actions.mdx#change-test-parallelism)
   - [CircleCI > Change test
     parallelism](./circleci.mdx#change-test-parallelism)

2. Add a profile to `behat.php` for each new container that runs Behat,
   and register it in the returned `Config`. **Vortex** ships with `p0`
   and `p1` only. If a container running Behat has no profile named after
   its derived number (its index minus `VORTEX_CI_BEHAT_PROFILE_OFFSET`),
   Behat stops with ``Can not find configuration for `p2` profile.`` A
   container excluded from Behat needs no profile:

   ```php title="behat.php"
   $p2 = (new Profile('p2'))
     ->withGherkinOptions((new GherkinOptions())->withCacheDir('/tmp/behat_gherkin_cache')->withFilter(new TagFilter('@smoke,@p2&&~@skipped')));

   return (new Config())->withProfile($default)->withProfile($p0)->withProfile($p1)->withProfile($p2);
   ```

3. Exclude the new tag from the `p0` catch-all, so its scenarios don't also
   run on the first container:

   ```php title="behat.php"
   $p0 = (new Profile('p0'))
     ->withGherkinOptions((new GherkinOptions())->withCacheDir('/tmp/behat_gherkin_cache')->withFilter(new TagFilter('@smoke,~@p1&&~@p2&&~@skipped')));
   ```

4. Tag scenarios with `@p2` to move them onto the new container.

Scenarios tagged `@smoke` run on every container by design, so they stay out
of the balancing arithmetic.

## Maintenance

### Pin SSH host keys

Strict host-key checking is disabled by default for the SSH connections the
pipeline makes to the hosting provider. Pinning the host keys is the secure
alternative. Add the verified host keys as a `VORTEX_SSH_KNOWN_HOSTS`
variable, and the SSH setup writes them to `known_hosts` and keeps strict
checking on, even where `VORTEX_SSH_DISABLE_STRICT_HOST_KEY_CHECKING` is
set.

On GitHub Actions, add it as a repository variable and map it into the
workflow `env` block yourself, because the shipped workflow doesn't
reference it. On CircleCI, add it as an environment variable with multiple
entries joined with `\n`.

On GitHub Actions, the steps that load the SSH keys also skip their
`known_hosts` file by default. Set the `VORTEX_FETCH_DB_SSH_KNOWN_HOSTS`
(database fetch) and `VORTEX_DEPLOY_SSH_KNOWN_HOSTS` (deployment) repository
variables to pin those host keys too.

### Enable debug mode

For verbose output while you troubleshoot a failing build, set the
`VORTEX_DEBUG` variable to `1` in your CI provider's settings. The
**Vortex** scripts then print every command they run.

### Runner disk space

Hosted runners come with a fixed amount of disk space, and running out of it
produces a misleading failure. The runner is terminated from the outside,
the step that was running never reports an error, and the failure looks like
a hang rather than a disk problem. If a build dies during provisioning
without reporting an error, suspect the disk first.

The most reliable fix is to reduce what has to fit: a sanitized dump or a
[database container image](#caching-strategy) instead of a full dump.

- On GitHub Actions, **Vortex** prints the disk state in the `build` and
  `database` jobs of every run, and can reclaim space held by preinstalled
  toolchains. See [GitHub Actions > Runner disk
  space](./github-actions.mdx#runner-disk-space).
- On CircleCI, disk space isn't tied to the [resource
  class](./circleci.mdx#change-runner-resource-class), so upgrading it adds
  CPU and memory but no extra room for the build.

### Update CI runner image

The CI jobs run inside the
[`drevops/ci-runner`](https://github.com/drevops/ci-runner) container, a
Docker image built for running CI jobs. It provides a consistent,
reproducible environment with 25+ pre-installed tools:

- **PHP & Node.js** - PHP 8.4, Node.js, Composer, npm, Yarn
- **Docker tools** - Docker, Docker Compose, Docker Buildx
- **Code quality** - ShellCheck, shfmt, Bats testing framework
- **Utilities** - Git, curl, rsync, jq, and more

Both providers run every job on this image, so a build doesn't depend on
whatever tools a provider happens to install. The image also speeds builds
up, because the jobs don't reinstall the same common tools on every run.

The image follows [CalVer](https://calver.org/) versioning (for example,
`26.10.0`) with monthly releases. The CI configuration pins it by tag and by
digest (`drevops/ci-runner:26.10.0@sha256:...`), and the digest fixes the
exact image. To update, change the tag and its `@sha256:` digest together,
everywhere the image appears: each job in
`.github/workflows/build-test-deploy.yml`, the job in
`.github/workflows/audit.yml`, and the shared `runner_config` block in
`.circleci/config.yml`.

When Renovate manages your dependencies (the installer's default), it
proposes new image releases for the GitHub Actions workflows. Nothing in its
configuration matches the `image:` line in `.circleci/config.yml`, so on
CircleCI the update is yours to make.

### Ignore tool failures

Sometimes you want a build to pass despite linter or test failures, for
example while you clear the findings of a rule you just enabled.

Set the corresponding `VORTEX_CI_*_IGNORE_FAILURE` variable to `1` to let
the build pass. The tool still runs and prints its results in the job log,
so you can see what you're letting through. On GitHub Actions, add the
variable under **Settings → Secrets and variables → Actions → Variables**;
on CircleCI, add it as a project environment variable.
