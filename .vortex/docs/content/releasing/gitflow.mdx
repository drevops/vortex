# GitFlow versioning workflow

[git-flow](https://nvie.com/posts/a-successful-git-branching-model/) is a
versioning workflow: a branching model that keeps development code and
production code apart. Work lands on `develop`, `main` holds only
production-ready code, and a short-lived branch carries each feature,
release, and hotfix. **Vortex** builds its defaults around these branch
names: the CI triggers, the deployment branch patterns, and the release
notes workflow all expect them.

```text
develop ──► git flow release start X.Y.Z
                     │
                     ▼
             release/X.Y.Z
             (final fixes, release notes)
                     │
                     ▼
            git flow release finish X.Y.Z
                     │
                     ├──► merges into `main` and tags `X.Y.Z`
                     ├──► merges back into `develop`
                     │
                     ▼
            deploy the `X.Y.Z` tag
            (or push `main` to `production` for branch-based hosting)
```

## Branch structure

- **`develop`** - the development branch, where features are integrated
- **`main`** - production-ready code, always stable and tagged with releases
- **`feature/*`** - a branch for each feature in development
- **`release/*`** - release preparation branches (for example,
  `release/25.1.0`)
- **`hotfix/*`** - emergency fixes for production (for example,
  `hotfix/25.1.1`)

<details>
  <summary><code>production</code> branch</summary>

  Most hosting providers can deploy a specific Git tag directly. Then you
  need no separate `production` branch: you tag releases on `main` and
  deploy those tags.

  Some providers, Lagoon among them, deploy only from a Git branch, and the
  **Vortex** Lagoon deployment skips tags. On those, you must create a
  `production` branch and sync code from `main` to `production` after each
  release.

  CI could copy `main` to `production` whenever a release is tagged, but
  **Vortex** deliberately leaves that step to a person. That way, nothing
  reaches production without someone deciding it should.

</details>

## Release operations

A typical git-flow release follows these steps. See the
[cheat sheet](https://danielkummer.github.io/git-flow-cheatsheet/) for a
quick reference on git-flow commands.

1. **Start the release**

   ```shell
   git flow release start X.Y.Z
   ```

   This creates a `release/X.Y.Z` branch from `develop`. We recommend
   pushing the branch to the remote: CI builds and deploys `release/*`
   branches, so the release gets its own build and deployment for final
   testing.

2. **Prepare the release**
   - Final bug fixes
   - Documentation updates
   - Release notes preparation

3. **Finish the release**

   ```shell
   git flow release finish X.Y.Z
   ```

   - Merges the release branch to `main`
   - Tags the release
   - Merges back to `develop`
   - Deletes the release branch

4. **Deploy to production**
   - **Tag-based hosting:** deploy the tag directly
   - **Branch-based hosting (for example, Lagoon):** manually sync to the
     `production` branch

     ```shell
     git push origin main:production
     ```

## Expected release outcome

A successful release meets these criteria (they also ship in your project's
`docs/releasing.md`):

1. Release branch exists as `release/X.Y.Z` in the GitHub repository
2. Release tag exists as `X.Y.Z` in the GitHub repository
3. The `HEAD` of the `main` branch has the `X.Y.Z` tag
4. The hash of the `HEAD` of the `main` branch exists in the `develop`
   branch
   - Everything pushed to `main` then also exists in `develop`
   - Important if `main` had any hotfixes not yet merged to `develop`
5. GitHub has no open PRs related to the release
6. On branch-based hosting, the hash of the `HEAD` of the `production`
   branch matches the hash of the `HEAD` of the `main` branch
